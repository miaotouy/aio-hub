一、后台分发壳与可重建工作台 ​

1. 设想与出发点 ​

目前我们的桌面端把 main 窗口（主工作台）当成了“万能工具人”：它既是用户操作的界面，又是托盘唤醒、单实例启动、Deep Link 导航的承载体，还顺便跑着各种全局状态同步。

设想是：能不能搞一个不露脸的“后台分发壳”（比如一个隐藏窗口或纯后台进程），让它来管所有窗口？ 这样一来：

  • 主工作台 main 就变成了一个普通的、可随时销毁和重建的窗口。
  • 哪怕用户把主工作台关了，后台任务、托盘和单实例唤醒依然能正常工作。

2. 核心结论 ​

完全可行，而且不需要塞一个偷偷运行的隐藏网页。

  1. Tauri 2 支持“零窗口”运行：我们不需要为了维持应用生命周期而特意挂一个隐藏的 WebView。只要在最后一个窗口关闭时阻止默认退出（prevent_exit），Tauri 的事件循环、托盘和 Rust 后台任务就能一直活着。
  2. 现在的 main 已经是动态创建的：它没有在 tauri.conf.json 里写死，而是 Rust 在 setup 阶段动态 New 出来的。所以从技术上讲，它随时可以被销毁和重新创建。
  3. 真正的难点在前端的历史债：代码里有太多地方硬编码了 "main" 这个名字。如果现在贸然允许销毁 main 或者改名，同步系统和窗口管理会直接罢工。

3. 两种轻量级的后台形态 ​

如果以后要实现这个设想，我们有以下两种选择，都比“挂一个隐藏的完整网页”要省资源得多：

形态实现方式优点缺点 / 注意事项
零窗口运行拦截 ExitRequested 事件，在没有窗口时保持 Rust 进程存活。结构最干净，零额外内存开销。必须严谨处理“用户在托盘点退出”和“系统关机”的语义，防止进程残留。
隐藏原生窗口用 WindowBuilder 创建一个不带 WebView 的原生隐藏窗口作为哨兵。避开了复杂的退出事件拦截，生命周期更稳妥。虽然不带网页，但依然是一个系统窗口对象（开销极小，但存在）。

注：极不建议使用“隐藏的 WebviewWindow”来当后台。那相当于在后台偷偷跑一套 Vue、Pinia 和各种工具实例，白白浪费几十兆内存，还会带来一堆多实例同步的诡异 Bug。

4. 拦路虎：当前代码的硬编码耦合 ​

如果我们想让主工作台 main 能够被安全地销毁和重建，必须先清理以下历史债务：

4.1. 前端对 "main" 标签的身份依赖 ​

前端的 useWindowSyncBus 和状态同步引擎严重依赖 "main" 这个字符串。

  • 很多服务通过判断 windowType === 'main' 来决定自己是“状态源（老大）”还是“同步端（小弟）”。
  • 如果 main 窗口被销毁了，谁来当老大？重建 main 之后，它怎么重新夺回控制权？这需要一套更动态的“主从选举”或“状态下沉 Rust”机制。

4.2. 窗口数量的粗暴统计 ​

托盘（tray.rs）和事件（events.rs）里，目前是用 app.webview_windows().len() 来判断“用户是不是把所有窗口都关了”。

  • 如果引入了隐藏的后台窗口，这个计数就会出错（永远多算一个），导致托盘和隐藏逻辑混乱。
  • 以后需要改成“只统计用户可见的业务窗口”。

4.3. 唤醒与导航直接定位 "main" ​

单实例唤醒、托盘点击、Deep Link 导航等路径，目前都是简单粗暴地 get_webview_window("main")。

  • 如果主工作台被销毁了，这些路径会直接拿到 None 然后什么都不发生。
  • 必须升级为“如果不存在，就先创建，再执行导航”的幂等唤醒逻辑。

5. 状态与体验的边界问题 ​

在讨论后续设想时，我们需要明确一个体验边界：销毁窗口 $\neq$ 隐藏窗口。

  • 如果只是隐藏（Hide）：网页还在内存里，用户再次打开时，输入到一半的表单、未保存的草稿、Pinia 的临时状态都在，体验是无缝的。
  • 如果是销毁（Destroy）：网页彻底死掉，内存释放。再次打开时是重新加载网页。
    • 除非我们把所有草稿和临时状态都实时落盘（或者下沉到 Rust 后台），否则重建窗口后，用户会面对一个“全新打开”的空白工作台。
    • 建议：如果只是为了释放内存，销毁重建是值得的；但如果为了保留用户现场，日常关闭主窗口时，托盘默认行为依然应该是“隐藏”，只有在极少数情况下（如崩溃恢复、重载配置）才执行“销毁重建”。

6. 给后续设想的铺垫建议 ​

如果以后想往这个方向推进，我们不需要一次性搞个大重构，可以先做两件顺手的事来铺垫：

  1. 收拢窗口创建入口：在 Rust 侧，把创建 main 窗口的代码从 lib.rs 的 setup 里抽出来，封装成一个 ensure_main_window() 函数。让托盘和单实例唤醒都走这个入口。
  2. 减少前端硬编码：前端写新工具或新同步逻辑时，尽量避免直接写死 windowLabel === 'main'，而是通过配置或初始化参数来声明窗口角色。

二、WebView 小部件与原生绘制 ​

1. 调查边界 ​

这里不讨论把 AIO Hub 主窗口或复杂工具整体迁移到 Rust UI。目标仅限于常驻、置顶、透明或点击穿透的小部件，例如：

  • 弹幕覆盖层、实时字幕框；
  • 系统状态 HUD、进度与任务状态条；
  • 以文本、图标、简单图表和少量拖动操作为主的悬浮组件。

复杂表单、设置页、富文本、编辑器和主要工具窗口仍适合使用 Tauri + Vue。原生化的价值主要来自减少每个常驻小窗口的 WebView 固定成本，而不是替换现有前端技术栈。

2. 当前实现与成本来源 ​

当前锁定依赖解析为 Tauri 2.11.5、Tao 0.35.3 和项目补丁版 Wry 0.55.1。分离工具、画布窗口和弹幕覆盖层都通过 WebviewWindowBuilder 创建独立 WebView：

  • 通用分离窗口与工具窗口：window_manager.rs
  • 画布窗口：canvas_window.rs
  • 弹幕覆盖层：external_player.rs

Windows 上的 WebView2 使用 Chromium 多进程模型。同一个 user-data-dir 下的多个 WebView 会共享 browser、GPU、network 和 storage 等进程，但每个顶层 WebView 仍可能新增 renderer；进程是否复用还受到站点隔离、来源和运行时策略影响。

因此新增窗口的成本不只是一个 Win32 HWND，还包括：

  1. WebView2 controller 和可能新增的 renderer；
  2. 独立的 HTML、JavaScript、Vue 实例与状态；
  3. 页面资源加载、路由初始化和组件挂载；
  4. Canvas 动画、定时器和 IPC 监听产生的持续 CPU/GPU 消耗。

通用分离预览和画布窗口目前还会固定等待 150 ms 再显示。这段等待不属于 WebView2 初始化成本，但会直接叠加在用户感知延迟上。

3. Windows 本机实测 ​

测试对象为 480 x 360 的最小 Vue + Canvas 弹幕页面。使用 production frontend、debug-native Tauri 构建，在 WebView2 进程组已经预热的条件下运行两次。测试通过现有 Tauri IPC 创建窗口，统计 AIO Hub 对应 WebView2 user-data-dir 的进程组变化。

这些数字只代表当前 Windows 机器和当前构建，不能当作所有设备上的固定常数：

  • WebView2 进程组已经预热，冷启动通常还要支付 browser、GPU 和辅助进程的首次初始化成本；
  • debug-native 不是完整 release 构建，时间结果应视为项目内决策样本，而不是公开 benchmark；
  • Working Set 汇总可能重复计算进程间共享页，容量规划应优先参考 Private Bytes；
  • 进程组在采样期间会主动回收或提交内存，因此“新增 renderer 自身内存”可能高于“进程组净增量”。

尽管存在这些限制，两次结果都稳定新增一个 renderer，说明多个常驻 WebView 小部件会形成可观的线性增量，值得为展示型部件提供更轻的原生路径。

5. 与 Tauri 共存的关键边界 ​

Tauri 2 可以通过 WindowBuilder 创建不带 WebView 的原生窗口，Window 也实现了 raw-window-handle，可以把 HWND 或其他平台句柄交给 Direct2D、wgpu 等渲染器。这比另起一个隐藏 WebView 更符合当前目标。

但不能直接把 eframe、Iced 或 Slint 的默认运行器塞进 Tauri 主进程：它们通常需要拥有自己的 Winit 事件循环，而 Tauri 已经由 Tao 控制主线程事件循环。可行方式有三种：

  1. 让 Tauri 继续拥有窗口和事件循环，只集成 UI 框架的核心布局/渲染层；
  2. Windows 下通过原生窗口过程补齐命中测试、鼠标和键盘输入；
  3. 若需要完整跨平台交互，让一个独立 helper 进程承载所有原生小部件，并通过 IPC 与 Tauri 后台通信。

当前 Tauri 高层 WindowEvent 主要覆盖 resize、move、focus、close、DPI、主题和拖放，不提供完整的鼠标与键盘事件。因此“纯展示或点击穿透”部件适合先做进程内原生窗口；带复杂输入的小部件不应低估平台适配成本。

6. 跨平台调查结论 ​

原生小部件能够跨平台，但能统一的主要是上层状态、绘制场景和生命周期，不是所有窗口管理语义。透明合成、屏幕绝对坐标、强制置顶、跨工作区和全屏覆盖都受操作系统窗口模型约束。

因此，后续实现应将“一个跨平台实现”拆为三层：

  1. 跨平台核心层：类型化的小部件状态、主题 token、布局、绘制场景、时钟和脏区管理。
  2. 平台窗口层：分别处理 HWND、NSWindow/NSPanel、GTK/X11 与 Wayland surface 的窗口属性、输入和合成。
  3. 能力与降级层：运行时报告能力，不支持时退回普通原生窗口、主 WebView 内浮层或平台通知。

这个边界也意味着，第一阶段不应实现任意 JSON UI 描述或在 Rust 里重造 DOM。原生层应仅提供少量有明确语义的部件，例如 ProgressHud、StatusPill、TextOverlay 和 QuickActions。

8. 各平台推荐路径 ​

8.1. Windows ​

Windows 的能力最完整，也是当前最适合先验证的平台。Tauri Window 可以提供 HWND，在此基础上使用：

  • WS_EX_LAYERED 和 UpdateLayeredWindow 实现小尺寸、低频更新的逐像素透明窗口；
  • Direct2D/DirectWrite 处理矢量图形、字体回退和高 DPI 文字；
  • DirectComposition 或 wgpu 处理持续动画；
  • WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE 控制任务栏、激活与焦点；
  • 根据交互模式动态切换窗口命中测试或 WS_EX_TRANSPARENT。

不应让每个小窗口创建独立 GPU device。如果选用 GPU 路径，应共享 device、queue、字形图集和图标缓存，每个窗口只保留 surface 与场景状态。

8.2. macOS ​

Tauri Window 可获取 ns_window() 和 ns_view()。小部件可以在 Tauri 创建的 NSWindow 上配置窗口属性，再使用 CALayer、Core Graphics 或 CAMetalLayer 绘制。如果功能强依赖 NSPanel 语义，则需要由 macOS 平台后端在 Tauri 已有 NSApplication 事件循环中创建 NSPanel，普通 NSWindow 不能在创建后改变类型成为 NSPanel。

  • ignoresMouseEvents 用于点击穿透；
  • window level 用于浮动层级；
  • canJoinAllSpaces 和 fullScreenAuxiliary 用于工作区与全屏辅助行为；
  • 需要点击但不应像常规窗口那样抢占焦点时，使用 NSPanel 或明确的 key/main window 策略。

当前 Cargo.toml 没有启用 Tauri 的 macos-private-api feature，因此 WindowBuilder::transparent(true) 在 macOS 目标上不可直接使用。实施时需要明确选择：评估并启用该 feature，或通过 AppKit 层配置透明 content view，不能直接复制 Windows builder 代码。新的 AppKit 适配也应优先评估 objc2-app-kit 系列，不继续扩大已有 cocoa 依赖的使用面。

8.3. Linux/X11 ​

X11 可以通过 ARGB visual 与 compositor 实现透明，通过 EWMH 设置 utility/notification 窗口类型、above/sticky 状态，通过 XShape 或 input region 实现穿透。

但 GTK 的窗口移动 API 本质上是向窗口管理器发送请求，窗口管理器可忽略初始位置或重新放置。因此 X11 应标记为“尽力而为”，而不是与 Windows 完全等价。

8.4. Linux/Wayland ​

Wayland 是跨平台契约中最重要的限制项。标准 xdg_toplevel 不提供任意屏幕绝对坐标，顶层窗口的放置由 compositor 决定。xdg_positioner 只用于相对父 surface 的 popup，不是持久的全局悬浮窗替代品。

wlr-layer-shell 可以提供屏幕边缘锚定、background/bottom/top/overlay 层级、margin、exclusive zone 和键盘交互策略，但它不是 Wayland 核心协议，不能假设所有 compositor 均支持。实现时必须：

  1. 运行时检查 layer-shell global 是否存在；
  2. 存在时使用锚点和 margin 表达屏幕边缘 HUD，不转换为伪绝对坐标；
  3. 在 wl_surface 首次映射前设置 layer-shell role；surface 一旦获得 xdg_toplevel role 就不能原地改成 layer surface，因此需要确认 Tauri/GTK 创建时机，必要时由 Linux 后端单独创建窗口；
  4. 不存在时降级为普通顶层窗口、主窗口内浮层或平台通知；
  5. 不以强制 XWayland 作为默认解决方案。

项目当前 Flatpak 已开放 --socket=wayland、--socket=fallback-x11 和 --device=dri，基础图形权限足够支持原生 surface 实验。但 AppImage 打包流程会移除随包携带的 Wayland/EGL/GBM/DRM 库，如果引入 wgpu，必须在最低支持发行版、AppImage 和 Flatpak 中分别验证驱动加载与回退后端。

9. 绘制后端与 UI 框架选择 ​

9.1. 低频、小尺寸展示部件 ​

这类部件不需要为每个窗口建立持续 GPU 帧循环。可用 tiny-skia 生成 RGBA 图像，用 cosmic-text 或平台文字引擎处理中文字形、字体回退和 shaping，然后由平台后端提交到窗口。

softbuffer 虽然支持 Win32、AppKit、X11 和 Wayland，但其 u32 像素格式为 0x00RRGGBB，高 8 位未使用。它可用于不透明小窗口，不应作为透明悬浮层的统一呈现后端。

9.2. 动画、图表和高频更新 ​

wgpu 是目前最合理的统一 GPU 层，可在 Windows、macOS 和 Linux 上分别使用 D3D12、Metal、Vulkan/GL。Tauri Window 已实现 HasWindowHandle 和 HasDisplayHandle，可以创建 wgpu surface。

透明能力不能写死。每个 surface 需要查询 SurfaceCapabilities.alpha_modes，优先选择 premultiplied alpha；只有 Opaque 时进入明确的不透明降级，而 Inherit 需结合平台窗口与 compositor 做实际透明验证，不假设所有驱动都提供一致合成。

9.3. Slint、egui 与 Iced ​

  • Slint 允许自定义 Platform、手动驱动 timer/animation，并将输入事件分发给其窗口。技术上可以接入 Tauri，但仍然需要完成平台窗口、事件和呈现适配，不是零成本插件。
  • egui 可以只使用 core 和渲染层，但 eframe 默认拥有自己的 Winit 事件循环，不应直接与 Tauri/Tao 双重运行。
  • Iced 更偏向完整应用框架，为少量类型化小部件引入的生命周期和布局体系偏重。

建议第一阶段使用类型化场景与精简绘制器；只有当原生小部件增长到需要通用布局、焦点导航和可访问性时，再对 Slint 做独立 PoC 与许可证复核。

10. 能力驱动的窗口契约 ​

跨平台 API 不应只接受 x/y + alwaysOnTop。这会让 Wayland 后端从契约一开始就无法正确实现。建议用语义化配置表达意图：

rust
enum NativePlacement {
    OwnerRelative { owner: String, anchor: Anchor, offset: Offset },
    MonitorEdge { monitor: MonitorTarget, anchor: Anchor, margin: Insets },
    Absolute { x: i32, y: i32 },
}

enum NativeInteraction {
    PassThrough,
    NoActivate,
    Focusable,
}

enum NativeZLevel {
    Normal,
    Floating,
    Overlay,
}

平台后端同时报告可用能力：

rust
struct NativeSurfaceCapabilities {
    transparent: bool,
    absolute_position: bool,
    always_on_top: bool,
    click_through: bool,
    no_activate: bool,
    all_workspaces: bool,
    layer_shell: bool,
}

创建窗口时不应静默吞掉不支持的属性。管理器应返回“按请求实现”、“已降级”或“不支持”，并记录实际采用的 placement、z-level 和 alpha mode。

建议的默认降级规则：

  1. Wayland 没有 layer-shell 时，MonitorEdge 退回普通顶层窗口或主窗口内浮层；
  2. 不支持透明 alpha 时，使用紧凑的不透明样式；
  3. 不支持 NoActivate 时，纯展示部件降级为 PassThrough，交互部件降级为普通可聚焦窗口；
  4. 强依赖全屏覆盖的功能在能力不足时显式报告不支持，不伪装为已成功。

11. 移动端边界 ​

移动端不应并入桌面“全局悬浮窗”契约：

  • Android 跨应用浮窗需要 SYSTEM_ALERT_WINDOW 类特殊权限与用户单独授权，还涉及应用商店政策和安全风险；
  • iOS 不向普通应用开放任意系统级悬浮窗，只能使用 PiP、Live Activity 等有明确用途和限制的系统能力。

移动端可以复用部件状态、绘制场景和主题 token，但应将窗口呈现实现为应用内 overlay、平台 PiP 或系统通知，不与桌面端 NativeWidgetManager 共用相同能力承诺。

12. 推荐落点与验收指标 ​

第一阶段建议选择 Windows 已有的弹幕覆盖层，或实时字幕监控框做 PoC：

  1. 新增 Rust NativeWidgetManager，统一管理创建、更新、定位、显示和关闭，并对外报告能力与降级结果；
  2. 使用 Tauri 原生 WindowBuilder，Windows PoC 共享一套 Direct2D/DirectWrite/DirectComposition 设备与字体缓存，同时保持绘制场景不直接依赖 HWND；
  3. 静态部件只在状态变化时重绘，动画部件明确限制到 30 或 60 FPS，隐藏后停止绘制；
  4. 配置编辑继续留在 Vue 主窗口，原生窗口只负责最终展示和少量拖动、点击穿透；
  5. 保留 WebView fallback，在功能和兼容性验证完成前不直接替换现有实现。

Windows PoC 通过后，按 macOS、Linux/X11、Linux/Wayland 的顺序补齐后端。Wayland 阶段的目标不是达成与 Windows 一样的绝对定位，而是验证 layer-shell 能力探测、锚定定位与无协议时的降级路径。

PoC 建议至少验证以下指标：

  • 热创建到可见小于 100 ms；
  • 共享渲染设备后，单个小窗口 Private Bytes 增量小于 15 MiB；
  • 静态窗口空闲 CPU 接近 0；
  • 动画帧耗时满足目标帧率，窗口移动、DPI、透明合成和多显示器行为正确；
  • 点击穿透、置顶、目标窗口跟随和退出清理不弱于现有 WebView 版本；
  • macOS 在 Retina 缩放、Spaces 和原生全屏中的行为符合实际能力报告；
  • Linux 分别在 X11、支持 layer-shell 的 Wayland compositor 和不支持 layer-shell 的 Wayland compositor 上验证；
  • AppImage 与 Flatpak 均能正确加载图形后端，不因打包时移除底层图形库而启动失败。

以上为目标值，不是当前原生实现的实测结果，需要通过 PoC 验证。

三、综合建议 ​

两项调查可以归纳为一条清晰的窗口边界：

  1. 后台生命周期由 Rust 管理：优先零窗口运行，必要时使用不带 WebView 的隐藏原生窗口，不使用隐藏网页充当分发壳。
  2. 主工作台和复杂工具继续使用 WebView：Vue 仍是主要 UI 技术栈，主工作台是否销毁重建是独立的生命周期决策。
  3. 常驻展示型小部件逐步原生化：先从 Windows 透明、低交互部件开始，但从第一版就使用语义化 placement 和能力报告，不将 HWND 特性暴露给上层。
  4. 先收拢管理入口，再替换渲染实现：ensure_main_window() 和 NativeWidgetManager 分别管理工作台与小部件，托盘、单实例、Deep Link 和前端不再直接依赖具体窗口实现。
  5. 抽象先定边界，后端逐步落地：先定义最小的场景、placement、interaction、z-level 和 capabilities 契约，Windows 先实现并验证资源收益，再逐步实现 macOS、X11 和 Wayland 后端。
