## 1. 总体战略定位

本计划受 DeepSeek Harness（DSH）的微内核与插件化设计启发，旨在将 AIO Hub 打造为模块高内聚、依赖声明化、生命周期自闭环的下一代智能体应用宿主。

为彻底根除此前实验分支在重构中“概念膨胀、战线过长、强行改造旧模块导致进退两难”的教训，本总纲制定**物理隔离的两大独立战场**：

```text
┌─────────────────────────────────────────────────────────────┐
│                 战场一：插件系统 Cordis 化                  │
│       （基础设施层：负责 Scope 生命周期、可撤销副作用、能力 Seam）      │
└─────────────────────────────────────────────────────────────┘
                               ▲
                               │ 依赖提供与能力注入
                               │
┌─────────────────────────────────────────────────────────────┐
│               战场二：独立会话运行时（全新模块）               │
│ （应用领域层：纯净的事件驱动、DSH 工作台范式、与旧 llm-chat 零侵入） │
└─────────────────────────────────────────────────────────────┘
```

## 2. 战场一：插件系统 Cordis 化（基础底座）

### 2.1 核心职责与边界

该战场的唯一使命是建立健壮的**插件依赖管理与自动资源回收体系**。

- **管辖范围**：
  - 插件启用与禁用状态机；
  - 插件资源挂载归属于独立 `Scope`（Tauri 事件监听、定时器、后台任务、UI 贡献）；
  - 统一的 Native / Sidecar 进程生命周期与注销桥接；
  - 提供声明式能力 Seam（如统一的 OCR Provider、转写 Provider、模型调用能力 Seam）。
- **绝对不碰**：
  - 会话数据结构、分支算法、任何与对话相关的业务 UI。

### 2.2 核心设计规范

1. **Scope-Aware 资源托管**：
   插件作者在 `apply(ctx)` 中通过 Context 注册的任何资源，在插件禁用或卸载时，必须由框架按反序自动注销，杜绝手动 `deactivate()` 漏清资源的内存泄漏。
2. **渐进式能力 Seam 注册**：
   通过 `ctx.provide` / `ctx.inject` 表达服务依赖。例如 OCR 插件仅需挂载为一个 OCR Provider，由宿主统一消费。

## 3. 战场二：独立会话运行时（从零生长的新模块）

### 3.1 核心决策：与旧 `llm-chat` 彻底物理隔离

- **零侵入原则**：**严禁修改 `src/tools/llm-chat/` 内部现有的任何代码、树状结构、存储逻辑或 Store**。
- **全新模块命名与路径**：建议设立全新的领域模块 `src/tools/agent-workbench/`（或独立包），作为一个平行、独立的工具存在。
- **复用模式（Fork & Pure）**：
  新模块如需利用旧 Chat 的能力（例如流式 Markdown 渲染、代码高亮、基础卡片布局），**直接复制相关代码文件到新模块目录中，裁剪掉对旧 Chat 全局 Store 的依赖，将其纯函数化/纯组件化**。

### 3.2 借鉴 DSH 的核心架构范式

新会话运行时全面对齐 DSH 的四大基石：

#### (1) 仅追加的事件日志（Append-only Event Log）

会话底层不再设计沉重的复杂多叉树状态字典，而是采用事件驱动事实：

- 结构：以 Session 为单元，仅维护有序的 `SessionEvent`（包括用户输入、模型回复、`assistant/live-chunk`、工具调用、审批通过/拒绝、运行结果）。
- 优势：持久化简单、天然支持确定性历史回放、易于多窗口状态广播，彻底摆脱复杂的树节点增删改查算法。

#### (2) 目标中立的视图装配（Target-Neutral Assembler）

参考 DSH 的 `ui-conversation` 设计：

- 装配层（Assembler）只负责消费事件流，将事件折叠为带有上下文位置（Turn、Step）的逻辑单元。
- **投影分离**：
  - **Chat 投影**：将事件流投影为供用户阅读交互的连续消息流；
  - **Trajectory 投影**：将事件流投影为包含思考过程、工具调用细节、审批事件的运行轨迹流；
  - 两者共享底层事件事实，但拥有独立的渲染视图。

#### (3) 会话策略与 Preset 静态冻结

- Profile / Bundle / Preset 只作为会话创建时的启动配置（注入指定的模型、工具白名单、权限模式、工作区范围）。
- **一旦 Session 创建，策略当即冻结**。
- **不在主工作台首页设计庞杂的配置卡片与调参面板**。

#### (4) 极简高效的 Session 工作台体验

完全参考 DSH Web 视图布局：

- **顶部**：Session 基础信息、模式标签、快速切换；
- **中部**：主视图（Chat / Trajectory 选项卡切换）；
- **底部**：强大的轻量级 Composer（包含快捷命令、附件入口、权限模式切换与发送按钮）。

## 4. 实施阶段与演进路线

### 阶段 1：插件系统 Cordis 化收敛并入主线

1. 检视并提炼实验分支上已经跑通的 `src/services/runtime/` 及插件生命周期 Scope 管理。
2. 保持对当前已有插件（OCR、Sidecar 等）的干净桥接。
3. 补齐单元测试，确保插件启停时资源可逆卸载，先行作为底层基础设施 PR 合入 `dev`。

### 阶段 2：独立 Agent 会话运行时骨架搭建

1. 在全新目录 `src/tools/agent-workbench/` 中搭建独立入口与路由。
2. 建立极简的 `SessionEvent` 数据模型与存储适配器。
3. 复制并纯化旧 Chat 中成熟的展示组件（Markdown 渲染、输入框样式等），建立独立的 UI 视图。

### 阶段 3：接通 Agent 执行闭环与增量流

1. 接入模型调用端口，支持请求级 text delta 实时流（打字机效果）。
2. 接入命令执行与工具调用（Tool Calling），记录工具请求与结果事件。
3. 实现审批机制（Approval）并在 Trajectory 视图中完整呈现。

### 阶段 4：产品化打磨与长远演进

1. 完善会话导入/导出、工作区管理与快捷命令体系。
2. 当独立工作台成熟、体验全面超越旧体系后，再从容评估旧 `llm-chat` 的过渡策略，保持绝对的主动权。
