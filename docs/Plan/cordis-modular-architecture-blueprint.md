## 1. 总体战略定位与物理宿主决断

本方案受 DeepSeek Harness（DSH）的微内核与插件化设计启发，旨在将 AIO Hub 打造为模块高内聚、依赖声明化、生命周期自闭环的下一代智能体应用宿主。

结合项目确立的全面迁往 Electron 工程规划，彻底根除此前实验分支在 Tauri WebView 内部艰难维系常驻状态的物理局限。整个架构确立为**物理隔离的两大独立战场**，并在宿主层级上彻底分工：

## 2. 战场一：插件系统 Cordis 化（基础底座）

### 2.1 核心职责与边界

该战场的唯一使命是在 Node.js 主进程中建立健壮的**插件依赖管理与自动资源回收体系**。

- **管辖范围**：
  - 引入成熟标准 Cordis 核心（在 Node 环境下开箱即用，不再自研简陋的前端仿制 Context）；
  - 插件启用与禁用状态机；
  - 插件资源挂载归属于独立 `Scope`（IPC 监听器、定时器、后台任务、系统级进程）；
  - 统一的 Native (napi-rs) / Sidecar 进程生命周期与注销桥接；
  - 提供声明式能力 Seam（如统一的 OCR Provider、转写 Provider、模型调用能力 Seam）。
- **绝对不碰**：
  - 会话数据结构、分支算法、任何与对话相关的业务 UI。

### 2.2 核心设计规范

1. **Scope-Aware 资源托管**：
   插件作者在 `apply(ctx)` 中通过 Context 注册的任何资源，在插件禁用或卸载时，必须由框架按反序自动注销，杜绝手动 `deactivate()` 漏清资源的内存泄漏。
2. **渐进式能力 Seam 注册**：
   通过 `ctx.provide` / `ctx.inject` 表达服务依赖。例如 OCR 插件仅需挂载为一个 OCR Provider，由宿主统一消费。

## 3. 战场二：独立会话运行时（从零生长的新模块）

### 3.1 核心决策：与旧 `llm-chat` 彻底物理隔离

- **零侵入原则**：**严禁修改 `src/tools/llm-chat/` 内部现有的任何代码、树状结构、存储逻辑或 Store**。
- **全新模块命名与路径**：设立全新的领域模块 `src/tools/agent-workbench/`（或独立包），作为一个平行、独立的工具存在。
- **严禁命名污染（防抄袭红线）**：
  - **严禁**在任何代码、路径、变量、类型或组件中使用外部参照物的专有代号（如 `dsh`、`dsh-*` 等）；
  - 外部设计仅供领会其架构范式，所有代码必须以 AIO Hub 自身的领域模型（如 `agent-workbench`、`session-event`、`conversation-assembler` 等）原生书写并符合仓库代码规范。
- **复用模式（Fork & Pure）**：
  新模块如需利用旧 Chat 的能力（例如流式 Markdown 渲染、代码高亮、基础卡片布局），**直接复制相关代码文件到新模块目录中，裁剪掉对旧 Chat 全局 Store 的依赖，将其纯函数化/纯组件化**。

### 3.2 吸收核心架构范式（仅取其神，严禁形代）

新会话运行时全面对齐 DSH 的四大基石：

#### (1) 仅追加的事件日志（Append-only Event Log）

会话底层不再设计沉重的复杂多叉树状态字典，而是采用事件驱动事实：

- 结构：以 Session 为单元，仅维护有序的 `SessionEvent`（包括用户输入、模型回复、`assistant/live-chunk`、工具调用、审批通过/拒绝、运行结果）。
- 优势：持久化简单、天然支持确定性历史回放、易于多窗口状态广播，彻底摆脱复杂的树节点增删改查算法。

#### (2) 目标中立的视图装配（Target-Neutral Assembler）

参考 DSH 的 `ui-conversation` 设计：

- 装配层（Assembler）只负责消费事件流，将事件折叠为带有上下文位置（Turn、Step）的逻辑单元。
- **投影分离**：
  - **Chat 投影**：将事件流投影为供用户阅读交互的连续消息流；
  - **Trajectory 投影**：将事件流投影为包含思考过程、工具调用细节、审批事件的运行轨迹流；
  - 两者共享底层事件事实，但拥有独立的渲染视图。

#### (3) 会话策略与 Preset 静态冻结

- Profile / Bundle / Preset 只作为会话创建时的启动配置（注入指定的模型、工具白名单、权限模式、工作区范围）。
- **一旦 Session 创建，策略当即冻结**。
- **不在主工作台首页设计庞杂的配置卡片与调参面板**。

#### (4) 极简高效的 Session 工作台体验

完全参考 DSH Web 视图布局：

- **顶部**：Session 基础信息、模式标签、快速切换；
- **中部**：主视图（Chat / Trajectory 选项卡切换）；
- **底部**：强大的轻量级 Composer（包含快捷命令、附件入口、权限模式切换与发送按钮）。

## 4. 实施阶段与工程总纲挂钩

本架构总纲的落地节奏，全面对齐 [`electron-migration-master-plan.md`](./electron-migration-master-plan.md) 中的实施路线图，杜绝在过渡态 Tauri 环境中重复制造临时脚手架：

### 阶段 1：前端解耦与平台门面就位（挂钩 Electron 阶段零）

- 前端通过 `@/platform/bridge` 彻底解开与底层框架的直接捆绑。
- 新建 `src/tools/agent-workbench/` 独立目录，搭好纯前端组件架子（视图装配器 + Composer 骨架）。

### 阶段 2：Node 主进程 Cordis 微内核入驻（挂钩 Electron 阶段四）

- 在 Electron 主进程引入成熟 `cordis` 依赖包，配置 Root Context；
- 将插件的生命周期管理（启用、禁用、Scope 资源回收）直接交由 Node 宿主托管；
- 原生支持定时器与后台任务，实现无需打开窗口的后台守护能力。

### 阶段 3：后台常驻 Agent 调度引擎闭环（挂钩 Electron 阶段四）

- 在 Node 进程落地仅追加事件日志（`SessionEvent`），天然实现文件持久化与断线无缝重放；
- 接入模型调用与工具调用闭环（Tool Calling）；
- 前端 `agent-workbench` 仅通过 IPC 订阅事件增量，实现毫秒级打字机流式渲染与轨迹追踪。

### 阶段 4：产品化打磨与生态延展

- 完善会话导入/导出、工作区管理与快捷命令体系；
- 当独立 Agent 工作台成熟、体验全面超越旧体系后，再从容评估旧 `llm-chat` 的过渡或退休策略，保持绝对的主动权。
