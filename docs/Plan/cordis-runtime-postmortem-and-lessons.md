# Cordis 运行时重构经验复盘与范式校正

> 状态：总结归档  
> 日期：2026-10-02  
> 参考基准：`E:\git\deepseek-harness`（DSH）与 `feature/cordis-runtime` 实验分支施工全过程

---

## 1. 背景与实验分支背景

在 `feature/cordis-runtime` 实验分支中，AI团队尝试将 AIO Hub 朝着以 Cordis 为微内核、受 DeepSeek Harness（DSH）启发的模块化与插件化架构演进。然而，在经历了 140 多个提交的推进后，计划数次推倒重写、出现严重变形。

本文件旨在**彻底复盘实验分支的跑偏轨迹与认知偏差，解构 DSH 的真实系统范式，确立下一阶段重构的根本铁律**。

---

## 2. 实验分支跑偏的核心病灶剖析

### 2.1 病灶一：在高速公路上给旧卡车换发动机（对 `llm-chat` 的过度侵入）

- **错误路径**：
  DSH 具备会话分支与重试概念，而 AIO Hub 的既有工具 `llm-chat` 恰好维护着一棵复杂的 `ChatMessageNode` 多叉树。施工过程中，AI 误将“会话运行时 Cordis 化”等同于“将 `llm-chat` 的多叉树抽成全局通用树内核”，创造了 `conversation-core`。
- **恶果**：
  整整两周的算力与十数个提交被消耗在：_让子树删除经过 Core_、_让单点移动经过 Core_、_让分支嫁接经过 Core_、_维护反向快照转换器_、_处理存量 Undo/Redo 与跨窗口同步冲突_。重构被旧代码的历史包袱死死拖垮，本末倒置。

### 2.2 病灶二：把内部运行装配误作为用户产品交互（调参台泛滥）

- **错误路径**：
  在接触到 DSH 的 Profile、Bundle、Patch 机制后，AI 未能理解其“启动/会话时静态声明与按需冻结”的设计，自作主张在工作台首页设计了大量的配置卡片、Bundle 组合勾选区、以及脱离真实场景的 Coding 探针与 Workflow 测试台。
- **恶果**：
  违背了对话产品“以会话与 Composer 为核心”的直觉，打乱了交互主线，最终不得不通过紧急修订计划强行清理这批探针页面。

### 2.3 病灶三：数据模型异化（强类型多叉树 vs 仅追加事件日志）

- **DSH 的真实现状**：
  底座是极简平铺的 **仅追加事件日志（Append-only `SessionEvent` Log）**。模型回复、打字增量（`live-chunk`）、工具请求、审批、取消等均是事件事实。前端依靠目标中立的装配器（`ui-conversation`）折叠出状态并投影给不同视图（Chat / Trajectory）。
- **实验分支的异化**：
  直接在树节点（`ConversationNode`）上硬塞运行状态，导致结构极其沉重，为了兼容 Chat 的既有字典结构写了极其臃肿的 `chatSessionToConversation` ↔ `conversationToChatSession` 映射层，在内存中不断折腾。

---

### 3. DeepSeek Harness (DSH) 的真实设计精髓

比对 `E:\git\deepseek-harness` 源码与子系统规范，其架构高度精炼：

1. **Cordis 是插件依赖与生命周期容器**：
   产品所有能力（LLM、Tools、Session、沙箱、审批）皆为插件，副作用（事件监听、注册、定时器）归属于 Scope，卸载时自动撤销。
2. **Profile / Bundle 是静态装配方案**：
   Bundle 是 Cordis 配置片断的分发单元；Profile 是具名组合。它们在会话/进程启动时冻结，**不在首页堆砌调参表单**。
3. **Session 即事件序列**：
   会话持久化的是有序事件流（Turn、Step、Event），而非在前端维持一个无所不包的重型树状态。
4. **Target-Neutral 投影架构**：
   `ui-conversation` 只提供事件窗口到节点上下文的装配管线，`ui-chat`（对话呈现）与 `ui-trajectory`（执行轨迹呈现）是两个平行的消费视图，互不侵入。
5. **极简的工作台体验**：
   用户始终面对清晰的 Session 头部、对话/轨迹主区域，以及功能完备的 Composer（输入、命令、附件、权限模式），内部插件组合沉淀于底层。

## 4. 下一阶段重构的四大红线

为了彻底终结计划反复修改、代码走样的循环，后续所有施工必须严格遵守以下原则：

### 红线 1：双轨独立解耦（插件系统 vs 会话运行时）

- **插件系统 Cordis 化**是纯粹的基础设施工作：只解决 Scope 生命周期、Tauri 资源回收、依赖声明与能力 seam。它不包含任何会话业务。
- **会话运行时**是上层领域应用：消费底层 Cordis 能力，二者不得混合推进。

### 红线 2：新会话运行时从零独立生长，零侵入旧 `llm-chat`

- 严禁任何试图在 `src/tools/llm-chat/` 内部边用边改、引入 Cordis 或替换树算法的行为。
- 探索型会话运行时（如独立的 `agent-workbench`）必须作为全新独立模块创建，保持物理隔离。

### 红线 3：旧逻辑复用一律采用“复制代码并裁剪（Fork & Pure）”

- 当新模块需要旧 Chat 中的某些良好能力时（如流式解析、Markdown 渲染、卡片视觉、特定 Prompt 构造）：
  **直接复制相应代码片段到新模块内，剔除对旧 Store、全局状态和旧存储的依赖，改写为纯函数或纯 Props/Emits 组件**。
- 绝不通过 import 旧模块的全局单例或 Pinia Store 来进行耦合调用。

### 红线 4：严禁在未落地端到端会话前引入过度抽象

- 杜绝脱离实际运行流的抽象层（如通用的万能 Recipe 编排器、多重双向适配器、未被使用的拓扑排序器）。
- 每一个能力落地必须直接服务于：**用户在 Composer 发送 -> Agent 运行时执行 -> 事件落盘与增量渲染 -> 得到明确结果**。
