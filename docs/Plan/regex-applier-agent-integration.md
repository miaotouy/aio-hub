# Regex Applier Agent 接口设计与受控执行方案

> 状态：Proposal（已根据当前工具调用机制修订）
>
> 针对问题：[AIO-I-005](../../docs/Plan/aio-investigation-issue-register.md#aio-i-005regex-applier-的-agent-接口尚未完成场景定义)
>
> 编写人：咕咕 (Gugu)

## 1. 核心定位：为什么要把正则工具暴露给 Agent？

如果仅仅是为了“帮用户写正则表达式”，在 `regex-applier` 模块内部提供一个“AI 辅助生成”按钮，直接把模型生成的规则填入规则编辑器，交互路径会比在 Chat 中来回对话更短，也更容易预览和修改。

因此，把 `regex-applier` 暴露给 Chat Agent 的主要价值不是生成正则，而是提供一个**能力范围受限、行为可预测的声明式文本/文件处理工具**：Agent 只能提交预先定义的正则规则和处理参数，不需要编写或执行 Python、Node.js 等任意脚本。

### 1.1. 权限前提与安全边界

本工具不会默认向 Agent 开放。只有用户在具体 Agent 的工具设置中主动启用 `regex-applier` 以及对应方法后，Agent 才能发现和调用这些能力。文件处理等方法是否可用，由用户的工具权限配置决定。

本文中的“受控”主要指：

- Agent 调用的是固定的文本/文件正则处理接口，而不是任意脚本执行接口；
- 处理规则、输入参数和执行结果都可以在工具调用记录中明确展示；
- Agent 无法通过该工具执行任意系统命令或加载任意代码。

这不是操作系统级的文件访问沙箱，也不承诺绝对安全隔离。当前版本继续沿用 `regex-applier` 已有的本地文件读写能力，路径权限和文件访问范围由用户主动启用工具时的运行环境决定。本计划不额外引入复杂的路径 allowlist、dry-run 或审批策略。

### 1.2. 传统脚本执行 vs 声明式正则接口

当 Chat 中的 Agent 面对“清洗日志”或“批量替换代码目录中的字符”这类任务时，可以比较两种实现路径：

| 维度             | 路径 A：Agent 自行编写并执行脚本 (Python/Node.js) | 路径 B：Agent 调用 `regex-applier` 声明式接口                             |
| :--------------- | :------------------------------------------------ | :------------------------------------------------------------------------ |
| **能力范围**     | 可以执行任意逻辑，能力强但行为难以预判。          | 只能提交预定义的正则处理参数，不提供任意脚本执行能力。                    |
| **环境依赖**     | 依赖本地脚本运行环境和相关包。                    | 使用 AIO Hub 已有的前端/Rust 处理引擎。                                   |
| **用户理解成本** | 用户需要理解或审批一段完整脚本。                  | 用户可以直接查看规则、路径和输出参数。                                    |
| **大文件能力**   | 取决于脚本实现和本地环境。                        | 不需要将完整文件内容放入 Agent 上下文，具体内存和文件大小取决于后端实现。 |

> 当前 Rust 文件处理实现使用整文件读取，不是严格意义上的流式处理。因此本方案不承诺“流式读写”或固定的 `>100MB` 文件能力。

## 2. 典型应用场景设计

### 场景 A：文本清洗与脱敏

- **用户输入**：“帮我把这段日志里的手机号和邮箱脱敏。”
- **Agent 行为**：
  1. 调用 `validateRegex` 检查规则是否兼容当前处理引擎；
  2. 调用 `applyRegexToText` 处理用户提供的文本；
  3. 将返回的处理结果交给用户确认。

第一期不新增剪贴板读写 Agent 接口。现有 `oneClickProcess` 仍然作为 UI 内部的一键处理能力；如果后续需要让 Agent 直接读写剪贴板，应单独设计 `applyRegexToClipboard`，并明确其权限和交互语义。

### 场景 B：批量文件处理

- **用户输入**：“帮我把这些 Vue 文件里的 `v-sub` 替换成 `v-subscription`。”
- **Agent 行为**：
  1. 调用 `validateRegex` 检查规则是否兼容 Rust 后端；
  2. 调用 `applyRegexToFiles`，传入文件路径或目录、输出目录和规则；
  3. 根据处理摘要向用户报告成功、失败和匹配数量。

第一期的 `filePaths` 表示用户明确传入的文件或目录列表。目录递归处理和文件过滤沿用当前后端能力；include/exclude glob 等更细粒度过滤能力不纳入本次接口接入范围。

### 场景 C：规则库预设的测试

- **用户输入**：“我想写一个清洗 Apache 日志的预设，你帮我先用这段日志测试一下。”
- **Agent 行为**：
  1. 调用 `getPresets` 了解当前已有预设；
  2. 调用 `validateRegex` 验证新规则的 Rust 兼容性；
  3. 调用 `applyRegexToText` 传入测试文本和临时规则；
  4. 根据结果引导用户在 UI 中保存或调整预设。

本计划不允许 Agent 直接创建、修改或删除预设，只提供预设查询和规则测试能力。

### 2.1. UI 优先与 Agent 适用边界

`regex-applier` 已经提供了较完整的可视化工作流。不是所有已有功能都值得再包装成 Agent 方法；如果用户已经在工具面板中，直接操作 UI 通常比让 Agent 代替用户点击更快、更直观，也更容易观察中间结果。

| 使用场景                                                              | 更适合的入口 | 原因                                                                                                                            |
| :-------------------------------------------------------------------- | :----------- | :------------------------------------------------------------------------------------------------------------------------------ |
| 粘贴文本、实时查看替换结果、复制结果或发送到聊天                      | 工具面板     | 面板已经提供输入/输出双栏、实时预览、粘贴、复制和“发送到聊天”按钮。让 Agent 代为读写剪贴板或转发文本只是绕路。                  |
| “一键处理剪贴板”                                                      | 工具面板     | 这是典型的 UI 优先场景：用户已经有明确的粘贴→处理→复制动作，Agent 参与不会增加理解或编排价值。剪贴板读写不纳入本次 Agent 接口。 |
| 新建、复制、重命名、删除预设                                          | 工具面板     | 这些操作有明确的表单、确认框和持久化语义，不需要通过自然语言间接完成。                                                          |
| 添加、编辑、启用/禁用、排序、删除规则                                 | 工具面板     | 规则编辑器提供规则列表、拖拽排序、快捷规则和 Rust 兼容性提示，直接操作更适合反复试错。                                          |
| 导入/导出预设、从文件或剪贴板导入 JSON                                | 工具面板     | 这是文件和配置管理流程，面板已有专门入口；Agent 不应为了模拟 UI 操作而暴露对应的写入接口。                                      |
| 手动选择文件/目录、选择输出目录、设置后缀和 `.txt` 输出、查看处理日志 | 工具面板     | 当前面板已经提供文件选择、拖拽、输出设置、逐文件状态和日志摘要。单纯把这些控件搬到 Agent 参数中，不能形成额外价值。             |

Agent 更适合以下情况：

- 用户在聊天中已经提供了一段文本，希望直接得到处理后的结果，而不想切换到工具面板；
- Agent 正在完成一个更大的任务，需要先通过其他工具定位文件，再把确定的路径交给正则处理；
- Agent 根据自然语言理解选择已有预设、组合预设和临时规则，并在处理后向用户解释结果；
- 用户希望在对话中完成“生成规则→验证兼容性→测试文本/处理文件”的连续流程。

因此，本计划中的 Agent 方法应被视为**聊天场景的编排能力**，而不是 `regex-applier` UI 的远程遥控器。判断标准是：

1. 如果用户已经在工具面板中，且任务主要是编辑、预览、选择和确认，优先使用 UI；
2. 如果任务起点在聊天中，或需要和搜索、文件分析、代码理解等其他 Agent 工具串联，才考虑调用 Agent 接口；
3. 如果唯一收益只是“替用户点击已有按钮”，则不新增 Agent 方法。

## 3. Agent 接口契约设计 (API Specification)

Agent 方法必须遵循当前 Tool Calling 的实际调用约定：

```ts
(args: Record<string, unknown>, context?: ToolContext) =>
  Promise<unknown> | unknown;
```

也就是说，Agent 方法的第一个参数是参数对象，而不是多个位置参数。由于当前 VCP 参数以字符串形式传递，数组和规则列表使用 JSON 字符串表示；方法内部负责解析和校验。

本次计划暴露以下 4 个方法：

### 3.1. `applyRegexToText`（文本正则替换）

用于对传入的纯文本按顺序应用临时规则和预设规则。

- **方法名**：`applyRegexToText`
- **Agent 参数**：
  - `text`（string，必填）：源文本；
  - `rulesJson`（string，可选）：JSON 规则数组。每条规则至少包含 `regex` 和 `replacement`，可选包含 `name`、`enabled`；
  - `presetIdsJson`（string，可选）：JSON 字符串数组，按数组顺序应用预设。
- **执行顺序**：先按 `presetIdsJson` 顺序展开并应用预设规则，再按 `rulesJson` 顺序应用临时规则。
- **约束**：`rulesJson` 和 `presetIdsJson` 至少提供一个；未知预设 ID、无效 JSON 或没有可执行规则时返回明确错误。
- **返回值**：处理后的文本字符串。处理失败时返回工具错误，不返回未经处理的原文。

临时规则不写入本地预设库，避免 Agent 调用测试接口时产生持久化副作用。

### 3.2. `applyRegexToFiles`（文件批量正则替换）

用于复用现有 Rust 后端，对文件或目录执行批量正则替换。

- **方法名**：`applyRegexToFiles`
- **Agent 参数**：
  - `filePathsJson`（string，必填）：JSON 字符串数组，元素为文件或目录路径；
  - `outputDir`（string，必填）：输出目录；
  - `rulesJson`（string，可选）：JSON 规则数组；
  - `presetIdsJson`（string，可选）：JSON 字符串数组；
  - `filenameSuffix`（string，可选）：文件名后缀，例如 `_processed`；
  - `forceTxt`（boolean，可选）：是否强制使用 `.txt` 扩展名，默认 `false`。
- **执行顺序**：预设规则按 `presetIdsJson` 顺序展开，临时规则追加到预设规则之后。
- **约束**：`rulesJson` 和 `presetIdsJson` 至少提供一个；路径、JSON 和规则参数必须在前端包装层完成基本校验。
- **返回值**：格式化处理摘要，至少包含成功文件数、失败文件数和总匹配数。详细后端日志继续保留在工具执行结果中。

该方法复用现有 `process_files_with_regex` 命令，不在本轮重新设计 Rust 文件处理模型。

### 3.3. `getPresets`（获取可用预设）

让 Agent 了解当前有哪些可用预设，以便推荐已有规则。

- **方法名**：`getPresets`
- **参数**：无；
- **返回值**：预设摘要数组，每项包含：
  - `id`；
  - `name`；
  - `description`；
  - 启用规则数量 `ruleCount`。

当前注册器已经实现了 `getPresets()`，本次主要补充 Agent 元数据并确认其与 Agent 参数对象调用方式兼容。

### 3.4. `validateRegex`（验证 Rust 正则兼容性）

用于验证规则是否能够被文件处理使用的 Rust 正则引擎编译。

- **方法名**：`validateRegex`
- **参数**：
  - `pattern`（string，必填）：正则表达式模式，可使用工具已支持的 `/pattern/flags` 格式；
- **返回值**：结构化验证结果，字段与已有 Rust 命令保持一致：
  - `isValid`；
  - `errorMessage`；
  - `parsedPattern`；
  - `parsedFlags`；
  - `warning`。

Agent 版本的 `validateRegex` 不直接复用当前 JavaScript `engine.validateRegex` 的位置参数实现，以避免 JavaScript 和 Rust 正则引擎之间出现兼容性误判。

## 4. 实施计划 (Implementation Plan)

### 4.1. Agent 接口实现

1. 在 [`src/tools/regex-applier/regex-applier.registry.ts`](../../src/tools/regex-applier/regex-applier.registry.ts) 中增加 Agent 参数对象适配方法。
2. 扩展文本和文件处理的规则输入，使其可以同时接受：
   - 已保存预设规则；
   - 不持久化的临时规则。
3. 在 `getMetadata()` 中声明 4 个方法，并为每个方法设置：
   - `agentCallable: true`；
   - 完整的参数描述；
   - 正确的返回类型；
   - 必要的调用示例。
4. 将 Agent 版本的 `validateRegex` 接到已有 `validate_regex_pattern` Tauri command，返回 Rust 兼容性结果。
5. 对输入 JSON、未知预设、空规则和无效规则返回明确错误。

### 4.2. 文档与状态同步

1. 更新 [`src/tools/regex-applier/ARCHITECTURE.md`](../../src/tools/regex-applier/ARCHITECTURE.md)，加入：
   - Agent 接入方式；
   - 权限前提；
   - 四个 Agent 方法的用途；
   - 临时规则不持久化的约定；
   - 当前文件处理能力和非流式读取限制。
2. `AIO-I-005` 当前已经是“已确认，待实施”，实施完成后根据实际完成范围更新为：
   - 仅完成接口：`已实现，待补充`；
   - 接口和相关验证均完成：`已关闭`。
3. 修正 issue register 中指向本计划的文档链接。

### 4.3. 验证

至少运行：

```bash
bun run check:frontend
bun run build:vite
```

并增加与本次改动相关的测试，覆盖：

- Agent 方法元数据发现；
- 参数对象调用；
- `rulesJson` 和 `presetIdsJson` 解析；
- 预设与临时规则的应用顺序；
- 无效 JSON、未知预设和无效规则；
- Rust 正则兼容性验证结果映射。

如果本次同时修改 Rust 后端，再补充：

```bash
bun run check:backend:compile
bun run test:backend
```

## 5. 本次范围与后续事项

### 本次范围

- 暴露 4 个面向聊天编排的 Agent 方法，而不是复制整个工具面板；
- 完成参数对象适配和元数据声明；
- 支持临时规则与已有预设组合处理；
- 提供 Rust 正则兼容性验证；
- 不新增 Agent 剪贴板读写接口；
- 不修改现有文件处理命令的路径权限、覆盖策略和读取模型。

### 后续事项

以下事项不作为本次接口接入的阻塞条件，但后续可以独立评估：

- Agent 剪贴板处理接口（当前视为 UI 优先反例，除非后续出现明确的跨工具编排需求）；
- include/exclude glob 文件过滤；
- dry-run 或变更预览；
- 文件覆盖和同名冲突策略；
- 更严格的路径授权范围；
- 大文件流式处理或资源上限。
