# v0.7.0-alpha.1 发布收口与体验优化记录

> 状态：主体功能基本完成；当前重点转为新功能 UI 打磨、升级说明的信息架构与交互设计，以及发布前联合验收
>
> 记录日期：2026-07-27
>
> 目标版本：桌面端 `0.7.0-alpha.1`；涉及插件随兼容主应用同步发布
>
> 文档定位：跨模块发布收口记录，不是面向用户的最终版本说明，也不替代各模块的专项测试与迁移门禁

## 1. 当前结论

自 `v0.6.6-r.1` 以来的主体功能和架构改动已基本落地。现阶段不再把 Sidecar Plugin API v3 视为“尚未打通”的功能：开发模式中，主应用已经可以成功调用 API v3 插件，并实际使用新的分批处理优化特性。

当前发布前最明显的工作不再是继续扩张功能范围，而是：

1. 系统打磨大部分新功能的 UI、交互细节和跨模块一致性；
2. 重新设计大版本升级说明的内容层级与呈现方式；
3. 将主应用与依赖 API v3 的新版插件作为一个兼容发布组合进行最终验收和同步发布；
4. 保留现有数据迁移、真实运行态和发布候选包门禁，不因为开发态功能已打通而省略最终检查。

除上述收口项外，其余主体工作可按“基本完成、等待发布前复核”处理，避免在 Alpha 1 发布前继续无边界增加需求。

## 2. Sidecar Plugin API v3 状态修正

### 2.1 已确认状态

- API v3 的宿主调用链已经在开发模式中成功运行；
- 新版插件已经实际进入新的分批处理路径，而不是回退到旧 API v2 调用；
- 分批优化是本次主应用与插件组合发布的一部分；
- 主应用与对应新版插件计划同步发布，避免先发布任一侧造成能力缺失或兼容误判；
- 主程序继续保留既有 API v2 插件加载能力，但依赖 API v3 新能力的插件必须按声明的主程序兼容范围发布。

### 2.2 发布前仍需确认

开发态成功调用证明主链路已经打通，但不自动替代以下发布验收：

- 发布候选主应用实际加载发布候选插件，而不是开发目录或陈旧二进制；
- manifest 当前平台键指向最终随包分发的稳定产物；
- 分批任务的进度、局部结果、取消、失败终态和完成终态表现正确；
- 插件进程重启后首次调用正常，旧进程迟到事件不会污染新作业；
- 主应用和插件版本、最低宿主版本及 API version 声明一致；
- 同步发布时准备清晰的兼容提示，避免用户只更新一侧后误以为功能损坏。

因此，Sidecar API v3 当前应描述为：**开发态主链路与分批优化已验证成功，等待主应用和插件发布候选组合的最终联合验收与同步发布。**

## 3. 新功能 UI 打磨

### 3.1 当前判断

本周期新增和重构的功能量很大，业务能力已先于视觉与交互细节完成。大部分新功能 UI 仍需要一次面向实际使用流程的集中打磨，不能仅以“页面可打开、操作可完成”作为发布体验验收。

重点范围包括但不限于：

- Recall 配置、检索管线、诊断和迁移入口；
- Knowledge 工作区、资料摄取、授权、检索与研究任务；
- Agent 中 Recall / Knowledge 的配置与能力说明；
- Guided Flow、版本说明和知识库迁移步骤；
- 移动端资产管理、聊天附件、预览和状态反馈；
- Smart OCR 与 Sidecar API v3 分批作业的进度、取消和结果呈现。

### 3.2 打磨原则

UI 收口应优先检查完整任务流，而不是逐页做孤立美化：

1. **层级清楚**：默认界面只展示完成当前任务所需的信息，高级诊断和实现细节按需展开；
2. **术语一致**：Recall、Knowledge、资料库、思绪、检索预设等概念在不同入口使用同一套命名；
3. **状态可理解**：准备中、执行中、部分成功、等待重建、失败、可重试和已完成需要有可区分的反馈；
4. **危险操作明确**：迁移、清理、重建、覆盖和不可逆转换必须说明对象、影响与恢复路径；
5. **错误可行动**：错误信息应告诉用户下一步能做什么，不直接暴露无解释的内部协议或堆栈；
6. **桌面与移动端各自成立**：不为了视觉统一照搬布局，应遵循各端已有组件和交互边界；
7. **控制本轮范围**：优先处理高频主路径、阻断理解的问题和明显不一致，不在发布前顺带重做整个设计系统。

### 3.3 建议验收方法

- 按“首次进入—完成主要任务—失败恢复—再次进入”走查每个新模块；
- 使用真实或接近真实的数据量检查空状态、长列表、长标题、长错误和窄窗口；
- 对跨模块流程做连续走查，例如从 Agent 授权进入 Knowledge 检索，或从升级说明进入旧数据迁移；
- 每个模块保留少量发布前截图或录屏，集中评审信息层级、文案和状态反馈；
- UI 调整后继续执行前端类型检查和对应 Vite 构建；涉及 Tauri IPC、插件、文件或迁移的界面必须在真实运行态复核。

## 4. 升级说明需要重新设计

### 4.1 现有问题

`0.7.0-alpha.1` 的改动跨越 Recall / Knowledge 重构、数据迁移、移动端资产与聊天存储、会话可靠性、插件 API、工具优化和升级基础设施。单篇线性说明很难同时满足“快速知道有什么变化”和“理解迁移及兼容细节”两个目标。

当前已有的 AI 草拟引导文案只能作为占位内容，存在以下不足：

- 概括范围偏窄，没有覆盖本次实际主要变更；
- 容易堆叠抽象描述，缺少对用户影响、使用场景和注意事项的准确解释；
- 所有信息处于同一层级，重点功能、内部重构和风险提示相互争夺注意力；
- 引导步骤、版本说明和必须确认的迁移事项混在一起时，流程会显得冗长；
- 文案语气和信息密度尚未达到正式发布质量。

在信息架构和交互形式确定前，不应只是继续扩写现有文案。

### 4.2 必须支持的两层内容

最终方案至少要区分：

#### 摘要层

面向希望快速了解版本的用户，回答：

- 这次升级最重要的变化是什么；
- 哪些变化会直接影响现有使用方式；
- 是否有数据迁移、插件同步更新或其他需要立即处理的事项；
- 用户现在可以选择继续了解、开始处理事项，还是稍后再看。

摘要应短、可扫描，以用户收益和影响为主，不罗列提交记录或内部模块名。

#### 详情层

面向希望完整了解版本的用户，按主题提供：

- 功能变化及典型使用场景；
- 与旧版本的差异；
- 数据迁移、兼容边界与恢复说明；
- 重要修复和稳定性改进；
- 开发者或高级用户关心的协议变化；
- 必要时链接到更完整的模块文档或迁移报告。

详情不应强迫所有用户在启动时逐段阅读。

### 4.3 待设计的交互问题

下列问题目前保持开放，不在本记录中提前冻结方案：

1. 摘要与详情是在同一流程内展开、独立页面展示，还是采用“升级中心 + 详情页”的组合；
2. 首次升级自动出现时展示到什么深度，关于页手动回看时是否提供更完整目录；
3. 版本说明与必须确认的数据迁移应如何分离，同时又保持清晰的上下文关系；
4. 大量主题使用卡片、目录、折叠章节还是独立详情页更合适；
5. 跨多个版本升级时，摘要应按最终用户影响合并，还是按版本逐项回放；
6. 主应用与插件同步发布的兼容提示应出现在摘要、迁移事项还是独立状态检查中；
7. 如何保存“已读摘要”“已处理事项”和“稍后查看详情”等不同状态，避免把阅读行为等同于迁移完成。

### 4.4 内容生产原则

- 先由实际代码、迁移边界和发布验证结果建立事实清单，再写用户文案；
- 摘要、详情、迁移确认和故障恢复文案分别编写，不从一篇长文机械截断；
- 每条重点说明采用“变化—用户影响—需要操作”结构；
- 对内部重构，只在它带来可感知能力、兼容变化或可靠性收益时进入摘要；
- 避免空泛的“全面升级”“焕新体验”“更智能”等宣传式表达；
- AI 可以辅助整理初稿，但正式内容需要人工复核事实、优先级、语气和信息密度；
- 在交互方案定稿前，现有 `v0.7.0-alpha.1` release note 继续视为占位资源，不视为发布文案完成。

## 5. 发布组合与收口顺序

建议按以下顺序推进：

1. 冻结 `0.7.0-alpha.1` 的功能范围，整理主应用和插件的兼容版本矩阵；
2. 完成高频主路径的 UI 走查和第一轮集中打磨；
3. 设计并评审升级说明的摘要/详情信息架构和交互原型；
4. 基于确认后的结构重写正式版本说明与迁移提示；
5. 构建主应用与新版插件发布候选组合，完成 API v3 分批作业联合验收；
6. 完成已有数据迁移、真实 Tauri 和安装包 smoke 门禁；
7. 复核最终包中的版本、manifest、插件产物、release note 资源和兼容提示；
8. 同步发布主应用和对应插件。

## 6. 本轮完成标准

满足以下条件后，本记录才可转为“发布准备完成”：

- 主要新功能 UI 已按真实任务流走查，高优先级体验问题已关闭；
- 升级说明的摘要和详情结构、打开方式、回看方式及迁移事项关系已经确定；
- `0.7.0-alpha.1` 正式文案已经人工复核，不再使用当前占位式 AI 草稿作为最终内容；
- API v3 主应用与新版插件发布候选组合通过分批、进度、取消、失败恢复和重启场景验收；
- 主应用与插件的版本和兼容声明一致，并具备同步发布安排；
- 各专项计划中仍适用的数据迁移、真实 Tauri 和安装包门禁已经记录明确结果；
- 最终版本检查、前端构建、后端编译和相关自动化测试通过。
