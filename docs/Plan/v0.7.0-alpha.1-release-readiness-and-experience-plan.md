# v0.7.0-alpha.1 发布收口与体验优化记录

> 状态：主体功能基本完成；当前按 Alpha 风险接受语义完成最低发布安全门禁，其余体验与完整验收进入 `0.7.0` 正式版最终门禁
>
> 初始记录：2026-07-27
>
> 最近修订：2026-07-31
>
> 目标版本：桌面端 `0.7.0-alpha.1`；涉及插件随兼容主应用同步发布；后续以不带预发布标识的 `0.7.0` 作为正式版最终收口点
>
> 发布范围：移动端版本与发布周期独立，不跟随桌面端 `0.7.0-alpha.1` 发布，也不作为本记录的桌面端发布审查范围；移动端另按自身版本计划和验收清单执行
>
> 文档定位：跨模块发布收口记录，用于定义 Alpha 与正式版的门禁边界；不是面向用户的最终版本说明，也不替代各模块专项计划中的完整验收清单

## 1. 当前结论

自上一已发布标签 `v0.6.6-r.2` 以来，`dev` 主线已经完成本版本主体功能和架构改动。由于 `v0.6.6-r.2` 标签位于独立的修复分支，主线在分叉后再合并回 `dev`；因此本记录以下清单按 `v0.6.6-r.2..HEAD` 的当前提交区间和实际代码主题归并，避免把 r.2 热修复重复列为 `0.7.0` 新功能。现阶段不再把 Sidecar Plugin API v3 视为“尚未打通”的功能：开发模式中，主应用已经可以成功调用 API v3 插件，并实际使用新的分批处理优化特性。

`0.7.0-alpha.1` 是供较早验证新能力、迁移路径和真实环境兼容性的桌面端预发布版本，不应按正式版或 RC 的完成度要求来定义。Alpha 允许存在已识别、可说明、可绕过或可恢复的中低风险问题，也允许部分体验打磨、完整桌面端平台矩阵和长尾场景验收继续留到后续预发布阶段或 `0.7.0` 正式版。

本记录只决定桌面端及其配套插件的发布门禁。移动端不要求与桌面端同步版本或同步发版，移动端功能、构建、平台矩阵、迁移和体验问题均不阻断本次桌面端 `0.7.0-alpha.1` 审查，除非后续另有明确的跨端依赖约束。

这不意味着 Alpha 可以忽略发布安全。当前收口目标调整为：

1. 冻结 Alpha 功能范围，避免继续无边界增加需求；
2. 只把可能造成数据损坏、安全或隐私问题、不可控资源消耗、应用无法安装/启动/升级、核心兼容声明失真等不可接受风险设为 Alpha 硬门禁；
3. 对其余未完成项分类处理：具体的中低风险缺陷进入已知风险记录；仅缺少完整验收证据的项目保留在专项计划，并明确为正式版最终门禁；
4. 用发布候选主应用与插件验证最小可用兼容组合，使 Alpha 用户能够真实试用并反馈；
5. 将系统性 UI 打磨、完整升级说明信息架构、全面迁移矩阵与长尾可靠性验收保留为 `0.7.0` 正式版最终门禁。

专项计划中的“最终门禁”不再自动等同于 `0.7.0-alpha.1` 的发布门禁。是否阻断 Alpha，应按风险严重度、暴露概率和可恢复性判断，而不是按待办数量或测试名称机械判断。

## 2. 分层发布门禁

### 2.1 三层口径

| 层级             | 含义                                                                                   | 处理方式                                                                     |
| ---------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Alpha 硬门禁     | 一旦发生会造成不可接受损失，或会使本次 Alpha 无法被有效安装、启动、升级和试用的风险    | 发布前必须关闭，或通过缩小发布范围彻底消除暴露面                             |
| Alpha 可接受风险 | 已知的中低风险问题，影响有限且可绕过、可重试或可恢复                                   | 可以随 Alpha 发布，但必须进入已知风险清单并指定后续收口版本                  |
| 正式版最终门禁   | 面向普通用户稳定发布所需的桌面端体验、兼容、迁移、可靠性、平台覆盖及尚未补齐的完整证据 | 最迟在不带预发布标识的 `0.7.0` 发布前关闭；后续 Alpha、Beta 或 RC 可逐步收紧 |

### 2.2 Alpha 硬门禁范围

以下问题原则上阻断 `0.7.0-alpha.1`：

- 发布候选安装包无法完成基本安装、启动、升级或进入主要界面；
- 已知路径可能静默损坏、覆盖或丢失既有用户数据，且缺少可靠备份、恢复或隔离措施；
- 存在高严重度的安全、隐私或权限越界问题；
- 常规操作可能触发无上限 CPU、内存、线程、磁盘或子进程消耗，导致系统或应用失去响应；
- 对外宣称可用的核心新能力在发布候选组合中无法完成最小主路径；
- 主应用、插件、manifest、最低宿主版本或 API version 声明与实际产物不一致，用户按声明安装后必然落入错误组合；
- 迁移或不可逆操作缺少最基本的对象、影响、失败状态和恢复提示，使试用者无法知情承担 Alpha 风险；
- 必需的版本检查、前端构建、后端编译或发布产物检查失败。

“尚未完成某项测试”本身不自动构成 Alpha 阻断，但如果该测试是排除上述高风险问题的唯一证据，则缺失证据仍应按硬门禁处理。

### 2.3 可留到正式版的典型项目

在没有证据表明会升级为高风险的前提下，下列项目可以不阻断 `0.7.0-alpha.1`：

- 非核心页面的视觉统一、低频交互细节、术语和文案的全面润色；
- 完整的升级说明摘要/详情信息架构、回看入口和跨版本聚合体验；
- 已有最小主路径证据后的全平台、全旧版本、全故障注入和长时间稳定性矩阵；
- 不会造成数据损坏或任务失控的进度精度、局部结果展示、取消反馈和重启长尾问题；
- 性能基准、诊断可观测性和上游集成的完整收口，但已知资源失控问题除外；
- 低频边界场景的自动化补齐，以及不影响 Alpha 风险知情和恢复能力的文档完善。

这些项目不是被取消，而是进入 `0.7.0` 正式版最终门禁。若 Alpha 反馈证明其影响范围、严重度或不可恢复性高于预期，应立即提升为后续预发布版本的硬门禁。

### 2.4 Alpha 已知风险记录

每个随 Alpha 接受的具体已知问题至少记录：

- 所属模块和对应专项计划条目；
- 触发条件与受影响用户；
- 最坏影响及是否涉及数据、权限或资源；
- 当前规避、重试、回滚或恢复方式；
- 为什么允许进入 Alpha，而不是硬门禁；
- 责任人或责任计划、目标修复版本和重新评估条件。

不得只写“Alpha 允许有问题”而不说明具体风险，也不得用已知风险记录豁免数据完整性、安全、隐私和不可控资源风险。

## 3. Sidecar Plugin API v3 状态与门禁

### 3.1 已确认状态

- API v3 的宿主调用链已经在开发模式中成功运行；
- 新版插件已经实际进入新的分批处理路径，而不是回退到旧 API v2 调用；
- 分批优化是本次主应用与插件组合发布的一部分；
- 主应用与对应新版插件计划同步发布，避免先发布任一侧造成能力缺失或兼容误判；
- 主程序继续保留既有 API v2 插件加载能力，但依赖 API v3 新能力的插件必须按声明的主程序兼容范围发布。

### 3.2 Alpha 硬门禁

开发态成功调用证明主链路已经打通，但 Alpha 发布前仍需确认：

- 发布候选主应用实际加载发布候选插件，而不是开发目录或陈旧二进制；
- manifest 当前平台键指向最终随包分发的稳定产物；
- 至少一个有代表性的分批任务可以完成，宿主能收到结果和明确终态，不会无限等待或持续泄漏资源；
- 主应用和插件版本、最低宿主版本及 API version 声明一致；
- 同步发布时提供明确的 Alpha 兼容提示，避免用户只更新一侧后误以为功能损坏。

因此，Sidecar API v3 当前应描述为：**开发态主链路与分批优化已验证成功；Alpha 发布前需完成发布候选组合的最小主路径和产物一致性验收。**

### 3.3 正式版最终门禁

以下完整可靠性矩阵默认不阻断 Alpha，但最迟在 `0.7.0` 正式版前完成：

- 分批任务的进度、局部结果、取消、失败终态和完成终态完整验收；
- 插件进程重启后的首次调用、旧进程迟到事件隔离和多作业竞争；
- 失败恢复、重复调用、异常退出和不同兼容组合的系统回归；
- 发布候选主应用与各正式支持插件版本的完整兼容矩阵。

如果其中任一未完成项已经表现为数据损坏、无限挂起、不可控资源消耗或错误兼容声明，则应从正式版门禁提升为 Alpha 硬门禁。

## 4. 新功能 UI 打磨

### 4.1 Alpha 范围

Alpha 不以“大部分新功能 UI 已达到正式发布质量”为前提。发布前只需确保：

- 对外邀请试用的核心主路径可以被理解并完成；
- 迁移、清理、重建、覆盖和不可逆转换等危险操作清楚说明对象、影响与恢复边界；
- 执行中、成功、失败和可重试等关键状态不会造成严重误判；
- 错误至少能指出可行动的下一步，不以无解释堆栈作为唯一反馈；
- 已知体验缺陷不会遮蔽高风险状态或诱导用户执行破坏性操作。

其余视觉统一、低频交互、跨模块术语治理和完整移动端体验可以进入后续预发布阶段或正式版最终门禁。

### 4.2 正式版重点范围

正式版前仍需按实际任务流集中打磨，而不是逐页做孤立美化。重点包括但不限于：

- Recall 配置、检索管线、诊断和迁移入口；
- Knowledge 工作区、资料摄取、授权、检索与研究任务；
- Agent 中 Recall / Knowledge 的配置与能力说明；
- Guided Flow、版本说明和知识库迁移步骤；
- 移动端资产管理、聊天附件、预览和状态反馈（仅作提交区间事实记录，不纳入桌面端本节的审查范围，按移动端独立计划执行）；
- Smart OCR 与 Sidecar API v3 分批作业的进度、取消和结果呈现。

打磨原则：

1. **层级清楚**：默认界面只展示完成当前任务所需的信息，高级诊断和实现细节按需展开；
2. **术语一致**：Recall、Knowledge、资料库、思绪、检索预设等概念在不同入口使用同一套命名；
3. **状态可理解**：准备中、执行中、部分成功、等待重建、失败、可重试和已完成需要有可区分的反馈；
4. **危险操作明确**：迁移、清理、重建、覆盖和不可逆转换必须说明对象、影响与恢复路径；
5. **错误可行动**：错误信息应告诉用户下一步能做什么，不直接暴露无解释的内部协议或堆栈；
6. **桌面与移动端各自成立**：不为了视觉统一照搬布局，应遵循各端已有组件和交互边界；
7. **控制范围**：优先处理高频主路径、阻断理解的问题和高风险操作，再处理装饰性统一。

## 5. 升级说明的信息架构与文案

### 5.1 Alpha 所需内容

`0.7.0-alpha.1` 不要求先完成正式版升级中心或完整的摘要/详情交互设计，但发布说明必须经过人工事实复核，并清楚包含：

- 这是风险高于正式版的 Alpha 预发布版本，适合愿意试用和反馈的用户；
- 本次最值得试用的能力和最小兼容要求；
- 数据迁移、插件同步更新或不可逆操作的明确提醒；
- 已知风险、影响范围、规避或恢复方式；
- 问题反馈入口，以及必要时的降级、备份或回退建议。

现有 AI 草拟 release note 继续视为占位资源，不能未经事实核对直接作为 Alpha 发布说明；但 Alpha 不需要为了替换该草稿而先完成正式版级别的完整内容架构。

### 5.2 正式版两层内容

正式版方案至少区分：

#### 摘要层

面向希望快速了解版本的用户，回答：

- 这次升级最重要的变化是什么；
- 哪些变化会直接影响现有使用方式；
- 是否有数据迁移、插件同步更新或其他需要立即处理的事项；
- 用户现在可以选择继续了解、开始处理事项，还是稍后再看。

摘要应短、可扫描，以用户收益和影响为主，不罗列提交记录或内部模块名。

#### 详情层

面向希望完整了解版本的用户，按主题提供：

- 功能变化及典型使用场景；
- 与旧版本的差异；
- 数据迁移、兼容边界与恢复说明；
- 重要修复和稳定性改进；
- 开发者或高级用户关心的协议变化；
- 必要时链接到更完整的模块文档或迁移报告。

详情不应强迫所有用户在启动时逐段阅读。

### 5.3 正式版待设计问题

下列问题不阻断 Alpha，但需要在正式版体验收口前解决：

1. 摘要与详情是在同一流程内展开、独立页面展示，还是采用“升级中心 + 详情页”的组合；
2. 首次升级自动出现时展示到什么深度，关于页手动回看时是否提供更完整目录；
3. 版本说明与必须确认的数据迁移应如何分离，同时又保持清晰的上下文关系；
4. 大量主题使用卡片、目录、折叠章节还是独立详情页更合适；
5. 跨多个版本升级时，摘要应按最终用户影响合并，还是按版本逐项回放；
6. 主应用与插件同步发布的兼容提示应出现在摘要、迁移事项还是独立状态检查中；
7. 如何保存“已读摘要”“已处理事项”和“稍后查看详情”等不同状态，避免把阅读行为等同于迁移完成。

### 5.4 内容生产原则

- 先由实际代码、迁移边界和发布验证结果建立事实清单，再写用户文案；
- 摘要、详情、迁移确认和故障恢复文案分别编写，不从一篇长文机械截断；
- 每条重点说明采用“变化—用户影响—需要操作”结构；
- 对内部重构，只在它带来可感知能力、兼容变化或可靠性收益时进入摘要；
- 避免空泛的“全面升级”“焕新体验”“更智能”等宣传式表达；
- AI 可以辅助整理初稿，但对外内容需要人工复核事实、优先级、语气和信息密度。

## 6. 发布组合与收口顺序

### 6.1 `0.7.0-alpha.1`

1. 冻结 Alpha 功能范围，整理桌面主应用和插件的最低兼容组合；
2. 将所有未完成项按 Alpha 硬门禁、Alpha 可接受风险和正式版最终门禁重新分类；
3. 关闭数据、安全、隐私、资源失控、安装启动升级和产物声明一致性相关硬门禁；
4. 只打磨核心试用路径和高风险操作所必需的 UI；
5. 编写经过人工事实复核的 Alpha 发布说明与已知风险清单；
6. 构建桌面主应用与新版插件发布候选组合，完成最小主路径和产物一致性验收；
7. 完成版本检查、前端构建、后端编译、发布候选安装/升级/启动 smoke；
8. 复核所有已知接受风险的影响、恢复方式和目标修复版本，并确认其余延期项已保留正式版门禁后，同步发布桌面主应用和对应插件。

> 移动端不属于本次桌面发布组合，按独立版本计划、构建流水线和发布审查周期处理。

### 6.2 后续预发布与 `0.7.0` 正式版

1. 根据 Alpha 真实反馈重新评估风险等级，高风险回归立即提升为下一预发布版本硬门禁；
2. 完成各桌面端专项计划中的完整数据迁移、真实 Tauri、故障恢复和桌面平台矩阵；
3. 完成 Sidecar API v3 的取消、失败、重启、迟到事件和兼容组合回归；
4. 系统打磨新功能 UI，解决已承诺范围内的高优先级体验问题；
5. 完成升级说明摘要/详情信息架构、正式文案和回看方式；
6. 关闭或重新决策全部 Alpha 已知风险，不把未经评估的遗留问题直接带入正式版；
7. 用正式发布候选包完成最终版本、manifest、迁移、安装包和联合插件验收。

## 7. `0.7.0-alpha.1` 完成标准

满足以下条件后，本记录可标记为“Alpha 发布准备完成”：

- Alpha 功能范围和桌面主应用/插件最低兼容组合已经冻结；
- 发布候选包通过基本安装、升级、启动和主要界面 smoke；
- 没有已知且仍暴露的数据损坏、安全、隐私、不可控资源消耗或核心启动阻断问题；
- 涉及既有用户数据的迁移与不可逆操作具备与风险相称的最小备份、失败提示和恢复证据；
- API v3 发布候选组合通过最小分批主路径，最终产物路径和兼容声明一致；
