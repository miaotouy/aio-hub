# 移动端与桌面端互通方式调查

> 调查日期：2026-11-02。结论基于当前工作区源码与所列官方资料；本文提供选型依据，接口示例属于建议稿。
>
> 方向性设计见：[移动端作为桌面 Companion 的连接构想](mobile-desktop-companion-connection-concept.md)。

## 1. 结论

2026-11-02 讨论收敛为 **可切换业务后端的移动客户端**：移动端复用聊天界面，在“本机”和“已配对桌面”之间切换业务后端。

- **本机后端**：沿用手机模型、角色、会话、资产与执行能力，本机保存正式业务数据。
- **远程桌面后端**：直接使用桌面会话及其模型、Agent、资产与任务。桌面负责业务状态和执行，手机采用 IM 式客户端缓存。
- **缓存与客户端状态**：手机可落盘远端列表、消息和预览，保存草稿、阅读位置；远端会话始终属于桌面，和本机会话库分开管理。
- **显式迁移**：导入导出作为独立操作；切换后端仅切换数据空间与订阅。
- **网络连接**：同网优先局域网，异地通过用户选择的虚拟局域网/VPN 或自定义隧道访问同一 Gateway。

产品与数据边界见第 3.1–3.5 节；该方向尚待实现，接口和实施范围仍需细化。

当前最值得解决的互通场景是：手机继续桌面会话、使用桌面模型与工具、查看任务结果、上传手机文件供桌面处理。双端离线共同编辑全量业务数据的成本明显更高，适合在出现明确需求后单独研究。

**最大工程缺口在业务运行时与授权边界。** 两端已有请求、存储和角色包处理基础，尚未形成可直接连接的 Companion 服务。

### 2.1 两个容易低估的复用问题

**聊天 service 具有交互上下文。** 当前发送逻辑在部分参数缺失时读取桌面当前会话、当前 Agent 和输入框临时模型，错误还经过 UI 错误处理器包装。远程请求应显式携带会话、Agent 与模型选择策略，通过专用适配器得到可判定的成功/失败结果，防止桌面正在编辑的上下文影响手机请求。

**快照恢复与任务恢复是两种能力。** 现有 registry 恢复非终态快照时会标记中断；它可以帮助手机展示历史状态。桌面进程重启后能否继续执行任务，取决于具体任务运行器的恢复支持，不能由网络重连或 registry 快照替代。

## 3. 互通方式比较与产品方向

| 方式 | 手机获得什么 | 桌面需在线 | 主要成本 | 适用判断 |
| --- | --- | --- | --- | --- |
| 文件导入导出 | 角色、预设、会话等独立副本 | 只在导出/发送时需要 | 格式兼容、资源打包、冲突提示 | 适合内容搬运；角色已有较好基础 |
| 模型能力网关 | 使用桌面配置的模型，手机维护自己的会话 | 是 | 独立推理 API、授权、额度控制、流式取消 | 适合仅需要“手机使用电脑上的模型” |
| Companion 业务网关 | 使用桌面会话、Agent、任务、授权工具与资产 | 是 | 设备身份、业务 API、投影、任务恢复、权限 | 已选定的远程业务后端方向 |
| 双端同步 | 两端都保留可独立修改的数据副本 | 可异步 | 双端 schema、增量日志、删除标记、冲突合并、资产引用与密钥策略 | 适合明确要求双端离线编辑的产品目标 |

当前远程后端使用桌面会话与执行运行时。模型网关保留为独立扩展选项：若未来仅借用桌面推理能力，会话与角色装配仍归手机，需要作为另一种明确能力设计。

WebDAV、共享目录或文件同步服务适合传递导出包、备份等文件。两端的原始配置目录和数据库具有各自 schema、关联资产与运行中写入状态，直接同步这些目录无法建立可靠的业务合并语义。

### 3.1 同一界面切换业务后端

```text
移动端聊天界面
  └─ 当前业务后端
       ├─ 本机 LocalChatBackend
       │    └─ 本机会话、模型、Agent、资产与执行
       └─ 办公室电脑 RemoteChatBackend
            ├─ 桌面：会话、模型、Agent、资产与任务
            └─ 手机：远端缓存、草稿、阅读位置与连接状态
```

| 行为 | 本机后端 | 远程桌面后端 |
| --- | --- | --- |
| 会话列表与新建 | 读取/创建本机会话 | 查询/请求创建桌面会话 |
| 发送与执行 | 本机请求模型并执行本机支持的能力 | 桌面执行，手机接收确认、任务状态与结果 |
| 编辑与删除 | 修改本机正式数据 | 提交桌面操作，按服务端确认或事件更新缓存 |
| 模型、Agent 与资产 | 在本机数据空间解析 | 在选定桌面数据空间解析；手机保存授权投影与受控预览 |
| 离线 | 继续使用当前可用的本机能力 | 查看已有缓存、编辑草稿，显示连接状态与缓存更新时间 |
| 切换 | 恢复本机列表与客户端状态 | 恢复对应桌面列表与客户端状态，并重新订阅 |

界面消费当前业务后端；连接管理负责配对、地址与重连。首版可保持一个活动后端，并保留其他后端的缓存与草稿。功能可用性依据后端 capabilities 和权限表达，缺失能力显示清晰原因；界面骨架保持稳定。

### 3.2 本机正式数据与远端缓存

远端缓存可以落盘到 SQLite，用于快速打开、分页阅读与离线展示。它是桌面数据的可重建投影，本机会话库持有本机的正式数据；两者使用独立的数据访问边界。具体共用数据库还是拆库留待实施设计。

- 缓存、草稿、阅读位置、选中会话与事件 cursor 按稳定 `backendId` 隔离。
- 会话和消息引用使用 `(backendId, sessionId, messageId)` 等组合身份；模型、Agent 与资产引用同样携带后端归属。
- 本机使用固定的本机身份，远端身份基于配对确认的桌面身份；IP、域名和当前访问路径只用于连接。
- 清理缓存只释放手机空间；删除桌面会话是需要授权和服务端确认的业务操作。草稿与待确认发送记录独立保留，避免随可重建缓存一起清理。
- 缓存按需加载并设置容量/淘汰策略；再次打开时获取最新投影或按 cursor 补偿。服务端删除、权限变化和缓存失效按协议回写客户端。
- 远端会话迁移为本机会话需要用户显式导入，并处理模型绑定、资产复制和 ID 映射。

### 3.3 切换与请求生命周期

所有已发起请求在创建时绑定 `backendId` 和显式业务目标。后端切换只改变当前界面订阅与数据来源：发给桌面的消息、重试和文件上传继续属于原桌面，异步返回也只更新原后端的状态。

切换界面时可以解除旧页面订阅、取消纯查询或预览请求。已接收的远端聊天和任务继续执行；用户主动取消任务时另行提交明确命令。返回原后端后，通过快照与事件恢复展示。

远端连接中断时保留当前数据空间，展示缓存与连接状态，由用户决定是否切到本机。首版离线发送保留为草稿，恢复连接后由用户发送；已提交但尚未确认的操作保留原请求 ID，通过查询或幂等重试确认结果。离线自动发送队列留作后续能力。

### 3.4 领域接口与实现边界

建议在聊天 Store 与数据/执行服务之间引入 `ChatBackend`，统一会话查询、创建、消息命令、任务控制和事件订阅。下面仅列能力形状，DTO 与错误协议在实施设计时确定：

```ts
interface ChatBackend {
  readonly id: BackendId;
  readonly kind: "local" | "remote";
  listSessions(query: SessionQuery): Promise<SessionPage>;
  getSession(sessionId: string): Promise<SessionSnapshot>;
  createSession(command: CreateSessionCommand): Promise<SessionSnapshot>;
  sendMessage(command: SendMessageCommand): Promise<SendReceipt>;
  cancelTask(taskId: string): Promise<void>;
  subscribe(cursor: string | null, onEvent: BackendEventHandler): Unsubscribe;
}
```

- `LocalChatBackend` 适配当前移动端聊天存储与执行器，保留现有本机使用能力。
- `RemoteChatBackend` 适配桌面受控 API、远端缓存和事件恢复；远端事件只更新所属缓存与客户端状态。
- 当前活动后端决定会话、模型、Agent、资产和任务的数据来源；界面只接触统一投影与能力状态。
- 连接凭据、证书信任、Endpoint 选择属于连接层；本地 Tauri IPC 与远端 API 各有独立适配。

### 3.5 界面信息

后端选择器显示“本机”及已配对桌面的用户名称，聊天工作区展示当前后端与连接状态。缓存展示应带可理解的更新时间，例如“办公室电脑 · 连接中”“已显示缓存内容，上次更新于 14:32”。

模式切换保留各自草稿和阅读位置。用户可明确区分“清理此设备缓存”“删除桌面会话”和“迁移到本机”；实际操作入口按对应页面需要放置。

## 4. 网络连接方式比较

网络层解决“到达桌面”，业务协议解决“允许做什么”；两层独立选型。

| 网络方式 | 建议定位 | 优点 | 限制与成本 |
| --- | --- | --- | --- |
| 局域网直连 | 同一 Wi-Fi/有线网络的优先路径 | 路径短，适合本地文件传输 | AP 隔离、访客 Wi-Fi、桌面防火墙可能阻断；发现失败时需手动地址/二维码兜底 |
| 用户虚拟局域网/VPN | 异地访问主路径 | 应用继续访问同一受控 API，网络实现可替换 | 用户需要配置网络；路径可能直连或经过该网络提供的中继 [1] |
| 用户反向隧道/自有服务器 | 高级用户选项 | 可提供稳定域名入口 | 用户承担服务器与网络维护；公网入口仍需完整应用认证和限流 |
| 自建 WebRTC DataChannel | 有强内置穿透诉求时再评估 | 可承载端到端数据通信 | 仍需信令交换与 ICE 配置，受限网络需要 TURN 等兜底；增加网络基础设施责任 [2] |
| 官方应用中继 | 独立托管产品议题 | 可统一接入体验 | 带宽、可用性、滥用处理、部署与运营形成长期服务责任 |
| USB/ADB 转发 | 开发诊断入口 | 适合验证 API 和定位网络问题 | 依赖线缆/开发环境，面向 Android 的调试能力，产品入口需另行设计 |

### 4.1 虚拟局域网需要说清的边界

以 Tailscale 为例，官方列出了直连、Peer Relay 与 DERP 路径；直连失败时可以转为中继，流量仍由 WireGuard 端到端加密 [1]。因此：

- AIO Hub 可以沿用“用户管理网络、项目提供应用协议”的维护边界。
- 若要求整个链路都由用户自有基础设施承载，应单独确认网络控制面、中继与流量路径。
- 普通 Endpoint 连接成功只能说明应用可达。界面只有获得网络提供者的可信诊断结果后，才应显示“直连/中继”。

当前建议先支持用户提供地址与二维码携带地址，自动发现作为便利层添加。采用 mDNS 时应使用平台发现接口并处理局域网权限；发现结果只作为候选地址，配对身份仍需校验。

## 5. 建议的应用协议形态

建议优先研究 **HTTPS 请求响应 + SSE 事件流 + 独立资产传输**。这是对当前代码基础和聊天/任务场景的工程判断；后续若有大量双向实时消息，再比较 WSS。

```text
手机本地模式 ──> 手机本地会话与模型请求

手机连接桌面模式
  ├─ 查询/命令 ── HTTPS ──> Companion Gateway
  ├─ 状态订阅 <── SSE ──── Gateway <── 桌面业务适配器
  └─ 文件传输 <─ HTTPS ──> 受控资产接口
                                      ├─ 聊天执行与会话持久化
                                      ├─ Agent / 模型选择
                                      └─ 工具 / 后台任务 / 审批
```

SSE 标准包含事件 `id` 与重连时的 `Last-Event-ID` [3]。服务端仍需保存可补偿的事件，定义保留窗口和快照恢复；只使用 SSE 无法自动获得这些业务能力。

### 5.1 控制面建议

| 能力 | 建议接口示意 | 关键语义 |
| --- | --- | --- |
| 能力协商 | `GET /companion/v1/capabilities` | 协议版本、功能、权限与资源限制；按设备权限过滤 |
| 会话浏览 | `GET /companion/v1/sessions`、`GET /sessions/{id}` | 受控投影、分页、revision；省略模型密钥与内部路径 |
| 发送消息 | `POST /companion/v1/sessions/{id}/messages` | 显式目标、客户端请求 ID，接收成功后返回 taskId 与可确认的消息身份 |
| 任务控制 | `GET /companion/v1/tasks/{id}`、`POST /tasks/{id}/cancel` | 独立于连接的状态机；取消请求与最终取消结果分开表达 |
| 事件补偿 | `GET /companion/v1/events?cursor=...` | 顺序、重复、保留窗口、cursor 失效与重新取快照的语义 |
| 文件传输 | 上传会话、资产预览与授权下载接口 | 资源大小限制、分块/恢复、完整性校验、设备授权 |

表中省略前缀的路径均属于 `/companion/v1`；精确 schema 留待实施设计。

重试需以 `(deviceId, clientRequestId)` 识别同一请求，并在约定保留期内返回同一接收结果；相同 ID 携带不同内容应返回冲突。否则 Wi-Fi 切换后重试发送可能造成重复聊天、工具执行与付费请求。

资源 revision、单任务 seq 和事件 cursor 分别服务于资源更新检测、任务内部排序和订阅恢复，需分别定义。快照与订阅还应共享一致性边界，覆盖“查询结束到订阅建立”之间的变化。桌面重启时通过新的运行代次或可持久化日志识别旧 cursor，历史缺失时回到快照。

### 5.2 数据面建议

手机上传图片/文档后，桌面生成自己的 assetId，手机发送消息时只引用授权资产。手机本地 assetId 与桌面 assetId 应建立显式映射。

缩略图、预览、音视频 Range 与原件下载按需要提供独立接口。下载能力需短期、限定资源和用途，避免把大文件塞进聊天状态事件。支持断点续传时同时约定上传 ID、有效期与校验规则。

手机已有原生流式和 multipart 传输，可参考其文件读取与取消机制；Companion 客户端应独立配置鉴权、超时、TLS 信任、重定向与日志脱敏。媒体预览若由 WebView 直接请求，也要具备与原生客户端一致的信任和授权路径，可考虑复用原生受控缓存及现有资产预览机制。

## 6. 配对与安全

建议的配对交互是：**桌面开启短期配对窗口 → 手机扫描二维码 → 校验桌面身份 → 桌面确认设备和权限 → 建立可撤销设备凭据。**

二维码可以携带协议版本、桌面身份公钥/指纹、短期 nonce、过期时间和候选地址。IP/域名仅作为路由信息；同一桌面切网后保持身份，其他设备占用旧 IP 时仍应校验失败。

核心约束：

1. Gateway 按领域操作建立白名单和设备 scope。聊天读取、发送、资产读取/上传、工具执行分别授权。
2. 桌面持有上游 API Key，手机只收到受控模型描述与执行结果；错误和调试投影同步脱敏。
3. Gateway 独立于现有 LLM proxy。远程调用限制在明确领域接口，内部任意命令、URL 转发与本机路径保持应用内部使用。
4. 首次配对通过二维码等可信带外信息引导证书/身份校验；本地自签名方案需要专门实现信任与轮换。现有请求层的“忽略无效证书”选项不能充当配对信任机制。
5. 设备私钥/长期凭据使用系统安全存储，短期访问凭据可刷新、撤销；桌面应能终止已撤销设备的活动连接。
6. 敏感工具动作复用桌面审批语义。仅手机拥有执行 scope 时，文件写入、Shell 等高风险操作仍可要求本机确认。
7. 用户主动开启共享后按所选接口/地址监听，配合系统防火墙；设备级并发、请求大小与消耗限额需要明确。

隧道若在第三方节点终止 TLS，该节点是否能看到业务明文取决于后续加密层。要求手机至桌面全程保密时，应明确采用 TLS 透传、已验证的端到端私网，或其他经过审查的端到端保护方案。

## 7. 移动系统与运行时约束

### 7.1 后台与通知

Android Doze 会限制后台网络，iOS 应用进入后台后可能被挂起 [4][5]。设计上应接受手机随时断流：

```text
发送请求 → 桌面确认接收并创建任务 → 桌面继续执行
手机进入后台 / 切网 / 进程退出
手机再次打开 → 查询任务快照 → 补齐事件或重新取快照
```

桌面自身也需要明确“窗口隐藏”“业务窗口销毁”“应用退出”“系统睡眠”的区别。手机断开后继续执行，依赖桌面执行上下文仍存活；桌面关机或应用退出后的行为另行定义。

锁屏完成通知属于单独的后台触达能力。当前可优先承诺前台实时更新、返回应用后恢复；持续可靠的锁屏推送需结合平台推送机制、服务部署与隐私边界进一步设计。

### 7.2 Android 局域网与明文策略

当前生成工程为 `compileSdk = 36`、`targetSdk = 36`，Manifest 声明了 `INTERNET`。官方文档区分 Android 16 的 opt-in 局域网保护与面向 target SDK 37+ 的 Android 17 权限要求 [6]。本项目当前目标 SDK 下，无需仅为将来的要求提前请求 `ACCESS_LOCAL_NETWORK`；升级 target 时需重新核对连接和发现路径。

当前 Android 工程默认 `usesCleartextTraffic=false`，debug 构建覆盖为 true。这说明 debug HTTP 连通结果不能直接证明 release 请求路径可用。Tauri WebView、HTTP 插件、Rust reqwest 各自具体受到哪些平台策略影响，需要在实际使用的客户端和发布包验证；Companion 协议优先使用 HTTPS。

源码：[Gradle 配置](../../mobile/src-tauri/gen/android/app/build.gradle.kts)、[Manifest](../../mobile/src-tauri/gen/android/app/src/main/AndroidManifest.xml)。

### 7.3 iOS 局域网与发现

Apple 要求局域网访问用途说明；使用指定 Bonjour 服务的注册/发现时配置服务类型，自定义组播还涉及额外 entitlement [7]。选型时应将这些作为原生平台接入工作，并保留用户拒绝权限后的地址管理与可行动错误提示。二维码携带地址可以简化发现流程，局域网访问本身仍遵循系统权限。

### 7.4 桌面业务目前仍在前端运行态

当前桌面聊天 service 和后台任务 registry 位于 TypeScript 前端领域层。Rust 中新增 Axum 路由后，需要通过明确的内部适配桥访问拥有业务状态的执行上下文。

可选实现形态：

- **当前 Tauri 适配**：Rust Gateway 管网络与身份；向选定的业务所有者发送受控命令，取得结果与事件。需处理所有者就绪、窗口生命周期、超时、重复请求和关闭中的状态。
- **独立领域运行时**：以后把适合后台执行的聊天/任务逻辑与 UI 生命周期解耦，Gateway 调用其领域 API；现有 UI 订阅相同业务状态。

仓库已有 Electron 迁移规划和平台 bridge，但当前正式 `electron/` 工程目录尚未落地；这些规划不能作为已经具备后台服务的证据。Companion 协议与 DTO 保持平台中立，可以先适配当前 Tauri，再随领域运行时演进。

## 8. 建议优先聚焦的能力

最有价值的连贯体验是：

> 用户在桌面确认手机配对，在手机将后端从本机切换为该桌面，直接打开桌面会话并发送消息；切回本机后桌面任务继续执行，再次切回桌面时恢复同一会话和任务结果。

它同时验证“设备身份、正确业务目标、受控模型使用、任务归属、连接恢复”，比直接追求全量同步更能暴露真实架构缺口。

后续可沿同一 Gateway 增加手机照片/文件上传、桌面任务查看/取消，再选择具有明确权限与可恢复语义的工具接入。角色包继续服务显式迁移；聊天迁移需要补齐手机端格式映射、分支语义和资产重建。

进入实施设计前最影响成本的决策有三项：

1. ChatBackend 的首批业务范围、缓存投影与失效策略如何划分？当前已确定远端直接使用桌面会话，手机保留缓存与客户端状态。
2. 用户是否接受自行配置虚拟网络？若要求内置、低配置的异地连接，需要重新评估网络服务责任。
3. 首次支持要求桌面完整应用运行，还是需要独立常驻后台？后者会显著扩大当前运行时调整范围。

本次完成了静态调用链与外部技术资料核对，未执行跨设备连通、证书信任、后台恢复或文件传输实验。相关结论属于设计依据，性能和真机可用性仍需后续实测。
