# 用户表情包功能调研与落地方案

> 调研日期：2026-08-22
>
> 状态：调研完成，待产品决策后实施
>
> 参考图说明：用户提供的两张图片仅作为 QQ 类表情快捷面板与消息展示的视觉参考，不视为必须 1:1 复刻的交互/尺寸/图标规范。

## 1. 需求边界

目标是在 LLM Chat 输入区增加 QQ 风格的表情快捷面板，支持：

1. 用户拥有自己的表情包资产，可以导入、删除、编辑描述、分组和搜索。
2. 应用提供只读内置表情包。
3. 输入框工具栏点击表情入口，打开快捷面板；点击某个表情后插入当前光标位置。
4. 发送后，消息展示应保留表情图片，而不是只显示文件名或纯文本。
5. 表情可配置用户描述。该描述用于模型理解，不等同于自动 OCR/视觉转写。
6. 表情发送链路尽量继承现有附件的原始媒体 / 转写策略，同时允许明确控制模型收到图片、描述或两者。

## 2. 当前代码基线与可复用能力

### 2.1 输入区

当前消息输入区由以下链路组成：

- `MessageInput.vue` 同时承载 CodeMirror 编辑器和原生 `textarea` 编辑器。
- `MessageInputToolbar.vue` 已经有附件、宏、快捷动作、更多菜单等入口。
- `useChatInputManager` 管理输入文本、光标位置、草稿、跨窗口同步和附件占位符替换。
- 两种编辑器都暴露了 `getSelectionRange()`、`insertText()`、`replaceRange()`，因此“点击面板后插入当前光标位置”不需要立即迁移到 contenteditable。

现有附件占位符为 `【file::assetId】`，上传中使用 `【file::uploading:tempId】`。输入管理器会在导入完成后修复占位符，且草稿与分离窗口同步已经包含输入文本和附件列表。

### 2.2 资产与附件

全局 `Asset` 已支持图片、音频、视频、文档和其他文件，并通过 Asset Manager 统一导入、去重、持久化和读取二进制。

**纠偏设计**：
用户表情包具有**数量大、体积小、高频使用、整包导入导出**的特点。如果强行塞入全局 Asset Manager，会导致：

1. **污染用户资产库**：用户在资产管理器中只想管理重要文档和素材，不希望被成百上千张表情包小图（如“流汗黄豆.png”）刷屏。
2. **生命周期冲突**：全局资产有其独立的去重、清理和引用计数逻辑，而表情包需要按包（Pack）进行整套导入、导出、删除和物理清理。
3. **性能开销过大**：全局 Asset 导入会触发复杂的哈希计算、数据库索引和缩略图生成，对表情包而言过于沉重。

因此，**用户表情必须采用完全独立的存储与绑定机制，参考 Agent 私有资产的设计进行自治**：

- **独立存储**：用户导入的表情图片不进入全局 Asset Manager，而是由表情包服务（Sticker Library Service）统一存放在**当前激活的用户档案目录内**（如 `{currentProfileDir}/stickers/`，即 `user-profile-manager/user-profiles/{profileId}/stickers/`）。这样表情包完全属于特定的用户档案，切换档案时表情包也会跟着切换，并且在导入导出用户档案时，表情包作为档案的一部分，自然而然就会被一起打包和恢复。
- **独立协议**：通过自定义协议（如 `sticker://packId/stickerId`）或表情服务直接读取本地二进制，不依赖全局 `Asset` 协议。
- **消息级引用**：消息中插入表情时，保存的是独立的 `MessageStickerRef`，不与全局 `attachments` 混淆，避免发送时被误判为普通附件卡片。

### 2.3 模型发送管道

当前附件处理链路为：

1. 用户消息节点保存文本与 `attachments`。
2. 上下文管道将附件解析为文本或媒体。
3. `resolveAttachmentContent()` 根据模型能力、配置和已有转写结果决定使用转写文本还是保留原始媒体。
4. `transcription-processor` 负责处理 `【file::assetId】` 占位符：有转写则注入文本；没有转写则保留附件供多模态模型使用。
5. `asset-resolver` 最终读取图片/文件二进制并生成模型所需的媒体内容。

这使“表情描述是否替代原图”可以复用附件的最终决策层，但需要增加“用户描述”这一种明确的语义注释，不能把它伪装成 OCR 或系统转写结果。

### 2.4 已有相关能力

- Agent 私有资产已经支持图片、分组、描述和 `agent-asset://` 引用，但它的定位是跟随 Agent 导入导出的私有资产，不等同于用户的全局表情包库。
- VCP Connector 已有表情包清单扫描、缓存和 URL 修复服务，但它依赖 VCP 图片服务，当前没有接入 LLM Chat 输入面板的本地选择链路。
- 因此，Agent 资产与 VCP 表情库可以作为后续表情来源适配器，不建议在第一版直接把它们和用户表情的持久化模型混在一起。

## 3. 推荐产品模型

### 3.1 统一的表情包与表情条目

建议增加独立的表情域模型，但复用 `Asset` 作为文件实体：

```ts
interface StickerPack {
  id: string;
  name: string;
  source: "builtin" | "user" | "agent" | "vcp";
  iconStickerId?: string;
  description?: string;
  sortOrder?: number;
  isReadOnly?: boolean;
  enabled?: boolean;
}

interface StickerItem {
  id: string;
  packId: string;
  localPath?: string; // 用户表情在独立存储目录中的相对路径/文件名
  providerRef?: string; // 内置/远程表情的引用标识
  name: string;
  description?: string; // 给模型看的默认语义描述
  aliases?: string[]; // 搜索词/快捷关键词
  tags?: string[];
  sortOrder?: number;
  createdAt?: string;
}
```

建议将 `StickerPack` 的索引、名称、描述、顺序和 `StickerItem` 元数据放入 `createConfigManager` 管理的轻量 JSON 配置，该配置文件也存放在当前用户档案目录下（如 `{currentProfileDir}/stickers/config.json`）；图片二进制由表情包服务在当前用户档案的独立目录中管理。表情数量较大时，可将条目索引拆成单独文件，但第一版不需要引入数据库。

### 3.2 用户表情与内置表情

| 来源       | 文件存储                                                   | 可编辑描述                       | 可删除        | 推荐首版状态 |
| ---------- | ---------------------------------------------------------- | -------------------------------- | ------------- | ------------ |
| 内置       | 随应用资源/静态资源发布                                    | 否或仅允许“另存为用户表情”后编辑 | 否            | 支持         |
| 用户       | 当前激活的用户档案目录内 (`{currentProfileDir}/stickers/`) | 是                               | 是            | 支持         |
| Agent 私有 | Agent 私有资产目录                                         | 沿用 Agent 资产编辑能力          | 由 Agent 管理 | 第二阶段适配 |
| VCP        | 远程 URL/现有 VCP 清单                                     | 可在本地加覆盖描述，但不修改远端 | 取消收藏/隐藏 | 后续适配     |

内置包建议采用 manifest + 资源目录，而不是启动时把内置图片导入用户资产库。用户点击内置表情时，可以在消息中保存稳定的 `providerRef`；若后续需要跨设备、导出或脱离内置包使用，再提供“复制到我的表情”。

## 4. 输入区交互方案

### 4.1 快捷面板

建议在 `MessageInputToolbar` 增加一个表情按钮，位于附件按钮附近。点击后打开 Popover/浮层，包含：

- 顶部搜索框：按名称、描述、别名和标签搜索。
- 包/分类标签：最近使用、我的表情、内置包，以及后续 Agent/VCP 来源。
- 网格预览：统一缩略图尺寸；透明 PNG/WebP/GIF 以 contain 方式展示。
- 点击插入；右键或更多操作进入编辑描述、收藏、删除等动作。
- 最近使用：单独持久化最近使用的表情 ID，避免每次翻包。
- 导入入口：选择图片文件、批量导入、从剪贴板粘贴图片；导入后自动创建用户表情条目。

首版不要直接复刻参考图中的所有系统级图标（GIF、剪刀、语音等），只增加表情入口和必要的表情包管理能力，避免扩大范围。

### 4.2 插入语义

首版建议继续使用现有文本编辑器和附件占位符：

- 点击表情时，将对应表情加入当前草稿的表情引用集合 `stickerRefs`（不混入普通附件集合，避免 UI 渲染冲突）。
- 在当前光标位置插入 `【sticker::stickerId】`；上传中的用户表情可使用 `【sticker::uploading:tempId】`。
- 发送时将 `stickerId -> localPath/providerRef/description` 一并保存到消息元数据。
- 输入框中暂时显示可读文本占位符，例如 `【表情：开心】`，但内部仍使用稳定 ID；不建议直接把图片 base64 塞进文本。

这样可以复用 `insertText()`、光标保存、撤销/重做、草稿持久化和分离窗口同步。后续若需要真正的行内图片 chip，再将编辑器内部状态抽象为“文本片段 + 表情片段”，同时适配 CodeMirror 和 textarea 降级模式；不建议第一版只给 CodeMirror 做富文本而让 textarea 行为不一致。

### 4.3 消息展示

消息气泡中应把 `【sticker::...】` 解析为图片节点，样式接近聊天表情而不是普通附件卡片：

- 默认限制最大宽高，保持原始比例。
- GIF/WebP 动图保留动画；点击可放大预览。
- 表情对应的描述可以在悬停提示、消息详情或“查看模型上下文”中展示，但不应默认替换用户看到的图片。
- 消息编辑、分支复制、导出和重新生成必须保留表情引用与描述。

## 5. 给模型发送什么：推荐决策

### 5.1 核心结论

**默认继承附件策略，但把用户自定义描述视为显式语义注释，而不是自动转写。**

推荐增加每条表情引用的输入策略：

```ts
type StickerInputMode = "inherit" | "image" | "description" | "both";

interface MessageStickerRef {
  stickerId: string;
  assetId?: string;
  providerRef?: string;
  description?: string; // 发送时使用的描述快照
  inputMode?: StickerInputMode;
}
```

默认值为 `inherit`，其决策如下：

| 当前模型/配置                          | 有用户描述 | 模型收到的内容                                     |
| -------------------------------------- | ---------- | -------------------------------------------------- |
| 模型支持原始图片，附件策略使用原始媒体 | 是         | 原始图片 + 简短的用户描述文本（推荐）              |
| 模型支持原始图片，附件策略使用原始媒体 | 否         | 原始图片                                           |
| 当前附件策略会转写/模型不支持图片      | 是         | 用户描述文本；不强制对表情执行 OCR                 |
| 当前附件策略会转写/模型不支持图片      | 否         | 沿用附件原有转写链路；没有结果则按现有降级策略     |
| 用户显式选择 `image`                   | 任意       | 尽量只发送原始图片；模型不支持时给出能力提示或降级 |
| 用户显式选择 `description`             | 任意       | 只发送用户描述，不发送图片                         |
| 用户显式选择 `both`                    | 任意       | 原始图片 + 用户描述                                |

理由：

1. 表情上的文字可能不是完整语义，单靠 OCR 会丢失“阴阳、开心、无语”等语用信息。
2. 用户描述是人工标注，可信度通常高于自动 OCR，应优先于系统自动转写。
3. 支持视觉的模型最好看到原图；不支持视觉的模型仍能通过描述理解表情意图。
4. 继承附件策略可以避免新功能破坏现有模型能力判断、Token 预览和转写设置。

### 5.2 管道实现建议

不要把 `description` 写入 `Asset.metadata.derived.transcription`，因为那会混淆“用户语义标注”和“由某个引擎生成的衍生数据”。建议在消息级保存 `MessageStickerRef`，并在上下文处理阶段生成独立的文本片段：

```text
用户原始内容
[表情描述: 开心地挥手，表示赞同]
```

处理顺序建议：

1. 在上下文预处理阶段解析 `sticker` 引用，解析为 `PipelineAttachment` 或可发送的媒体引用。
2. 根据 `inputMode` 和附件策略决定是否向消息文本注入描述。
3. 若注入描述，标记该表情引用已被“描述消费”，但不要因此删除原始媒体，除非最终策略明确选择 `description`。
4. 若最终需要原始媒体，将表情附件保留给 `asset-resolver`。
5. `description` 应在发送前冻结为消息快照，后续用户修改表情库描述不应悄悄改变历史消息含义；重新编辑消息时可提供“同步最新描述”的显式操作。

### 5.3 Token 预览与转写

Token 预览必须走与实际发送相同的表情决策，否则用户会看到预览与实际请求不一致。首版可以按估算规则计算描述文本和图片 token；不能只把所有表情当普通文本字符计数。

表情默认不自动触发 OCR/视觉转写任务。只有以下情况才进入原有转写链路：

- 用户把该表情作为普通图片附件发送；
- 用户在表情设置中明确选择“无描述时允许自动转写”；
- 当前模型/策略明确要求转写且没有用户描述。

## 6. 数据持久化与兼容性

### 6.1 草稿

当前 `ChatInputDraft` 只有文本、附件、临时模型、Knowledge 等字段。建议增加：

```ts
stickerRefs?: MessageStickerRef[];
```

输入框同步状态、分离窗口同步和草稿剪贴板也要同步该字段。不能只依赖文本中的 `stickerId`，否则用户删除占位符后会留下悬挂引用。

### 6.2 消息

建议在 `ChatMessageNode` 增加可选字段：

```ts
stickers?: MessageStickerRef[];
```

为兼容旧消息：

- 没有 `stickers` 字段时按现有 `attachments` 和 `file` 占位符处理；
- 新消息使用 `sticker` 占位符；
- 编辑/导出时同时读取 `stickers` 与占位符，发现不一致时以消息级引用为准并记录诊断日志。

### 6.3 导出与导入

#### 6.3.1 架构解耦原则

**会话（Session）、智能体（Agent）、用户档案（User Profile）是三方完全独立的域。**

- **会话导入导出**：不携带用户档案，也不携带任何表情包物理资源。消息中保存的 `MessageStickerRef` 仅记录 `stickerId`、`localPath`、`providerRef` 和发送时的 `description` 快照。
- **智能体导入导出**：仅携带 Agent 自身的私有资产（Agent Assets），不携带用户的表情包。
- **用户表情包导入导出**：作为用户档案（User Profile）的一部分，其导入导出完全独立，或在未来用户档案整体迁移时跟随。

#### 6.3.2 表情包独立导入导出

用户表情包配置应支持独立导出与导入，采用类似 Agent 资产的打包机制：

- **导出格式**：打包为 `.zip` 文件，其中包含 `manifest.json`（记录表情包元数据、条目索引、描述、别名等）以及对应的图片文件。
- **去重策略**：导入时，根据图片文件的 MD5/SHA256 哈希进行去重。若本地已存在相同图片，则复用本地文件并重新绑定 `localPath`，避免磁盘空间浪费。
- **内置表情**：内置表情只导出稳定 ID（`providerRef`），不重复打包物理图片。

#### 6.3.3 跨设备/缺失资源降级

由于会话导出不携带表情资源，当用户在另一台设备导入会话，或删除了本地表情时：

- **无缝降级**：消息气泡中若检测到本地物理图片缺失，应优雅降级显示：
  1. 优先显示发送时冻结的 `description`（如 `[表情: 流汗黄豆]`）；
  2. 悬停或点击时提示“表情资源已失效或未在当前设备导入”；
  3. 绝不因为资源缺失导致消息渲染崩溃或显示空白。
- **快捷收藏**：如果未来支持了云端或 VCP 远程同步，用户可以点击缺失占位符尝试重新下载或关联。

## 7. 分阶段实施建议

### Phase 0：产品契约与技术骨架

- 确认“表情是附件 + 引用”而不是直接插入 Markdown 图片。
- 确认默认 `inputMode = inherit`，并确定 `both` 是否默认发送描述。
- 定义 `StickerPack`、`StickerItem`、`MessageStickerRef`。
- 定义内置 manifest 格式和用户表情配置文件名。

### Phase 1：可用 MVP

- 用户图片导入、我的表情包、内置表情包。
- 输入框表情按钮、搜索、分类、点击插入。
- 使用 `【sticker::id】` 占位符和 `stickers[]` 消息字段。
- 消息气泡图片展示、删除/编辑消息保留引用。
- 用户描述注入模型；默认继承附件原始媒体/转写策略。
- Token 预览、草稿、分离窗口同步。

### Phase 2：完整管理与质量

- 自定义表情包分组、排序、批量导入、最近使用。
- 表情描述编辑、标签和别名。
- `image / description / both` 单条或全局策略设置。
- 会话/表情包导入导出、缺失资源诊断。
- 统一编辑器行内表情 chip；同时覆盖 CodeMirror 与 textarea。

### Phase 3：来源扩展

- Agent 私有表情包作为可选来源，沿用 `agent-asset://` 的生命周期。
- VCP 表情库作为远程来源，复用现有 `vcpEmoticonService` 和 `emoticonFixer`，增加本地描述覆盖及缓存失效处理。
- 可选地支持收藏远程表情而不复制文件。

- 消息展示：`MessageContent.vue`，以及导出/编辑/分支相关逻辑。
- 资产与配置：新增表情包独立存储服务/类型，不复用全局 `useAssetManager.ts`。
- 文档：LLM Chat 架构、数据持久化、附件/转写说明和用户指南。

## 9. 风险与验收重点

1. **文本与引用不一致**：用户删除 `【sticker::...】` 后，消息仍带有 stickers 引用会导致无意发送。发送前必须根据占位符重新计算“已使用表情”，或明确规定未出现在正文的引用仍属于附件。
2. **编辑器双实现不一致**：不能只在 CodeMirror 支持图片 chip；textarea 是当前兼容路径，MVP 应先用纯文本占位符。
3. **内置资源路径不稳定**：内置表情必须使用 manifest ID，不要把构建目录路径写入会话。
4. **历史语义漂移**：消息必须保存描述快照，不能每次渲染或重放时读取表情库最新描述。
5. **转写策略重复计算**：Token 预览、真实发送、上下文分析必须调用同一决策函数。
6. **分离窗口同步**：新字段必须加入输入状态同步，否则主窗口与悬浮输入区会出现“图片已插入但发送端无引用”。
7. **大图与动图资源**：缩略图、原图、GIF 解码和消息列表销毁时的 URL 生命周期需要单独验证。
8. **外部来源安全**：VCP 远程 URL 必须继续经过现有鉴权修复和来源校验，不应把远程 URL 当作本地 Asset 路径。

## 10. 建议默认值

- 面板入口：输入框工具栏表情按钮。
- 默认分类：最近使用 → 我的表情 → 内置表情。
- 默认插入：当前光标位置；选中文本时替换选区。
- 默认模型策略：`inherit`。
- 有自定义描述且模型支持图片：发送原图 + 描述。
- 模型不支持图片：发送自定义描述；没有描述时才考虑原有转写。
- 用户描述：消息发送时保存快照。
- 内置表情：只读，不自动复制到用户资产库。
- 用户表情：使用当前激活的用户档案目录内（`{currentProfileDir}/stickers/`）存储，支持去重。
- 第一版编辑器表现：可读占位符，不做 contenteditable/行内图片迁移。

## 11. 待确认产品决策

1. 点击内置表情后，是否默认发送图片 + 描述，还是严格继承当前附件策略只二选一？
2. 自定义描述是表情资产的默认描述，还是每次插入都允许临时修改？本方案建议“资产默认描述 + 消息级快照”，后续支持单次覆盖。
3. 未出现在正文中的已插入表情，发送时是否仍作为附件发送？本方案建议只发送正文中实际引用的表情，避免悬挂附件。
4. 用户表情是否需要支持 GIF/WebP 动图？建议 MVP 支持展示和发送，但导入压缩、缩略图和动画预览单独验收。
5. 是否把现有 Agent/VCP 表情库纳入首版面板？建议首版先做内置 + 用户，保留来源适配器接口。

## 12. 表情包资产管理面板设计

### 12.1 面板定位

建议把“表情包管理”做成独立的管理面板/对话框，而不是把所有编辑能力塞进输入框快捷面板。

- 输入框快捷面板：负责快速查找和插入，操作路径短。
- 表情包管理面板：负责导入、分组、描述编辑、排序、批量操作和资源清理。
- 全局 Asset Manager：完全不参与表情包管理，保持职责单一，避免表情包污染用户个人资产库。

推荐入口：

1. 输入框表情面板右上角的“管理”按钮；
2. 设置 → 聊天 → 表情包。

不要让用户必须进入全局 Asset Manager 才能编辑表情描述，因为“图片文件管理”和“聊天语义管理”是两个不同概念。

### 12.2 推荐布局：双栏 + 弹窗详情

同意不采用三栏。表情包管理的核心操作是“浏览、搜索、整理”，详情编辑不是高频操作，长期固定占用右侧空间会压缩图片网格，也会让管理面板显得过重。

建议采用：**左侧分组导航 + 右侧主内容区**。点击卡片后的编辑与预览使用弹窗或抽屉，不常驻第三栏。

```text
┌──────────────────────────────────────────────────────────┐
│ 表情包资产                              [导入] [导出] [×] │
├──────────────┬───────────────────────────────────────────┤
│ 表情包/来源   │ [搜索表情] [类型] [排序] [批量选择]        │
│              │                                           │
│ 最近使用     │  ┌────┐  ┌────┐  ┌────┐  ┌────┐           │
│ 我的表情     │  │图  │  │图  │  │图  │  │图  │           │
│ 内置表情     │  └────┘  └────┘  └────┘  └────┘           │
│ Agent        │                                           │
│ VCP          │  ┌────┐  ┌────┐  ┌────┐  ┌────┐           │
│              │  │图  │  │图  │  │图  │  │图  │           │
│ + 新建分组   │  └────┘  └────┘  └────┘  └────┘           │
└──────────────┴───────────────────────────────────────────┘

点击卡片 → 表情详情弹窗：预览、描述、标签、分组、输入策略、保存/删除
```

这样有几个好处：

- 主区域可以保持足够大的表情网格；
- 用户不会在浏览时被大量详情字段干扰；
- 详情编辑是明确的“进入编辑态”，不容易误触；
- 小窗口可以直接把详情弹窗改成全屏或底部抽屉；
- 与当前 Asset Manager 的侧边栏 + 工具栏 + 网格模式更一致。

### 12.3 左侧导航

左侧导航显示来源与表情包分组，并显示数量：

- 最近使用
- 我的表情
  - 默认表情
  - 用户自定义分组
- 内置表情
  - 内置分组 A
  - 内置分组 B
- Agent 表情（如果当前 Agent 有私有资产）
- VCP 表情（如果已连接并启用）
- 未分组

每个分组支持：

- 新建；
- 重命名；
- 删除空分组；
- 调整排序；
- 设置分组图标；
- 查看分组描述。

内置、Agent 和 VCP 分组应显示来源标记。只读来源不显示删除入口，VCP 分组只允许隐藏或取消收藏，不直接删除远程资源。

### 12.4 顶部工具栏

当前列表顶部建议包含：

- 搜索框：搜索名称、描述、标签、别名和文件名；
- 来源筛选：全部 / 用户 / 内置 / Agent / VCP；
- 类型筛选：静态图片 / GIF / WebP / 其他；
- 排序：最近使用、创建时间、名称、文件大小、手动顺序；
- 视图切换：网格 / 紧凑网格 / 列表；
- 批量选择；
- 导入按钮；
- 导出当前表情包或选中条目。

当前 Asset Manager 已经有搜索、排序、分组、网格大小和批量选择等交互，可以优先复用其视觉和状态模式，而不是重新设计一套完全不同的资产列表。

### 12.5 表情卡片

网格卡片建议包含：

- 图片缩略图；
- 表情名称；
- 描述的单行摘要；
- 来源/只读标记；
- 最近使用标记；
- 选择框；
- 悬停操作：插入、预览、编辑、移动、删除。

卡片默认不显示完整 ID，避免界面被技术字段占满。ID、Asset ID、来源路径等信息放在详情弹窗的“高级信息”区域，并支持复制。

- 右键菜单建议包含：

  - 插入到当前输入框；
  - 编辑描述；
  - 移动到分组；
  - 复制为我的表情；
  - 复制引用 ID；
  - 删除/移出表情包。

“移出表情包”与“删除文件”必须是两个不同操作。对用户资产而言，移出只删除 `StickerItem`，不删除物理文件；删除文件需要二次确认并提示可能影响历史消息。

### 12.6 表情详情弹窗/抽屉

点击或双击一个表情后打开详情弹窗；在窄窗口中使用抽屉或全屏编辑页。详情分为三个区域：

#### 预览区

- 大图预览；
- GIF/WebP 动画预览；
- 原始尺寸、文件大小、格式；
- “在消息中预览”按钮；
- “打开原资产”按钮。

#### 语义信息

- 表情名称：面向用户显示；
- 给模型的描述：核心字段；
- 搜索别名：例如“无语、沉默、汗”；
- 标签：例如“开心”“拒绝”“疑惑”；
- 所属分组；
- 默认模型输入策略：继承 / 原图 / 描述 / 两者。

描述编辑建议使用多行输入框，并给出提示：

> 描述应表达表情的动作、情绪和语气，例如“角色无奈地摊手，表示不理解或不想继续解释”。

不建议默认调用视觉模型自动生成描述。可以提供“生成描述”按钮作为可选能力，但生成结果必须先由用户确认，不能静默覆盖已有描述。

#### 高级信息

- `stickerId`；
- `assetId` 或 `providerRef`；
- 来源；
- 创建时间；
- 使用次数；
- 最近使用时间；
- 是否只读；
- 是否存在缺失资源。

### 12.7 导入流程

点击“导入”后建议支持两种模式：

#### 快速导入

适合输入框内临时添加：

1. 选择一个或多个图片文件；
2. 自动导入 Asset Manager；
3. 自动加入当前用户表情包；
4. 默认名称取文件名；
5. 描述为空，允许稍后补充；
6. 导入完成后自动定位到新条目。

#### 高级导入

适合管理面板批量整理：

- 选择目标分组；
- 是否根据文件名生成名称；
- 是否使用文件名作为初始别名；
- 是否覆盖同名条目；
- 是否尝试生成缩略图；
- 是否在导入后批量编辑描述。

导入时应显示逐项状态：等待、导入中、完成、失败。复用 Asset Manager 现有导入状态，不要在表情层重复实现文件复制逻辑。

### 12.8 批量操作

选中多个表情后显示批量工具条：

- 移动到分组；
- 批量添加标签；
- 批量设置输入策略；
- 批量生成或清空描述；
- 导出选中项；
- 从当前表情包移除；
- 删除对应文件。

“批量删除文件”必须明确显示：

- 仅从表情包移除；
- 同时删除底层资产；
- 历史消息是否仍能显示。

默认只执行“从表情包移除”，避免误删被其他工具或历史会话引用的全局 Asset。

### 12.9 表情包分组编辑

新建/编辑分组对话框建议包含：

- 分组名称；
- 分组 ID；
- 图标：选择首个表情、Emoji 或自定义图片；
- 分组描述；
- 排序权重；
- 是否在输入框快捷面板显示；
- 是否作为默认插入分组。

分组描述主要用于管理和后续模型上下文扩展，不应在每次插入时自动发送给模型。只有表情条目的 `description` 参与单条表情语义注入。

### 12.10 与输入框快捷面板的关系

快捷面板不是管理面板的缩小版。两者职责应保持不同：

| 能力          | 快捷面板       | 管理面板 |
| ------------- | -------------- | -------- |
| 浏览和搜索    | 支持           | 支持     |
| 点击插入      | 核心能力       | 支持     |
| 新建分组      | 不建议         | 支持     |
| 编辑描述      | 可提供快捷入口 | 核心能力 |
| 批量导入      | 简单导入       | 高级导入 |
| 批量移动/删除 | 不建议         | 支持     |
| 文件预览      | 简单预览       | 完整预览 |
| 导出/备份     | 不建议         | 支持     |

快捷面板中建议保留“管理表情包”入口，点击后打开独立管理面板，并在关闭后恢复原输入框焦点。

### 12.11 删除、引用与资源安全

删除操作需要区分三个层级：

1. **从当前分组移除**：只改 `StickerItem`；
2. **从所有表情包移除**：删除表情索引，但保留物理图片文件；
3. **删除底层资产**：由表情包服务直接删除当前用户档案目录下的对应物理图片文件，可能影响历史消息。

建议默认只允许前两种操作。底层资产删除应在表情包管理面板中执行，并展示引用数量和影响范围。

历史消息保存的是 `MessageStickerRef` 快照，因此：

- 删除表情条目不应让历史消息失去描述；
- 删除底层图片后，历史消息显示缺失资源占位；
- 消息中应保留发送时的描述快照；
- 重新添加同名表情不能自动覆盖旧消息引用。

### 12.12 响应式与窗口模式

建议根据容器宽度采用以下布局：

- 宽窗口：左侧分组 + 右侧网格主区域；
- 中等窗口：左侧分组可折叠，详情使用弹窗；
- 输入框弹出面板：仅显示分组标签 + 网格 + 搜索，管理操作跳转独立对话框；
- 分离输入窗口：限制面板最大高度，避免遮挡发送按钮；菜单打开时沿用现有动态调整窗口高度机制。

表情网格建议使用 `grid-template-columns: repeat(auto-fill, minmax(...))`，不要固定列数，以适配不同 DPI、窗口和缩放比例。

建议组件职责如下：

```text

├── StickerManagerDialog.vue       # 完整管理面板
├── StickerPackSidebar.vue         # 分组/来源导航
├── StickerToolbar.vue             # 搜索、筛选、排序、批量操作
├── StickerGrid.vue                # 网格卡片
├── StickerCard.vue                # 单个表情卡片
├── StickerDetailPanel.vue         # 预览与编辑
├── StickerImportDialog.vue        # 导入流程
├── StickerPackEditDialog.vue      # 分组编辑
└── StickerBatchDialog.vue         # 批量操作
```

逻辑层建议拆分为：

```text
src/tools/llm-chat/
├── types/sticker.ts
├── stores/stickerStore.ts
├── services/stickerLibraryService.ts
└── composables/useStickerLibrary.ts
```

其中：

- `stickerLibraryService` 负责配置加载、保存、内置 manifest 合并和迁移；
- `stickerStore` 负责当前面板状态、筛选、选择和最近使用；
- `useStickerLibrary` 负责导入图片、创建条目、移动分组和删除引用；
- 具体图片读取由表情包服务直接处理，不调用 `useAssetManager`。

### 12.14 管理面板 MVP 范围

第一版资产管理面板建议只实现：

- 我的表情 / 内置表情两个来源；
- 分组列表；
- 搜索；
- 网格预览；
- 导入图片；
- 编辑名称、描述和分组；
- 单项删除/移出；
- 批量移动；
- 表情预览；
- 最近使用；
- 缺失资源提示。

以下能力可以后续增加：

- 批量生成描述；
- 表情包导入导出；
- Agent/VCP 来源；
- 远程表情收藏；
- 真正的输入框行内图片编辑；
- 使用次数分析和自动排序。
