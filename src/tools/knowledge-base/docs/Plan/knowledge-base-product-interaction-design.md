## 1. 文档目的

此前 Knowledge 的建设主要由 Recall 领域拆分和现有索引实现反推，已经完成资料库、文档、分块、关键词索引、语义索引、检索测试和来源回溯，但没有先确定一个足以指导后续细节的产品定位。

这导致若干阶段性实现被误当作长期产品决策：

- Knowledge 沿用了 Recall 的绑定、占位符和“缺少宏时保底注入”结构。
- 设置计划从硬编码缺口直接推导出全局设置和单库设置，没有先区分产品配置、查询策略与运行参数。
- “实际向量维度必须可信”被扩大为“不允许用户请求输出维度”。
- Agent 主动检索、用户显式召唤和复杂研究任务没有形成清晰的主次关系。

本方案先定义 Knowledge 是什么、如何被使用、与 Recall 和世界书如何分工，再约束后续工具、交互、设置、摄取和索引设计。

## 2. 产品定义

Knowledge 是 AIO Hub 中面向大型外部资料的本地检索服务：

> 用户把相对稳定、可追溯的成套资料存入资料库；用户或 Agent 在需要时带着明确问题主动查询，并获得可继续阅读、可核对来源的检索结果。

Knowledge 的主要价值不是“自动把相关内容塞进每轮上下文”，而是：

1. 长期管理较大规模的冷资料。
2. 为 Agent 提供稳定、结构化、可授权的查询工具。
3. 允许用户在消息中显式指定资料库并当场发起查询。
4. 对复杂问题提供可升级的多轮检索与证据整理能力。
5. 保留文档、章节、片段和文件路径，使答案能够回到原始资料核验。

### 2.1 “冷数据”的含义

“冷”描述的是数据生命周期和使用方式，不只是创建时间：

- 来源通常是手册、论文、百科、项目文档、代码资料、规则说明、私有档案等外部内容。
- 数据以批量导入、目录同步和低频更新为主，不从每轮会话自动生成。
- 内容规模可以远大于单次上下文，只在明确需要时检索。
- 文档是事实源，chunk、FTS、vector 和 graph 是可重建的派生索引。

刚导入的技术手册仍是 Knowledge；多年以前形成但持续参与人物关系和当前行为判断的经历仍可能是 Recall。冷热不是按时间一刀切。

## 3. 与 Recall、世界书的边界

三者的核心差异是数据来源、触发机制和上下文职责：

| 系统      | 主要数据                               | 触发者                         | 日常交互             | 上下文职责               |
| --------- | -------------------------------------- | ------------------------------ | -------------------- | ------------------------ |
| 世界书    | 人工编排的设定、规则和条件条目         | 关键词、规则、位置和递归扫描   | 配置后按确定规则生效 | 在指定位置注入设定或指令 |
| Recall    | 会话形成的经历、关系、偏好、反思和联想 | 系统根据当前会话和算法自动判断 | 环境式自动召回       | 为当前对话补充长期记忆   |
| Knowledge | 外部文档、资料集和低频更新的冷数据     | 用户显式召唤或 Agent 主动调用  | 目标驱动的按需检索   | 为具体问题提供证据和来源 |

### 3.1 不替代世界书

Knowledge 不负责复刻酒馆世界书的关键词激活、插入位置、递归扫描、常驻条目和概率规则。世界书仍适合：

- 角色与世界观的强约束设定。
- 必须在特定提示词位置生效的规则。
- 由作者精确控制触发条件和注入文本的内容。

RP 场景中的长篇原作、设定集、规则手册、历史资料和参考文献可以进入 Knowledge；需要始终或按规则影响角色行为的精编条目仍应使用世界书。

### 3.2 不复制 Recall 自动召回

Recall 的常态是系统根据会话上下文自动检索。Knowledge 的常态是 Agent 判断“需要查资料”后调用工具，或者用户明确指定资料库发起查询。

Knowledge 可以被 Agent 授权访问，但“有权访问”不等于“每轮自动检索”。没有明确查询意图时，不应产生 Embedding 调用、检索、上下文注入或额外模型费用。

### 3.3 允许显式组合但不混淆领域

复杂任务可以同时使用 Recall 与 Knowledge，例如先从 Recall 获取项目历史，再从 Knowledge 查询技术规范。组合应由 Agent 或上层研究编排器显式执行，不要求底层把两者伪装成一种检索域，也不直接比较两个领域的原始分数。

## 4. 调查结论

### 4.1 市面产品

本轮对照了五类常见产品：

| 类型           | 代表产品                   | 可借鉴点                                     | 不直接复制的部分                            |
| -------------- | -------------------------- | -------------------------------------------- | ------------------------------------------- |
| 来源型笔记本   | NotebookLM                 | 来源优先、引用明确、用户围绕资料提问         | 云端产品边界和生成式内容工作室              |
| 本地资料问答   | Cherry Studio、AnythingLLM | 本地资料管理、对话中按需使用、低门槛主流程   | 把资料库固定绑定为某个 workspace 的唯一形态 |
| 对话平台资产   | Open WebUI                 | Knowledge 作为可复用资产，区分全文与按需检索 | 服务端多用户管理和平台级权限体系            |
| AI 应用数据集  | Dify                       | 元数据、召回测试、应用消费边界               | 面向发布 AI 应用的工作流和团队协作体系      |
| RAG 运维工作台 | RAGFlow                    | 解析结果检查、分块干预、检索质量调试         | 专业 RAG 平台的全部运维复杂度               |

AIO Hub 应采用“本地资料服务 + Agent 工具 + 可检查索引”的组合，而不是完整复制任一产品。

### 4.2 VCPToolBox 冷知识库

VCPToolBox 已把热记忆与冷知识分为平行通道：

```text
热记忆   KnowledgeBaseManager / TagMemo   -> 高频经历与联想
冷知识   TDBKnowledge / TriviumDB          -> 大规模稳定资料
路由层   LightMemo                         -> Agent 主动选择检索通道
```

值得吸收的机制：

- `knowledge/` 一级目录对应一个独立资料库。
- 文件监听后进入带 lease、失败状态和有限重试的持久摄取队列。
- checksum 不变时跳过重复 Embedding。
- document 与 chunk 分层，并建立 `contains`、`next`、`prev` 关系。
- Agent 可通过工具检索全部库或指定库。
- 结果保留资料库、文件路径、chunk 和相关度。
- Rerank、候选数量和父文档展开是查询选项，不是资料库身份。

不应复制的实现：

- 用一个 LightMemo 工具同时承载热记忆和冷知识，导致参数和说明持续膨胀。
- 依赖 `[知识库]` 文本前缀在工具内部再次分流。
- 冷知识占位符重新引入自动上下文注入，与主动工具路径并存但边界不清。
- 通过固定环境变量手工声明向量维度。
- 声明支持 PDF，但摄取实现仍按 UTF-8 文本统一读取。
- 更新文件时先删除旧节点，失败时可能失去旧索引。
- 普通结果只返回 `text_preview`，全文展开又可能一次塞入整个文档。
- `Deep Research` 依赖远端服务前缀，尚未形成可复用的本地多轮研究编排。

## 5. 目标用户任务

Knowledge 需要优先完成以下用户任务：

### 5.1 建立资料馆

用户可以把一套相关资料组织为一个资料库，持续添加、更新和移除来源，并查看当前摄取与索引状态。

### 5.2 当场查询

用户在聊天消息中明确选择一个或多个资料库并提出问题。系统保证执行本次查询，而不是只把库名作为提示交给模型自行猜测。

### 5.3 Agent 自主查证

Agent 获得指定资料库的访问权限后，可以在任务中自行判断何时搜索、何时继续阅读来源、何时停止。未发生工具调用时，Knowledge 不参与本轮上下文。

### 5.4 检查资料质量

用户可以查看解析出的文档、实际 chunk、索引覆盖、失败原因和检索结果，判断问题来自原文、解析、分块、模型还是检索策略。

### 5.5 深度研究

面对跨文档汇总、冲突核对、方案比较和证据链构建等问题，用户或 Agent 可以启动研究任务，由子 Agent 多轮检索和阅读后返回带引用的整理结果。

## 6. 调用模型

Knowledge 提供四个层次的调用方式，按重要性排列如下。

### 6.1 Agent 主动工具调用

这是 Knowledge 最常见、最重要的运行路径：

```text
用户提出任务
  -> Agent 判断需要外部资料
  -> knowledge.search
  -> 根据候选调用 knowledge.read
  -> Agent 基于证据回答
```

工具权限决定 Agent 能访问哪些资料库。资料库内容不应因为已授权而自动进入提示词。

### 6.2 用户显式引用资料库

聊天输入区应提供一个明确的 Knowledge 入口，让用户从可访问资料库中选择目标，并决定执行快速查询还是研究任务。首期入口使用输入框旁的独立按钮与资料库选择器，不依赖用户在文本中输入特殊字符。

当前 Chat 输入框旁的 `@` 快捷按钮已经用于设置会话级模型覆盖，输入框本身也尚未实现基于 `@`、`/` 等字符的触发与候选选择。因此本方案不把 `@` 作为 Knowledge 的产品契约，不复用现有 `@` 按钮，也不假定发送阶段能够从纯文本解析出资料库引用。

用户完成选择后，输入区应显示可移除、可检查的资料库引用标记。该引用在数据层保存为结构化对象，而不是只保存容易因改名失效的显示文本：

```ts
interface KnowledgeReference {
  type: "knowledge";
  libraryIds: string[];
  mode: "search" | "research";
}
```

发送时由运行时把结构化引用转换为明确的 Knowledge 调用：

```text
KnowledgeReference
  -> search: 执行 knowledge.search 并生成可见工具结果
  -> research: 创建 knowledge.research 任务
  -> 将结构化结果交给当前 Agent 继续回答
```

这保证用户显式引用必然生效，同时让聊天入口、Agent 自主调用和工作台检索复用同一服务契约。未来如果 Chat 建立了统一的 mention / command 输入触发基础设施，并解决现有 `@` 模型覆盖入口的交互冲突，可以再把 `@` 或 `/` 增加为同一结构化引用的快捷创建方式；它们不应形成另一套发送与检索协议。

### 6.3 Knowledge 工作台检索

工作台提供直接搜索和检索测试，用于浏览资料和诊断质量。它不依赖某个会话或 Agent，也不需要先建立绑定。

### 6.4 二阶研究任务

复杂问题使用独立的研究编排，而不是让每次普通检索都启动子 Agent：

```text
问题分析
  -> 制定检索子问题
  -> 多库 search
  -> read 命中上下文
  -> 识别证据缺口或冲突
  -> 改写查询并继续检索
  -> 汇总证据
  -> 返回带引用的结论与未解决项
```

研究任务必须有最大轮次、最大工具调用数、证据字符预算、超时、取消和进度状态。普通事实查询继续走一次或少量原子工具调用。

首版采用当前 Agent 编排，不创建隐藏的专用研究 Agent，也不要求额外模板。Knowledge 研究服务负责问题拆分、多轮 `search` / `read`、预算、进度、取消、证据、空缺、潜在冲突和终止原因；结构化结果作为可见工具节点交给当前 Agent 生成最终语言结论。这样沿用用户已选择的模型、参数和权限，成本边界可见；未来若引入专用研究 Agent，必须作为显式可选模板重新评审模型选择、费用和权限继承。

## 7. 占位符与绑定决策

### 7.1 已验证实现

当前实现已经收敛到主动工具语义：

- `{{knowledge_list}}`：在用户放置的位置列出当前 Agent 获授权的资料库目录，不触发检索。
- `knowledge.listLibraries`、`knowledge.search`、`knowledge.read`：通过统一 application service 执行主动查询，并在工具事件中保留来源与策略。
- 用户显式引用：输入区保存结构化 `KnowledgeReference`，发送时执行快速查询或研究任务。
- `knowledgeAccess`：只表达授权范围和能力开关，不表达每轮自动注入配置。

早期开发期的 `{{knowledge}}`、`【knowledge::...】` 和 Knowledge context processor 未随正式版本发布，已从宏注册、预设编辑、上下文管道和文档中移除。

### 7.2 目标语义

Knowledge 的标准运行路径不使用检索占位符或自动注入，但保留用户可编排位置的资料库目录宏：

- 保留 `{{knowledge_list}}`，在用户放置它的预设消息位置展开当前 Agent 可访问的资料库目录；宏本身不执行检索。
- Agent 设置提供独立的 Knowledge 资料访问配置，决定该 Agent 可使用、也可由 `{{knowledge_list}}` 展示的资料库范围。
- 未放置 `{{knowledge_list}}` 时不自动寻找预设位置注入目录；是否常驻、位于哪种角色和哪个注入位置由用户编排。
- 移除生成检索占位符的 `{{knowledge}}`，不再让宏展开结果触发每轮 Knowledge 检索。
- “允许 Agent 访问资料库”只产生访问范围，不产生每轮检索。
- 聊天中的结构化 Knowledge 引用转换为显式工具执行，不转换为隐藏占位符。
- Agent 自主查询使用 Knowledge 工具，不依赖 `{{knowledge}}`。
- Agent 未常驻目录或需要刷新状态时，可以主动调用 `knowledge.listLibraries`。

### 7.3 收敛处理

由于相关检索占位符从未发布，本轮重构不为它们设置运行时兼容期。实施时直接收敛到新的产品契约：

1. 删除 `{{knowledge}}` 以及 `【knowledge::library=...】` 对应的生成、解析、编辑和替换路径；只保留对历史测试输入的“不处理”断言。
2. 删除 `autoInjectIfMacroMissing` 及 Knowledge 自动注入配置，不保留默认关闭但仍可启用的入口。
3. 将资料库绑定模型改为 `knowledgeAccess` 访问授权语义，由 `{{knowledge_list}}` 与 Knowledge 工具共享；strategy、limit、minScore 和 citation 不再作为每个授权库的绑定属性。
4. 保留 `{{knowledge_list}}` 的宏注册、宏选择器入口和预设导入导出语义，改为从访问授权读取并输出紧凑目录。
5. Agent 预设编辑器和说明文档不再暴露 Knowledge 检索占位符格式，但继续允许用户在任意合适的预设消息中放置 `{{knowledge_list}}`。
6. 当前开发环境中由阶段性检索实现产生的测试配置不视为用户数据，可按最终 schema 清理或重建。

`{{knowledge_list}}` 与 `knowledge.listLibraries` 应共享权限校验、资料库摘要格式和可用状态来源，但职责不同：前者由用户控制 Prompt 中的常驻位置，后者是 Agent 按需执行的主动发现工具。工具或动态上下文不能取代宏的预设编排能力。

## 8. Agent 权限与资料范围

### 8.1 授权而非自动绑定

Agent 配置需要表达：

- 是否允许使用 Knowledge 工具。
- 允许访问哪些资料库。
- 未指定资料库时，是否允许搜索全部已授权库。
- 是否允许读取完整文档或只读取命中附近片段。
- 是否允许启动高成本研究任务。

建议的产品语义：

```ts
interface AgentKnowledgeAccess {
  enabled: boolean;
  allowedLibraryIds: string[];
  allowSearchAll: boolean;
  allowDocumentRead: boolean;
  allowResearch: boolean;
}
```

这不是最终代码类型，但后续类型设计必须表达这些权限，不能继续用“绑定即注入”的含义承载。

Agent Manager 的 Knowledge 配置页是这组授权的唯一编辑入口。配置持久化稳定 library ID；宏和工具在运行时根据 ID 解析名称、说明、来源数量和可用状态。资料库改名不改变授权，暂时不可用的库应明确标记，不得从目录中静默消失。

### 8.2 资料库发现

资料库发现提供两种互补方式：

- 预设作者在需要常驻目录的位置放置 `{{knowledge_list}}`，宏在 injection assembler 的宏阶段原位展开。
- Agent 在未获得常驻目录或需要最新状态时调用 `knowledge.listLibraries`。

两者输出同一种紧凑目录：

```text
- 产品文档 (id=...): 安装、配置、迁移和发布说明
- API 规范 (id=...): 接口、错误码和调用示例
```

目录只包含 ID、名称、说明、来源数量和可用状态，不包含 chunk 或全文。

系统不因 Agent 获得资料库权限而自动注入目录。需要常驻目录时，用户应在启用的预设消息中显式放置 `{{knowledge_list}}`，并通过现有预设注入策略决定角色、锚点、深度和顺序。

## 9. 工具能力设计

### 9.1 `knowledge.listLibraries`

用途：发现当前 Agent 可访问的资料库。

返回：

- 稳定 library ID。
- 名称和说明。
- 文档数量与索引状态摘要。
- 支持的检索能力。

### 9.2 `knowledge.search`

用途：执行快速、可重复的资料检索。

建议参数：

```ts
interface KnowledgeToolSearchRequest {
  query: string;
  libraryIds?: string[];
  strategy?: "auto" | "keyword" | "semantic" | "hybrid";
  topK?: number;
  filters?: {
    documentIds?: string[];
    sourceTypes?: string[];
    pathPrefixes?: string[];
  };
}
```

基础工具不要求 Agent 直接操作向量维度、space ID、批次大小和底层融合权重。高级检索调优应进入工作台或受控的高级参数，而不是污染常用工具说明。

返回候选必须结构化：

```ts
interface KnowledgeToolHit {
  libraryId: string;
  documentId: string;
  chunkId: string;
  chunkIndex: number;
  title: string;
  heading?: string;
  sourcePath: string;
  snippet: string;
  score: number;
  signals: string[];
}
```

`score` 保留原始意义并配合 `signals` 解释，不把 BM25、向量和融合分数伪装成统一准确率。

### 9.3 `knowledge.read`

用途：根据检索命中继续读取证据，而不是一次展开整个文档。

建议支持：

- 按 `chunkId` 读取完整 chunk。
- 按 `documentId + chunkIndex` 读取相邻范围。
- 按 heading 或字符范围读取文档局部。
- 显式 `maxChars` 或 token 预算。

返回值继续携带来源定位。普通 Agent 不应默认获得无预算限制的全文读取。

### 9.4 `knowledge.research`

用途：创建多轮资料研究任务。首版可以在独立阶段实现，不阻塞原子检索工具上线。

建议参数：

```ts
interface KnowledgeResearchRequest {
  question: string;
  libraryIds?: string[];
  maxRounds?: number;
  evidenceBudget?: number;
  output?: "brief" | "report" | "comparison";
}
```

返回包括：

- 整理后的结论。
- 引用列表和证据定位。
- 使用过的查询和资料库。
- 发现的冲突、空缺和不确定项。
- 任务耗时、调用轮次和终止原因。

## 10. 检索管线

### 10.1 快速检索

```text
查询与权限校验
  -> 确定资料库范围
  -> keyword / semantic 候选
  -> hybrid 融合
  -> 可选 Rerank
  -> 去重与相邻 chunk 补充
  -> 按字符预算生成结构化命中
```

`auto` 应根据当前资料库实际可用能力选择策略，而不是失败后静默伪装成另一种成功。降级时要在结果 metadata 中说明。

### 10.2 多库检索

多库查询应并行生成候选，并按明确的融合方式合并。不同向量空间可以分别生成查询向量和候选，不能因为模型或维度不同而禁止跨库查询；跨库融合发生在候选排名层，不混用向量。

### 10.3 继续阅读

`search` 负责找到证据位置，`read` 负责读取足够上下文。不要把“返回截断预览”和“展开整篇文件”作为仅有的两个极端。

## 11. 来源与摄取

### 11.1 来源是真源

每个文档必须保留：

- 来源类型。
- 原始路径或稳定来源标识。
- 内容 checksum。
- 解析时间、更新时间和解析器版本。
- 当前摄取状态和最近错误。
- 可回溯到原文的定位信息。

### 11.2 导入方式

按产品优先级支持：

1. 文件选择与多文件拖放。
2. 目录作为持续同步来源。
3. 直接粘贴文本或创建内部资料。
4. URL、网页抓取和其他连接器。

当前阶段可以先完成文件导入，但数据模型和 UI 不应把 Knowledge 永久限制为“选几个文件后一次性入库”。成套文档和目录同步是冷资料场景的重要形态。

### 11.3 可靠摄取

借鉴 VCPToolBox 的有效经验：

- 文件稳定性检查。
- checksum 去重。
- 持久 ingest queue。
- pending、processing、retry、failed、completed 状态。
- lease 恢复和有限重试。
- 文件级失败隔离。

更新文档时，旧文档与旧索引应保留到新解析、分块和基础索引成功提交，不能先删除旧资产再开始可能失败的模型调用。

### 11.4 格式能力

格式支持以“解析器能力”而不是单一扩展名白名单定义：

- 已知二进制格式必须由专用解析器处理。
- 已知文本格式进入文本解析器。
- 未知扩展名可以经过文本/二进制检测后决定是否允许作为通用文本导入。
- 页面显示已验证格式、实验格式和不支持格式。
- 扫描 PDF、图片和 OCR 必须明确标注能力状态。

## 12. 索引与配置分层

### 12.1 系统运行设置

面向整个 Knowledge 服务：

- 默认 Embedding 调用渠道。
- 请求并发、批次和重试。
- 摄取队列并发和资源限制。
- 默认解析与索引预设。

批次大小属于运行性能参数，通常不需要成为每库的常规产品设置。

### 12.2 资料库索引配置

影响资料库派生资产：

- 分块预设或自定义分块参数。
- Embedding 调用渠道。
- 可选的请求输出维度。
- 任务类型与编码契约。
- 是否建立关键词、向量和其他索引。

修改会改变 chunk 或向量空间的配置时，必须明确提示并重建，不得静默让旧索引与新配置混用。

### 12.3 请求维度与实际维度

必须区分：

- `requestedDimensions`：用户或预设传给 Embedding API 的可选请求参数；留空表示模型默认。
- `actualDimensions`：实际响应向量长度，由首批响应确认并写入 space descriptor，只读展示。

用户不能伪造实际维度，但可以在模型支持时请求输出维度。后续查询使用已确认的 descriptor 契约；修改请求维度会产生新空间并要求重建。

### 12.4 Agent 访问策略

属于消费方而不是资料库索引：

- 允许访问的 library ID。
- 是否允许搜索全部授权库。
- 是否允许读取文档。
- 是否允许启动研究任务。

### 12.5 单次查询参数

属于调用行为：

- 查询文本和资料库范围。
- strategy、topK、过滤条件。
- 是否 Rerank、是否扩展邻近 chunk。
- 结果字符预算。

`minScore` 只有在特定策略的分数语义经过标定后才适合作为产品阈值。不能用一个 0 到 1 的共享滑块假设 BM25、向量和混合分数完全等价。

## 13. Knowledge 工作台

工作台面向资料管理和质量检查，不承担 Agent 日常查询的唯一入口。

### 13.1 资料库列表

- 名称、说明和来源数量。
- 摄取、关键词索引和语义索引状态。
- 最近更新与失败数量。
- 新建、重命名、删除和打开来源位置。

### 13.2 资料视图

- 添加文件、目录、文本或其他来源。
- 查看解析状态、checksum、来源路径和错误。
- 文档详情展示实际 chunk，而不是伪造原文件预览。
- 支持重新解析、重新索引和移除来源。

### 13.3 检索视图

- 输入查询并选择单库或多库。
- 展示候选、signals、原始分数和来源。
- 从命中继续读取相邻 chunk 或文档局部。
- 支持比较策略，但不把调试参数全部暴露为常规设置。

### 13.4 索引与诊断

- 当前 Embedding route 和 space descriptor。
- 请求维度与实际维度。
- chunk、FTS 和 vector 覆盖率。
- ingest queue、失败任务和重试。
- 重建影响范围和进度。

## 14. 错误与降级

- 没有语义索引时，关键词检索仍可用。
- `auto` 降级必须标注实际使用的策略。
- 单文件解析失败不回滚同批其他成功文件。
- 自动向量化失败不回滚已经成功保存的文档和关键词索引。
- 更新已有文档失败时继续保留旧的可用版本。
- Agent 请求未授权资料库时返回明确权限错误，不静默搜索其他库。
- 用户显式引用的资料库不可用时必须在发送流程中可见，不把结构化引用当普通文本忽略。
- 研究任务允许取消；失败时保留已收集的证据与失败阶段。

## 15. 实施顺序

### Phase 0：修正产品契约

- 将本方案作为 Knowledge 后续工作的上位依据。
- 暂停按旧设置与导入补完计划直接施工。
- 删除未发布的 `{{knowledge}}`、Knowledge processor 检索替换路径和自动注入配置。
- 将 Agent 资料库绑定直接改为访问授权语义，不为阶段性格式保留迁移分支。
- 保留并重构 `{{knowledge_list}}`，使其从访问授权生成可由用户编排位置的只读资料库目录。
- 同步清理 Agent 预设编辑器和说明文档中的 Knowledge 检索占位符入口。

### Phase 1：建立独立 Knowledge 工具

- 提供 `listLibraries`、`search` 和 `read` 原子能力。
- 工具层执行 Agent 资料库权限校验。
- 返回结构化命中和来源，不只返回拼接文本。
- 保留 Recall / Knowledge 上层组合能力，但不要求 Agent 日常使用 mixed 工具。

### Phase 2：实现用户显式引用

- 在聊天输入框旁增加独立的 Knowledge 引用按钮与资料库选择器，不占用现有会话级模型覆盖的 `@` 按钮。
- 在聊天消息中实现结构化 `KnowledgeReference`，并显示可移除、可检查的引用标记。
- 支持快速查询和研究任务两种 mode。
- 将调用与结果记录为可见工具事件。
- 资料库改名不破坏历史引用的稳定 ID。
- 不以 `@`、`/` 文本触发作为本阶段前置条件；后续如接入统一输入触发基础设施，只创建同一种结构化 `KnowledgeReference`。

### Phase 3：补齐资料工作台与可靠摄取

- 重写设置与导入计划，使其遵循本方案的配置分层。
- 将索引配置和活动向量身份保存在各 library DB，与 chunk、FTS、vector、graph 使用单库 WAL 事务；manifest 只承担目录职责，不依赖 `ATTACH` 跨文件事务保证崩溃原子性。
- 统一文件选择、拖放、解析器能力和错误明细。
- 引入持久 ingest queue 和目录同步来源。
- 完成更新失败保留旧版本的原子替换流程。

### Phase 4：二阶研究

- 建立 Knowledge Research 编排器或专用子 Agent。
- 复用原子工具，不另写一套检索实现。
- 支持多轮查询、证据预算、冲突发现、引用和任务进度。
- 用固定问题集评估研究质量、延迟和成本。

### Phase 5：产品接入收口

- Agent Manager 已统一为“Knowledge 资料访问权限”，编辑、创建和保存入口都写入同一 `knowledgeAccess` 契约。
- Chat、Agent Manager 和 Knowledge 工作台共用授权摘要与 application service；Recall 只在上层显式编排时参与组合。
- 新建、复制、导入和导出的 Agent 配置只保留稳定资料库 ID，不生成阶段性检索占位符或自动注入配置。
- `{{knowledge_list}}` 的预设位置和内容可往返保留，只列当前 Agent 授权目录；宏选择器明确标注“只列目录，不检索”。
- Agent 配置向导、工具说明、上下文管道和用户指南已同步主动工具、显式引用和研究任务语义。

## 16. 验收标准

- 用户和开发者能清楚说明 Recall、世界书和 Knowledge 的触发差异。
- 新 Agent 获得资料库权限后，不会因此在每轮自动执行 Knowledge 检索。
- Agent 预设、导入导出和运行时不再生成或解析 `{{knowledge}}` 与 `【knowledge::...】` 检索占位符。
- `{{knowledge_list}}` 在用户指定的预设位置展开授权资料库目录，不执行检索，宏缺失时系统不保底注入目录。
- Agent 可以通过独立 Knowledge 工具发现、搜索和继续阅读授权资料。
- 用户可以在消息中显式指定资料库，并看到实际执行和引用结果。
- 工作台可以脱离会话管理成套资料、检查 chunk 和测试检索。
- 多库检索不要求各库使用相同向量空间，也不会混用不同空间的向量。
- 请求输出维度可配置，实际响应维度由 descriptor 确认且不可伪造。
- 更新和重建失败不会破坏原有可用文档与索引。
- 复杂研究任务与快速检索分层，普通查询不承担不必要的子 Agent 成本。
- 来源、文档、chunk 和工具调用记录可以形成可核对的证据链。

## 17. 明确不做

- 不替代世界书的规则触发和提示词编排。
- 不把 Knowledge 变成 Recall 的第二套自动召回。
- 不因 Agent 获得访问权限而默认向每轮上下文注入资料。
- 不把 `{{knowledge_list}}` 与 Knowledge 检索占位符混为一类，也不在宏缺失时猜测位置注入资料库目录。
- 不把普通检索强制升级为子 Agent 研究。
- 不在常用工具参数中暴露 space ID、批次大小等底层实现细节。
- 不把不同检索策略的分数伪装成统一准确率。
- 不以实时模型元数据规则覆盖已有资料库的索引契约。
- 不在首期复制 Dify、RAGFlow 的团队发布、工作流编排和平台运维体系。

## 18. 待后续验证

以下项目需要原型或真实使用验证，但不改变本方案的产品边界：

1. Knowledge 独立入口的位置、默认 mode、多库选择方式，以及引用标记在紧凑输入区中的呈现。
2. Chat 未来建立统一 mention / command 输入触发基础设施后，是否需要为 Knowledge 增加 `@` 或 `/` 快捷入口，以及如何避免与会话级模型覆盖交互冲突。
3. Agent 是否需要轻量资料库目录上下文，还是始终先调用 `listLibraries`。
4. `knowledge.read` 的最佳范围表达：chunk 邻域、heading、字符范围或组合方式。
5. 已决定首版使用当前 Agent；专用研究 Agent 或可选模板仅作为未来显式能力评估，不在后台自动切换。
6. 目录同步、URL 来源和内部文本资料的实施优先级。
7. 若未来重新引入显式 `【】` 检索占位符，必须先评审触发方式、权限继承、工具节点可见性、引用追溯，以及与主动 Knowledge 工具的去重和共存；本轮不恢复该路径。
