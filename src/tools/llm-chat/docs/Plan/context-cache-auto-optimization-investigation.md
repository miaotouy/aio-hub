# Chat 缓存友好型上下文组装优化方案（动静分离）

> 日期：2026-10-29  
> 状态：候选设计，已完成既有样例离线回放；在 [变化诊断与缓存用量分析](./context-change-cache-analysis-investigation.md) 之后实施。  
> 范围：桌面端自动工具宏、Recall 自动注入、时间宏，以及相关消息后处理。

## 1. 问题与当前实现

本方案通过减少请求前部的动态变化，延长相邻请求的公共前缀。本地比较提供内容变化证据；服务端缓存是否命中，还需结合渠道能力、缓存配置、有效期和上游 Usage 判断。工具、顶层指令与正文的具体处理顺序由协议适配器决定。

现有代码有以下影响前缀稳定性的行为：

1. **Recall 自动注入可能改写 System 正文**。在 [`insertAutoPlaceholders()`](../../core/context-processors/recall-processor.ts) 中，`context_head` 会向最后一条 System 消息追加占位符；`before_last_user` 在前一条消息恰好为 System 时，也会追加到该消息。召回结果发生变化时，差异会出现在对应的 System 正文内。Recall 的实际执行与结果变化还取决于配置和检索条件。
2. **工具保底宏混合静态说明与动态环境**。[`injection-assembler.ts`](../../core/context-processors/injection-assembler.ts) 的 `auto-tool-macro` 在历史前注入 `{{tools}}\n{{tool_usage}}\n{{tool_context}}`。实时环境变化会改变这条 System；静态说明本身也可能随工具配置、插件定义和协议更新而变化。
3. **System 的最终位置受后处理与协议转换影响**。[`handleMergeSystemToHead()`](../../core/context-processors/message-format-processors.ts) 默认启用，在可合并的 System 多于一条时将其合并至头部；只有一条时保持原数组，带有效回放产物的消息会跳过该合并。随后，Anthropic 适配器将 System / Developer 抽到 `body.system`，Gemini 适配器将其抽到 `body.systemInstruction`。将动态 System 移到消息列表末尾，仍可能在最终请求中回到正文之前。
4. **消息合并与历史处理也会产生差异**。连续同角色合并会扩展旧末条消息；摘要、限长与转写可能改写或移除旧历史。诊断时需要分别解释这些来源。

## 2. 既有样例验证（2026-10-29）

使用已处理的 8 组会话样例，共 361 个消息树节点，经过现有会话加载器、Recall 处理器、角色合并与 Provider 请求构造函数做离线验证。保留历史压缩过滤，关闭 HTML 转写与资源解析；尾部注入使用受控实验实现。

| 观察项 | 结果 | 对方案的约束 |
| --- | --- | --- |
| 相邻用户轮次 | 121 对；受控召回结果变化时，现有头部注入均从首条 System 出现差异 | 动态召回宜后移，收益由最终请求投影确认 |
| 模拟尾部注入 | 差异位置后移，完整消息级追加为 0 / 121 对 | 需明确旧动态块的生命周期，收益限定到动态块之前的前缀 |
| 关闭动态注入的对照 | 5 对发生历史节点移除；另有 6 对原始历史只追加，合并同角色后旧消息被扩展 | 区分历史移除、边界合并和内容改写 |
| 工具结果候选边界 | 长会话 11 个、工具会话 7 个；现有默认配置均转为 User | 定位目标需结合原始节点身份与工具链边界 |
| 首次用户边界的 Recall 注入 | 6 组重现 `before_last_user` 拼接 System；2 组因用户之前已有助手消息而保持独立块 | 拼接取决于相邻角色，不能按“首次用户消息”一概推断 |

样例已移除原始预设、请求参数和服务端 Usage。本轮验证覆盖结构与方案边界，实际缓存读取量留待实发观测。临时探针与详细结果保存在本机忽略目录 `.tmp/context-cache-review/`；上述结论保留在本文，实施时按对应公开行为补充回归用例。

## 3. 缓存优化模式

在 Agent / 会话设置中提供可选的“上下文缓存优化”，默认关闭。关闭时沿用现有角色、位置与正文组装行为，诊断采集照常记录来源；开启后，自动生成的动态块采用下述规则。用户手写预设继续遵循其显式注入配置。

### 3.1. 动态块的载体、位置与生命周期

**载体与信任边界**：自动生成的 Recall 结果和工具运行态使用独立的 User 环境块，例如：

```xml
<runtime-context>
本轮检索结果或工具运行状态
</runtime-context>
```

静态 System 说明该块是供参考的环境数据，并保留工具权限与执行规则。XML 标签只负责分隔正文；角色从 System 改为 User 会改变指令层级，需通过开关和配置说明让用户知晓。

**定位**：复用 [动态消息注入锚点待办](./dynamic-message-injection-anchors-todo.md) 中的定位能力，基于有效会话历史和本次触发节点确定边界，随后再插入动态块。普通用户输入放在本轮输入之前；工具续轮放在完整工具结果组之后；续写需保持末尾助手前缀的协议要求。工具调用与结果配对、媒体块结构均需保留。安全落点无法确定时保留原行为，在分析器中说明原因。

定位时从原始会话节点识别用户和工具结果，避免把转换成 User 的工具消息或其他注入块误认成用户输入。首期桌面端复用公共定位逻辑，移动端按关联待办独立排期。

**生命周期**：首期动态块仅参与当前请求组装，后续请求重新生成。业务会话树继续保存原有用户、助手和工具节点；请求快照保存本次动态块的摘要及来源。由此产生的序列可能为：

```text
上一轮：System → 历史 H → 动态 D1 → 用户 U1
下一轮：System → 历史 H → 用户 U1 → 助手 A1 → 动态 D2 → 用户 U2
```

这类策略保护动态块之前的前缀，上一轮的 `D1` 所在位置仍会发生变化。连续同角色合并后，变化也可能出现在同一条 User 消息内部。若后续需要更长的追加式前缀，应另行设计旧动态块的保留与重放，评估过期信息和上下文增长。

### 3.2. 拆分工具保底宏

在 [`injection-assembler.ts`](../../core/context-processors/injection-assembler.ts) 中保留现有保底触发条件；开启优化后，将自动生成的内容拆成：

- `auto-tool-static`：`{{tools}}\n{{tool_usage}}`，使用 System，放在 `CHAT_HISTORY` 之前。
- `auto-tool-context`：`{{tool_context}}`，仅在展开结果非空时生成，使用 §3.1 的 User 环境块与安全落点。

预设显式使用工具宏时，继续按现有规则处理。静态部分是否稳定，以工具定义、说明及最终 Schema 摘要的比较结果为准；工具开关未变只是其中一个条件。

### 3.3. 调整 Recall 自动注入

在 [`recall-processor.ts`](../../core/context-processors/recall-processor.ts) 中，为自动注入记录 `sourceId: "recall:auto"`，并按集合与出现位置保留子来源，便于定位同一请求中的多个召回片段。

开启优化时，自动注入结果采用 §3.1 的独立 User 环境块，替代拼接到相邻 System 或头部 System 的路径；`context_head` 的运行时落点随优化模式调整，Agent 原始配置继续保留。关闭优化后恢复原配置的组装行为。显式 Recall 占位符保持用户指定的位置与角色。

来源记录应覆盖替换前的占位符及其输出片段，使同一条合并消息中的预设正文、工具宏和 Recall 可以分别归因。

### 3.4. 时间宏窗口对齐

时间对齐作为独立选项提供：实时、10 分钟、30 分钟、1 小时，默认实时。选定时间窗后，同一请求使用一次冻结的有效时间，避免宏展开跨越窗口而产生内部差异。

对齐应用于前部自动说明或预设的时间宏格式化阶段，范围在配置中说明。原始请求时间、节点时间、日志时间和宏执行耗时保留真实值；用户输入与历史正文沿用原文。现有 [`datetime.ts`](../../macro-engine/macros/datetime.ts) 支持虚拟时间，应先计算虚拟时间再按所选粒度对齐展示时间，避免直接修改共享 `macroContext.timestamp` 影响其他宏。

相同时间窗只保证所覆盖时间宏的输出一致，其他动态宏、召回、工具定义及历史处理继续由分析器解释。

## 4. 实施顺序与验证

1. **先完成实发诊断**：按 [变化与缓存分析方案](./context-change-cache-analysis-investigation.md) 采集适配后的请求投影、来源和上游 Usage，建立真实变化记录。
2. **接入安全定位与来源**：复用动态消息锚点的定位逻辑，覆盖普通输入、工具续轮与续写；保留角色转换前的节点身份。
3. **接入优化开关**：拆分自动工具宏，调整 Recall 自动块，关闭状态保持现有输出；随后增加时间对齐选项。
4. **针对行为验证**：复用已有样例检查来源归因、角色与位置、工具链结构以及消息内部前缀；前端实现时按项目要求执行类型检查、Vite 构建和真实窗口走查。缓存收益通过服务端读写量与本地变化记录一起评估。

首期聚焦自动生成的内容。手写混合预设继续按原文展开；工具定义由现有发现与配置流程管理。后续是否扩展动态块重放或工具工作集固定，根据实发诊断结果决定。
