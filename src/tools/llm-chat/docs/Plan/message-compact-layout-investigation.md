# Chat 连续紧凑消息模式：结构评估

> 日期：2026-10-31  
> 范围：桌面 chat 消息列表、工具消息、操作栏、统计、滚动测高与截图。本文保留实施前的结构评估；首版连续紧凑布局已落地，实际文件与验证见[实施记录](./message-list-ui-architecture-proposal.md#13-首版实施记录2026-10-31)。

后续调查见[本机同类项目对比](./message-compact-layout-comparative-research.md)：连续角色共享头栏与过程折叠适合分开设计。补查 DSH 后，独立回合尾栏、正文保留策略和多请求用量累计有了更直接的参考；OpenCode 提供显式展示行投影，assistant-ui 保留合并展示到原消息的回溯映射。首版仍建议保留当前逐消息行壳。


架构细化见[消息列表 UI 架构优化探索](./message-list-ui-architecture-proposal.md)：明确展示组与请求回合的区别、共用消息行和操作上下文、统计口径、测高失效与截图局部选区。本轮补查发现仓库已有可选的 request / attempt 快照，可辅助用量去重；其记录可关闭或裁剪，布局与累计完整度需分别处理。

## 1. 结论

可以增加连续紧凑模式。现有消息树和逐节点执行机制适合保留，展示层需要一次局部整理。

主要债务集中在消息行编排、跨组件样式、统计渲染和截图布局复制。直接在现有模板追加分组条件，会进一步放大这些耦合。建议先收敛消息行入口与统计边界，再接入连续紧凑展示。

推荐保持每个原始消息节点及其直属 `.message-slot`，通过展示投影为每行补充组首、组中、组尾信息。连续的 assistant / tool 行视觉上组成一个角色区块，组首展示身份，组尾展示汇总；编辑、分支与工具结果继续定位到原节点。

### 2.1 消息行编排重复

`MessageList.vue:716–829` 为外置头栏路径，`946–1039` 为普通 ChatMessage 路径。两边分别绑定编辑、重试、分支、翻译等操作；工具消息还有独立分支。

增加组首身份、组尾统计和紧凑操作栏后，这些路径需要同时维护。适合提取一个消息行组件，统一节点参数、展示参数和事件转发；会话写操作继续经过列表已有的只读与作用域保护。

### 2.2 外观规则跨越组件内部

`MessageList.vue` 有 32 处 `:deep(`，涉及消息表面、头部镜像、工具卡片、统计和悬停操作栏。头像位置、头部位置和左右对齐已经形成多个组合。

`ScreenshotRenderer.vue:644–648` 明确说明需要复制列表的气泡布局规则。新增模式若继续分别加样式，聊天与截图的同步负担会增加。

建议收敛消息行布局与外观样式的共享入口。滚动容器专属规则继续留在列表；截图保留自己的导出元素开关。

### 2.3 统计与可行动错误共用容器

`MessageContent.vue:1062–1153` 计算统计与元信息可见性，`1517–1604` 将字数、Token、速度、TTFT、耗时、错误和空响应诊断放进 `.message-meta`。

`ToolCallMessage.vue:1352–1367` 另有一套 usage 与错误展示。

因此，中间节点整体隐藏 `.message-meta` 会一起隐藏错误与诊断。应拆分普通统计与可行动信息：普通统计受展示策略控制，错误、诊断和工具待处理状态留在对应段落附近。

### 2.4 操作栏已有可复用基础

`config/messageToolbar.ts` 默认固定复制、编辑、重新生成，其他动作进入更多菜单；`MessageMenubar.vue:397–424` 已统一计算可用动作与显示分区。

进一步收缩只需增加集中定义的展示策略，例如中间段显示复制与更多，组尾提供常用操作。展开全部与自定义入口可以移入更多菜单，保留现有偏好。具体常用操作数量在界面走查时确定。

紧凑模式的展示覆盖应与用户已保存的固定动作偏好分离。原有动作注册、生成中可用性与预设限制继续复用。

普通消息和工具消息分别有悬停工具栏 CSS，工具消息折叠后还会切换为绝对定位。只缩小按钮尺寸无法收敛这部分差异。

## 3. 需要保留的结构边界

### 3.1 行测量保留直属行壳，导航单独投影

- `MessageList.vue:326–329` 通过消息数组索引访问容器的 `children[index]`。
- `MessageList.vue:410–429` 对直属子元素二分查找，并将索引映射回原消息。
- `useMessageReadingArea.ts:40–75` 通过直属行壳判定预热区，内容注册时寻找最近的 `.message-slot`。
- `useMessageHeights.ts` 为每行维护尺寸缓存、实测与占位。
- `MessageList.vue:1082–1095` 的屏外渲染规则依赖直属行壳与最后一行。

整轮只渲染一个大行壳，会改变上述索引与尺寸契约，也会扩大长工具循环的屏外渲染粒度。当前需求可以通过相邻行的间距、表面、头尾可见性形成视觉分组。保留行壳是当前测高与阅读锚定的实现选择。

2026-10-31 主人明确导航可以改：合并模式按用户提问 / 已合并用户消息组生成导航点，AI 和工具循环映射到所属提问点。导航点与物理行分别建模；搜索、错误和分支仍可精确跳到源节点。方案见[用户提问点导航](./message-list-ui-architecture-proposal.md#91-合并模式按用户提问点导航)。

首版保留逐行结构后，滚动时组首头栏可能离开视口；若后续需要整组吸附头栏，再单独设计。

### 3.2 行高缓存需要感知分组位置

`useMessageHeights.ts:141–150` 的外观采样分类包含角色、身份和 usage 等信息；`199–242` 的普通文本估高计入现有头部占用。`355–389` 的修订监听主要来自当前消息自身。

新增尾段可能使上一条消息失去统计，删除或切换分支也可能改变相邻行的组首、组尾身份，而这些消息的正文与元数据可能完全没变。

需要让行绑定、修订与外观采样识别分组展示上下文，区分带头、无头、带汇总等高度；切换模式时沿用现有阅读锚点机制校准。仅新增全局设置指纹无法覆盖追加消息引起的局部分组变化。

### 3.3 展示归组与节点操作分别定义

消息树、编辑、删除、禁用、重新生成和分支切换继续针对原始节点。中间段保留低干扰的局部操作入口与分支入口。

组尾若出现“复制整组”等操作，应明确其范围。现有 `MessageMenubar` 接收的是单个消息，将它直接挂到组尾并标成整组操作，容易产生操作对象歧义。

### 3.4 身份与状态分别处理

`MessageHeader.vue` 同时显示身份、模型渠道、时间和当前节点状态。组首节点完成后，后续工具和 assistant 仍可能执行。

共享头栏需从组内活动节点派生执行状态，身份使用归组后的角色信息。工具审批、错误和重试等操作仍绑定各自节点。模型或渠道变化应保留可查看的局部标记，或采用保守的切组策略。

## 4. 推荐展示投影

增加独立的分组计算，输出与原消息一一对应的展示描述，例如：

```ts
interface MessageRowPresentation {
  groupId: string;
  position: "single" | "first" | "middle" | "last";
  showIdentity: boolean;
  statsPlacement: "inline" | "group-footer" | "hidden";
  toolbarVariant: "standard" | "compact";
}
```

组摘要单独按 groupId 保存成员 ID、活动状态和统计。groupId 优先使用组首消息 ID，追加后续段时保持稳定。

分组计算只依赖路径结构、角色、身份和分组标记，避免每个流式字符到达都重算整条消息路径。正文、编辑器与现有流源继续按消息 ID 工作。

### 建议的首版归组规则

1. 从 assistant 开始，将身份可确认一致的后续 assistant / tool 连续段归到同组。
2. 用户、系统、压缩节点和预设展示节点形成边界；来源变化时重新判断身份。
3. 工具归属优先结合父子关系、请求关联和 agent 身份；孤立工具节点保留独立展示。显式知识引用可能形成 user → tool → assistant，不能预设所有 tool 都属于前一个 assistant。
4. 旧数据缺少身份或关联信息时保守切组。启用、禁用和压缩状态仍逐段表达。
5. 分支切换后从当前展示路径重新派生分组。

当前本地循环由 `useToolCallOrchestrator.ts:231–250` 创建 tool 子节点，再于 `422–449` 创建后续 assistant 节点。VCP 拆分具有 `metadata.vcpResponse.requestId`，可提供明确关联。当前消息类型中尚无覆盖本地循环、续写和重试的统一回合 ID，因此首版宜称“连续角色分组”，归组结果作为临时展示数据。

## 5. 统计如何收在结尾

建议组尾显示一行摘要，按需展开逐段明细：

- 字数：汇总组内 assistant 正文，工具结果单独计量。
- Token：区分各次请求 usage 与可见正文的 contentTokens。请求总用量可以相加，但应标明请求累计口径；后续请求会再次携带历史上下文。
- VCP：遵循现有逐 assistant 段 usage 归属，聚合前确认来源与请求范围，防止重复计量。
- 总耗时：有足够时间信息时使用组内起止时间跨度，包含工具等待；模型生成耗时可作为独立明细。
- TTFT 和生成速度：优先保留逐请求明细，组摘要采用明确命名的口径。各段 t/s 的简单平均缺乏稳定意义。
- 缺少的数据保留缺失状态，避免显示成零。

错误和空响应诊断继续在原段落展示，普通统计再按组尾策略折叠。

## 6. 建议实施顺序

1. **收敛消息行入口**：统一两套 ChatMessage 参数与事件绑定，保持现有显示行为；梳理主列表和截图共享的布局样式。
2. **拆开统计与错误**：提取统计计算和展示边界，让普通消息与工具消息使用一致策略。
3. **加入展示投影与测高上下文**：派生归组信息，保留逐节点行壳，接入组首头栏与组尾摘要。
4. **完成紧凑外观与操作栏**：集中定义紧凑展示策略，首版固定布局规则，控制与气泡头像位置、左右镜像等选项的组合范围。

工作量属于中等规模前端改造。局部整理足以支撑该需求，消息执行管线、树形持久化与整个工具结果组件可以继续沿用。

后续验证重点放在真实行为：身份或特殊节点能否正确切组；追加、删除和分支切换后是否保持阅读位置与操作目标；usage 聚合是否重复计量；只读与截图是否沿用展示规则。现有工具栏、行高和滚动测试可复用，新增用例围绕这些具体回归点选择。
