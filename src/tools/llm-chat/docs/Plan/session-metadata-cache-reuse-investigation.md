# 会话标题与标签的主请求缓存复用调研

> 日期：2026-11-02
> 状态：调研记录，方案待实施；字段名与设置布局为建议。
> 范围：桌面端 `llm-chat` 的话题命名、持续标题更新、可选会话标签，以及共享模型元数据和缓存用量适配。

## 1. 需求与当前结论

现有话题命名功能继续保留。新增一种可选策略：在主会话完成回复后，沿用本轮实际使用的模型、渠道与请求上下文，末尾追加标题更新指令，再发起一次独立辅助请求。通过复用主请求前缀，争取按缓存读取价格处理大部分输入。

主人提出的主要收益是成本：DeepSeek 的缓存读取价格足够低，完整复用较长主会话，可能比提取少量消息并重新组装命名上下文更便宜，同时提供更完整的主题依据。

已明确的方向：

- 增加可选开关，保留现有命名方式。
- 研究模型缓存能力元数据，用于判断复用模式是否适用；功能启用仍由主人选择。
- 优先评估 DeepSeek 自动缓存场景。
- 顺带研究持续标题更新与会话标签，允许将两类信息合并在一次辅助请求中生成。

请求构造方式、持续更新策略与标签范围属于不同设置维度。首版具体范围仍需在实施时确定。

## 2. DeepSeek 缓存规则与价格依据

### 2.1. 核实来源

2026-11-02 读取 DeepSeek 官方中文文档，价格与主人提供的截图一致：

- [模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)
- [上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache)

以下金额单位均为人民币元 / 百万 tokens，属于本次调研的价格快照。实际计费以请求时的渠道报价为准。

| 模型 | 时段 | 缓存命中输入 | 缓存未命中输入 | 输出 | 未命中 / 命中输入价 |
| --- | --- | ---: | ---: | ---: | ---: |
| `deepseek-flash` | 空闲 | 0.02 | 1 | 4 | 50 倍 |
| `deepseek-flash` | 高峰 | 0.04 | 2 | 8 | 50 倍 |
| `deepseek-v4-pro` | 空闲 | 0.15 | 4.5 | 13.5 | 30 倍 |
| `deepseek-v4-pro` | 高峰 | 0.30 | 9 | 27 | 30 倍 |

官方当前定义的高峰时段为北京时间周一至周五（中国法定节假日除外）09:00–12:00、14:00–18:00，其余时段为空闲时段。

### 2.2. 命中前提

按本次读取的官方规则：

- 硬盘缓存默认开启，每次请求会触发缓存构建。
- 命中要求完整匹配已落盘的缓存前缀单元。
- 用户输入结束位置与模型输出结束位置会形成缓存前缀单元；公共前缀检测与长序列固定 token 间隔也会形成前缀单元。
- 缓存构建为秒级，系统按尽力而为方式工作；保留时间通常为数小时至数天。
- 返回的 `usage.prompt_cache_hit_tokens`、`usage.prompt_cache_miss_tokens` 用于报告实际命中与未命中输入量。

因此，“主请求已完成”提供了复用机会，实际命中量仍需从辅助请求的服务端 Usage 获取。客户端公共前缀长度只用于诊断。

### 2.3. 成本对比

设 `H` 为命中输入量、`U` 为未命中输入量、`O` 为输出量，`Ph`、`Pu`、`Po` 为对应每百万 tokens 单价：

```text
单次请求费用 = (H × Ph + U × Pu + O × Po) / 1,000,000
```

使用同一模型、同一时段，先单独比较上下文输入部分：

| 假设场景 | Flash 空闲 | Pro 空闲 |
| --- | ---: | ---: |
| 100,000 tokens 主上下文全部命中缓存 | ¥0.002 | ¥0.015 |
| 4,000 tokens 重新组装上下文全部未命中 | ¥0.004 | ¥0.018 |

这是用于说明价格关系的假设示例，4,000 tokens 并非当前命名器的固定输入量。新增标题指令、当前回复中未命中的部分以及输出，均需另计。

同模型下，Flash 的 100,000 tokens 缓存读取费用相当于 2,000 tokens 未命中输入；Pro 相当于约 3,333 tokens。高峰时段金额翻倍，比例相同。

收益对命中率敏感。例如 Flash 的 100,000 tokens 上下文，有 98,000 命中、2,000 未命中时，上下文输入费用为 ¥0.00396，已接近上述普通路径的 ¥0.004。该示例尚未计入新增指令和输出差异。

实际评估应比较两条路径的完整费用：

- 普通命名请求也可能命中自身的固定前缀。
- 独立命名模型可能采用另一套价格。
- 思考、输出长度与额外重试可能超过输入节省的金额。
- 中转服务的价格和缓存策略以实际渠道为准。

价格快照用于解释方案价值，运行策略应依赖主人配置和实际能力；自动成本路由可另行研究。

## 4. 建议的请求复用方式

### 4.1. 生命周期

```text
主请求实际执行上下文 P
  → 主回复 A 完成，工具调用循环结束
  → 根据开关、缓存能力、命名触发条件决定是否发起辅助请求
  → 在保留 P 前缀的基础上，按协议追加 A 与元数据指令 M
  → 解析标题 / 标签，校验任务所属会话与分支，再持久化
```

- `P` 采用本轮实际发送的处理结果，包含影响前缀的顶层指令、工具定义、消息及媒体结构。
- 已执行的宏、时间注入、检索和压缩结果沿用本轮值；辅助请求直接使用临时复用数据，避免再次运行上下文管道造成变化。
- `A` 的追加需使用协议允许的完整助手表示。媒体、思考字段、原生工具结构和续写标记的处理需要在适配层核实。
- `M` 携带当前标题、已启用的元数据任务及必要约束，放在可安全追加的末尾位置。
- 辅助请求与结果独立于主消息树，避免标题指令进入后续聊天历史。
- 临时数据随本轮任务结束释放；多会话并发按会话、分支和请求标识隔离。

### 4.2. 请求边界

`messagesForRequest` 是已有的可利用入口，但仅保留它还无法证明适配后的完整前缀一致。实施时需核对 Provider 对消息合并、工具定义、顶层指令与结构化输出的转换。

尤其需要确认：

1. 更改 `responseFormat`、关闭思考、调整工具调用策略时，服务端缓存前缀会发生什么变化。
2. 主回复追加后能否复用模型输出结束位置的缓存；思考和工具结构是否需要特殊处理。
3. 原生工具定义如何保留前缀，同时让辅助请求只产出元数据。辅助流程应禁用本地工具编排，并妥善处理意外工具调用。
4. 主会话角色提示可能影响元数据输出，末尾指令与现有解析策略的成功率需要实测。

对于虚拟渠道，辅助请求应通过渠道管理提供的继承或执行关联机制复用最终成功目标。下游只表达复用意图，候选选择和回退仍由渠道管理负责。逻辑模型相同、实际成员不同会影响缓存收益。

参考：[虚拟渠道组合与统一模型回退实施方案](../../../../../docs/Plan/llm-virtual-channel-investigation.md)。

### 4.3. 异常与并发

- 主回复正常结束后执行辅助任务，失败时保留当前标题和标签。
- 辅助任务设置独立取消和输出预算，避免阻塞聊天输入。
- 写回前检查会话仍存在、目标分支及标题来源仍匹配；主人在请求期间手动改名时优先保留手动结果。
- 自动压缩可能与主请求收尾并行，复用数据应固定到本轮执行结果。
- 复用信息缺失或能力未知时，自动任务建议跳过本轮复用；手动入口可提供现有命名方式。具体回退行为在实施时确定，避免隐式重复请求。
- 缓存未命中通常在请求完成后才能确认，已发生费用无法撤回；命中不足可用于调整后续行为。

## 5. 模型能力与设置建议

缓存能力建议区分机制，初步可表达为：

| 建议值 | 用途 |
| --- | --- |
| 自动缓存 | 首期复用模式的主要适用对象 |
| 显式缓存 | 预留给需要缓存资源或缓存标记的协议，接入相应机制后再启用 |
| 未支持 / 未知 | 保持普通命名策略，允许主人补充准确配置 |

字段名、枚举及所在层级待定。模型能力用于说明支持方式，缓存命中量由服务端报告，渠道价格用于成本计算，各自保持独立。

模型元数据沿用项目现有流程：创建、导入、刷新或显式应用预设时固化到模型对象，运行时读取已存能力；缓存规则也需覆盖预设应用、导入导出和编辑入口。渠道适用性需结合实际执行目标核对。

设置建议分为三个维度：

- **复用主会话上下文**：默认关闭，开启后使用本轮模型和请求上下文；现有独立命名配置继续保存。
- **随对话更新标题**：与初次命名独立，可设置更新间隔，允许输出沿用当前标题；具体节奏待定。
- **生成会话标签**：独立选择，开启后与标题合并请求。

持续更新应记录自动 / 手动标题来源，并提供恢复自动更新入口。现有会话的标题来源迁移策略需谨慎确定。

## 6. 会话标签扩展

目前属于研究项，首版是否包含标签待定。候选返回结构示例：

```json
{
  "title": "渠道回退策略调整",
  "tags": ["渠道管理", "故障排查"]
}
```

可通过返回当前标题表达保持名称。请求只生成已启用的字段，标签数量和长度设置小范围上限。

标签实施前需要明确：

- 手动标签与自动标签的来源记录、合并及删除规则。
- 标签同义词、大小写和重复项归一化。
- 采用自由标签还是已有标签词表，以及列表筛选入口。
- 索引持久化、导入导出及旧数据兼容。
- 元数据请求的分支归属，切换分支时如何影响会话级标签。

## 7. 后续实施建议

建议先完成最小可用路径，再确定标签规模：

1. 定义缓存能力和设置，沿用现有元数据固化流程。
2. 在共享请求边界提供临时复用信息，并将最终成功请求的关联传到命名流程。
3. 实现主上下文命名路径，保留普通命名路径与现有解析能力。
4. 补充 DS 缓存 Usage 归一化，复用现有分析设施查看实际命中与输出量。
5. 按确定的产品范围加入持续更新、标题来源；标签可复用相同请求通道。

实施前重点确认四项：适配后前缀一致性、辅助输出参数对缓存的影响、虚拟渠道执行目标继承，以及接近主请求结束时的实际缓存命中表现。当前尚未进行真实计费请求或命中率测量。
