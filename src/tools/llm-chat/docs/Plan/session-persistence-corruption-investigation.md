# LLM Chat 会话持久化损坏与启动阻塞调查

> **状态**：调查完成，待确认施工
>
> **调查日期**：2026-07-24 至 2026-07-25
>
> **影响范围**：桌面端 `llm-chat` 会话文件、会话索引、启动加载与索引自愈
>
> **不在本轮范围**：移动端 SQLite 会话存储、代码修改、用户数据清理

## 1. 结论

本次日志已经证实：`llm-chat/sessions-index.json` 和一个会话 JSON 曾被 NUL（`\u0000`）字节污染。索引解析失败后，通用 `ConfigManager` 返回默认空索引；会话存储随后把目录中的 2061 个会话文件全部视为新增文件，逐个读取并重建索引。该恢复路径在骨架屏期间执行，直接造成重新打开界面时长时间等待，严重时表现为无法进入。

故障不是单个坏会话造成的孤立问题，而是以下机制叠加的结果：

1. 会话文件和索引文件均使用 `writeTextFile()` 直接覆盖，没有临时文件、原子替换或最后一份有效备份。
2. 会话持久化由调用方 fire-and-forget 触发，没有按会话文件和索引文件串行化；流式生成、结束保存、标题更新等入口可以重叠。
3. 每次会话保存都会重新读取并完整写回整个索引，当前索引约 660 KiB。
4. 索引解析失败被降级为空配置，调用方无法区分“首次使用”与“已有索引损坏”。
5. 空索引恢复会在首屏加载路径中串行读取全部会话，没有进度、超时、并发上限或可交互的降级界面。
6. 正常启动 3 秒后仍会无条件运行一次全量 `repairIndex()`，再次顺序读取所有会话。

当前损坏会话已由用户手动删除，现有索引和会话文件均可解析，但上述触发条件仍然存在，问题可以复发。

## 3. 当前实现分析

### 3.1 会话和索引直接覆盖

[`saveSession()`](../../composables/storage/useChatStorageSeparated.ts) 直接把序列化结果写到正式会话路径。索引由 [`ConfigManager.save()`](../../../../utils/configManager.ts) 以相同方式直接覆盖。两条路径都缺少：

- 同目录临时文件；
- 写入完成后的内容校验；
- 原子替换；
- 上一份有效文件备份；
- 写入修订号或过期写拦截。

一旦写入中断，正式路径可以留下截断内容或 NUL 区域，下次加载没有可回退版本。

### 3.2 持久化没有单写者

[`useSessionManager.persistSession()`](../../composables/session/useSessionManager.ts) 调用存储 Promise 后立即返回，只在 `.catch()` 中记录错误。模块内有大量直接调用点，涵盖流式响应、工具调用、图操作、撤销重做、标题生成和生命周期操作。

[`persistSession()`](../../composables/storage/useChatStorageSeparated.ts) 每次执行以下读改写流程：

1. 强制覆盖会话文件；
2. 重新读取完整索引；
3. 修改一个索引项与 `currentSessionId`；
4. 覆盖完整索引。

多个调用重叠时，不仅会同时写同一文件，还可能各自基于旧索引计算结果，产生后完成的旧快照覆盖新快照、索引字段丢失和 `currentSessionId` 回退。

### 3.3 损坏索引被当作空索引

[`ConfigManager.load()`](../../../../utils/configManager.ts) 捕获解析异常后返回 `createDefault()`，没有把“文件存在但损坏”传递给领域调用方。

随后 [`loadSessionsIndex()`](../../composables/storage/useChatStorageSeparated.ts) 调用 `syncIndex()`。由于默认索引没有任何条目，目录内所有文件都进入 `newIds`，并在 `for ... of` 中逐个 `await loadSession(id)`。这段工作发生在 [`LlmChat.vue`](../../LlmChat.vue) 的首屏 `Promise.all()` 内，完成前骨架屏不会退出。

### 3.4 索引损坏还会造成不可恢复的元数据丢失

会话文件保存时会显式移除 `isFavorite` 和 `favoriteFolderId`，收藏文件夹也只存在于索引。`currentSessionId` 同样只存在于索引。因此当损坏索引被替换为空索引并从会话文件重建时，以下信息无法恢复：

- 当前选中的会话；
- 会话收藏状态；
- 会话所属收藏文件夹；
- 收藏文件夹定义与顺序。

这意味着当前恢复路径不只是性能问题，也可能静默丢失用户组织信息。

### 3.5 无条件全量自愈放大正常启动成本

[`sessionLifecycleManager.loadSessions()`](../../stores/session/sessionLifecycleManager.ts) 在正常加载结束 3 秒后无条件执行 `repairIndex()`。后者顺序加载并解析全部会话，用于重算 `messageCount` 和 `displayAgentId`。

在当前 2061 个文件、约 144.5 MiB 的数据规模下，这会在界面出现后再次制造大量 IPC、磁盘读取和 JSON 解析压力。它与“索引损坏时的阻塞重建”是两个独立问题，不能只修复损坏恢复而保留每次启动的全量扫描。

## 4. 风险分级

| 级别 | 风险                                 | 影响                                                   |
| ---- | ------------------------------------ | ------------------------------------------------------ |
| P0   | 正式文件直接覆盖且存在并发写         | 会话或索引损坏，可能丢失最近内容                       |
| P0   | 损坏索引静默降级为空索引             | 首屏读取全部会话，长时间卡住；收藏与当前会话元数据丢失 |
| P1   | 每次会话保存重写完整索引             | 高频 I/O、竞争窗口扩大、写放大随会话数增长             |
| P1   | 启动后无条件全量 `repairIndex()`     | 正常启动后仍可能卡顿，规模越大越严重                   |
| P1   | 损坏会话只被跳过，没有隔离与恢复入口 | 文件持续留在目录时，每次同步都会再次尝试解析           |
| P2   | 日志缺少写入事务标识和修订号         | 难以确认是哪一次写入、退出还是竞态导致损坏             |

## 5. 建议实施方案

### Phase 0：先阻止再次损坏

1. 为 llm-chat 建立领域专用的会话持久化协调器，所有会话文件按 `sessionId` 串行，索引文件全局单写者。
2. 同一会话的高频保存使用“运行中保留一次、等待中只保留最新快照”的合并策略，避免无限排队，也避免旧快照后完成覆盖新快照。
3. 会话与索引改为同目录临时文件写入，完成序列化、写入和 JSON/关键字段校验后再替换正式文件。
4. 索引至少保留一份最后有效备份；正式索引替换成功后才更新备份状态。
5. 只有会话文件提交成功后才提交对应索引元数据，失败时保留旧会话和旧索引。
6. 不再让每次流式增量保存都独立执行一次完整索引读改写；索引更新由内存中的单一状态源合并并降频提交。

`sessions-index.json` 已经是高频、大列表、需要一致性和恢复语义的领域索引，不符合普通扁平配置的适用边界。建议从 `ConfigManager` 中迁出该索引，而不是直接给通用配置管理器加入 llm-chat 特有的事务逻辑。

### Phase 1：让损坏恢复不阻塞首屏

1. 明确区分“文件不存在”“内容损坏”“版本不兼容”和“读取失败”，不得统一返回默认空索引。
2. 索引损坏时先读取最后有效备份；备份可用时直接启动，并在后台核对目录差异。
3. 主索引与备份均不可用时，先进入可交互的降级界面，再后台重建索引；展示进度和失败数量，允许用户离开工具。
4. 重建使用有上限的并发读取或分批 idle 调度，不能在首屏串行读取全部文件。
5. 无法解析的会话进入可恢复的隔离清单，保留原文件，不应静默删除；后续启动不再反复解析同一坏文件。
6. 恢复完成前不要用默认空索引覆盖损坏文件；先保留故障样本和最后有效备份。
7. 如果收藏等索引专属元数据确实无法恢复，必须向用户明确说明，而不是静默归零。

### Phase 2：移除无条件全量扫描

1. 删除每次启动 3 秒后的无条件 `repairIndex()`。
2. 仅在索引版本迁移、检测到目录差异、显式手动修复或诊断模式下执行全量检查。
3. 普通启动只加载索引和当前会话；目录同步保持轻量，并记录文件大小、修改时间或索引修订号以支持增量核对。
4. 手动修复提供进度、取消和失败报告，不占用首屏初始化 Promise。

### Phase 3：评估长期存储演进

当前桌面端已经达到两千余会话和百 MiB 级数据，JSON 文件 + 单个全量索引会继续放大写入和恢复成本。完成 Phase 0 至 Phase 2 后，再独立评估桌面端是否迁移到 SQLite 或日志式索引。长期方案不能阻塞眼前的原子写与恢复修复。

## 7. 验收与测试建议

### 7.1 自动化故障注入

至少覆盖：

1. 同一会话连续触发多次保存，最终磁盘内容必须是最新修订，且同一路径最大并发写入数为 1。
2. 不同会话并发保存时，索引不丢条目、不回退 `currentSessionId`。
3. 在临时文件写入、校验、正式替换各阶段注入异常，旧正式文件始终可读取。
4. 主索引为截断 JSON、全 NUL、部分 NUL、空文件时，优先恢复备份且不写入空索引。
5. 主索引和备份同时损坏时，首屏仍可交互，后台重建可报告进度并跳过坏会话。
6. 坏会话被隔离后，下一次启动不再重复解析。
7. 收藏、收藏文件夹和当前会话在主索引损坏但备份有效时保持不变。
8. 保存过程中模拟窗口关闭或进程中止，重启后至少能读取旧版本或已提交的新版本。

### 7.2 性能基线

使用接近本次真实规模的数据集验收：

- 约 2000 个会话；
- 会话文件总量约 150 MiB；
- 索引约 650 KiB；
- 单会话最大约 4 MiB。

建议目标：

| 场景                 | 目标                                                 |
| -------------------- | ---------------------------------------------------- |
| 索引正常的首屏加载   | 不读取全部会话；加载时间不随会话内容总量线性增长     |
| 主索引损坏、备份有效 | 使用备份完成首屏，不触发阻塞式全量重建               |
| 主索引和备份均损坏   | 500 ms 内进入可交互降级界面，重建在后台进行          |
| 正常进入后           | 不再自动启动 150 MiB 全量扫描                        |
| 流式生成             | 同一会话最多一个落盘任务运行，等待队列只保留最新快照 |

### 7.3 验证边界

完成前端改动后至少运行：

```powershell
bun run test:run -- <新增的会话持久化测试文件>
bun run build:tsc
bun run build:vite
```

文件原子替换、进程中止恢复和真实 Windows 文件占用不能只用 Vitest 证明。若涉及 Tauri command，还需要按工具测试指南执行 Rust 定向测试，并在真实 Tauri WebView 中验证：

- 正常保存与快速连续保存；
- 生成过程中关闭窗口再重开；
- 人工注入损坏索引后的备份恢复；
- 人工注入损坏会话后的隔离和 UI 可用性；
- 2000 会话规模下的启动耗时与后台 I/O。

## 8. 实施顺序建议

1. 先完成 Phase 0 的单写者、最新快照合并和原子替换，阻止产生新的损坏文件。
2. 再完成 Phase 1 的备份恢复、错误分类和非阻塞重建，避免已有损坏拖死界面。
3. 随后移除无条件 `repairIndex()`，建立性能基线。
4. 最后评估 SQLite 等长期迁移；不要用长期迁移推迟前两阶段。

在 Phase 0 和 Phase 1 同时完成前，不应把问题判定为已解决：只做原子写不能处理历史坏文件，只做恢复也不能阻止再次损坏。
