# 长文本粘贴与虚拟文本附件设计

- 日期：2026-10-30
- 状态：已实施，验证记录见文末
- 范围：桌面端聊天输入、消息展示、上下文和会话数据流

## 1. 产品定义

虚拟文本附件是保存在消息上的可编辑文本块。草稿阶段归当前会话输入管理；发送后，标题和全文写入该条消息，跟随会话保存、复制和导出。

用户界面统一称为「文本附件」，「虚拟」只用于开发文档和类型命名。真实文件继续沿用现有资产附件流程。文本附件直接保存字符串，存储所有权属于聊天模块，生命周期跟随草稿或消息。

这项功能解决长文本挤占输入区、修改材料需要往返文件管理的问题。材料全文仍参与模型上下文和 Token 计算。

## 2. 主要交互

### 2.1 长文本粘贴

建议默认开启「长文本粘贴为附件」，阈值为 **6,000 字符**，在现有输入设置面板中提供开关和阈值配置。阈值属于初始产品建议，可在真实窗口体验后调整。

- 只判断本次粘贴的 `text/plain` 字符数，达到阈值时转换；已有输入内容保持原样。启用 Base64 图片提取时，相关粘贴优先沿用图片处理流程。
- 字符数按 Unicode 码点计数；原始文本逐字保存，保留换行、缩进与首尾空白。
- 每次粘贴生成独立卡片，按创建顺序追加。即使内容相同，也保留为独立材料。
- 输入区维持焦点，光标保留在原位置，方便接着写问题。
- 存在选区时，转换仍保留选区原文；只有选择「直接粘贴文本」时，才采用编辑器原有的选区替换行为。
- 编辑器预览区、附件编辑器和导入恢复流程使用各自的文本编辑行为；自动转换只挂载到聊天输入框的用户粘贴入口。

转换后的草稿示意：

```text
┌──────────────────────────────────────────────────────┐
│ 文本  粘贴文本 1     8,432 字符       编辑   ···   ×   │
│       export function parseConfig…                   │
├──────────────────────────────────────────────────────┤
│ 帮我检查这段代码的边界条件。                         │
│                                                      │
│ 附件  …                                    发送      │
└──────────────────────────────────────────────────────┘
```

转换后短暂出现内联操作：「已添加文本附件 · 直接粘贴文本」。该操作按本次粘贴捕获的插入锚点，将卡片恢复成正文；输入继续变化后需同步映射锚点，无法定位时先让用户选择插入位置，避免覆盖后续输入。

「撤销」应回到粘贴前状态，同时移除新增卡片；「直接粘贴文本」则把本次材料插入正文，两者含义分开。附件卡片也提供「插入正文」操作，在当前光标处插入全文，成功后移除卡片。

### 2.2 卡片与编辑器

复用现有附件区域与长条卡片的视觉规格。文本卡片显示文本图标、标题、字符数和一行摘要；摘要折叠连续空白，正文维持原样。Token 沿用现有统计开关。

- 标题默认「粘贴文本 1」「粘贴文本 2」，由当前草稿分配序号，用户可重命名。
- 草稿卡片单击即编辑，右侧保留删除入口；更多菜单提供复制全文、插入正文、另存为文本文件。
- 附件菜单增加「新建文本附件」，用于手动输入和小段材料整理。
- 编辑面板复用项目通用对话框和现有代码编辑能力，包含标题、正文、字符数、保存和取消；宽窄窗口都保留完整操作区。
- 编辑期间使用独立副本；保存时原子替换附件，取消时保留原状态。关闭含改动的面板时确认是否放弃修改。
- 空白正文保留在编辑器中供继续编辑，保存按钮禁用；需要移除时使用删除操作。
- 附件编辑器内的发送快捷键仅作用于编辑器自身约定，聊天发送动作需等待编辑完成。

「另存为文本文件」通过系统文件保存交互生成用户选择的文件。创建与编辑文本附件本身只更新聊天数据。

### 2.3 发送后

消息气泡中继续显示文本附件卡片，点击打开预览，提供「编辑」入口。进入编辑后仍使用副本：

- 「保存到消息」更新该消息的材料，沿用现有消息编辑、持久化、同步和撤销通道。
- 会话有后续回复时，保存入口旁提示「后续回复保持原样」。下次生成使用更新后的材料。
- 「保存到新分支」复用现有消息分支编辑能力，将正文、真实附件和文本附件一起复制为独立快照。
- 历史附件的修改完成后，草稿中曾从它复制的材料保持独立。
- 正在生成时，可以预览材料；编辑保存遵循现有生成期间的消息编辑限制。请求启动时冻结全文快照，保证单次请求数据稳定。

## 3. 粘贴处理顺序与异常恢复

现有 `messageInputStore.handlePaste()` 只处理 Base64 图片，并且由 `extractBase64FromPaste` 开关提前返回。新增逻辑需要统一分流，两个开关独立生效。

推荐顺序：

1. 同步读取剪贴板类型、原文、会话标识、选区和草稿版本。
2. 纯文件、图片剪贴板继续走既有媒体行为；同时存在文件与文本时优先保持既有文件粘贴约定，避免重复导入。
3. 符合长文本阈值时，同步执行 `preventDefault()`，直接将原始全文创建为文本附件。本次文本中的 Base64 字符串作为材料保留，避免代码、日志或 JSON 因图片提取而改变。
4. 其余文本按现有 Base64 图片提取设置处理，最后回到普通编辑器粘贴。

长文本转换优先于 Base64 提取；关闭长文本转换后，图片提取仍按原设置运行。

**两个编辑器共享同一粘贴决策和草稿操作入口。** 原生 textarea 与 CodeMirror 都需要在默认插入发生前完成是否接管的判断；CodeMirror 的事件处理返回值也要反映事件已被接管，覆盖默认插入路径。

异步落盘完成前即可展示卡片，但要记录保存状态：

- 创建失败时完整恢复原文到原插入位置；若目标草稿已经切换，恢复到捕获的会话草稿。
- 单次材料超过 **1 MiB UTF-8** 时先确认，提供「添加文本附件」「直接粘贴文本」「取消」；原始数据始终保留。这是大体积操作提示阈值，实际可用上限在实施时根据编辑器与存储能力确定。
- 保存失败显示可行动提示：「草稿保存失败，请重试或复制内容」，保留内存数据和复制入口。
- 发送成功的判定沿用用户消息的实际保存结果；失败时保留可重试草稿，提交成功后才清除对应草稿快照。
- 发送期间继续输入或新加的附件归新的草稿版本，成功回调只清理已提交的那一版。

## 4. 数据模型与所有权

为消息增加独立字段，保持现有 `attachments?: Asset[]` 的契约。真实文件相关管理器、文件路径、转写和资产引用继续消费 `Asset`。

```ts
interface VirtualTextAttachment {
  id: string;
  kind: "text";
  title: string;
  text: string;
}

interface ChatMessageNode {
  // 原有字段保持
  virtualAttachments?: VirtualTextAttachment[];
}

interface ChatInputDraft {
  // 原有字段保持
  virtualAttachments?: VirtualTextAttachment[];
}
```

字符数、UTF-8 大小、摘要和 Token 从正文派生，避免持久化重复数据。第一版仅承载纯文本，代码与 Markdown 都通过原文保存。

所有权约定：

| 场景 | 处理方式 |
| --- | --- |
| 未发送材料 | 属于 sessionId 对应草稿；新会话草稿沿用当前草稿标识体系 |
| 发送 | 把附件全文复制为用户消息的不可共享快照 |
| 编辑 | 替换当前草稿或当前消息的附件对象 |
| 复制消息、分支、跨会话复制 | 深拷贝文本附件；独立消息中的附件生成新 ID |
| 重试、重建上下文 | 读取目标消息当前保存的快照 |
| 删除消息、删除会话 | 全文随对应消息数据一起删除 |
| 撤销删除或修改 | 由现有会话历史恢复消息及其全文 |

与其他附件共存时，第一版按「现有文件附件顺序 + 文本附件创建顺序」展示，发送顺序一致。以后需要混排时再引入统一顺序引用。

## 5. 草稿持久化与窗口同步

当前 `useChatInputManager` 将各会话草稿及剪贴草稿整体序列化到 localStorage（version 3）。长文本直接追加到该存储会放大容量与同步写入压力，实施时应同时调整草稿正文的持久化位置。

建议新增聊天专用的输入草稿存储封装，通过 `createConfigManager` 保存 `input-drafts.json`，复用其路径解析能力。内容包含各会话输入、真实附件引用、文本附件全文、临时模型选择和剪贴草稿；沿用现有防抖与串行写入方式。草稿正文由该封装统一管理，输入偏好继续使用现有设置存储。

- 主窗口负责写入；分离窗口通过现有输入同步通道提交带 sessionId 和草稿版本的更新。
- 虚拟附件编辑使用附件级更新操作，避免保存一张卡片时覆盖另一窗口刚输入的正文。
- 同一附件并发修改通过基准版本检测，提示重新载入或另存副本，保留本地编辑内容。
- 高频正文编辑使用防抖；附件创建、编辑保存、切换草稿和发送前触发明确保存。可显示简洁的「保存中 / 保存失败」状态。
- 首次读取新存储为空时迁移旧 version 3 草稿；新存储写入成功后再清理旧草稿数据。读取或解析失败时暂停写回，保留原文件与旧数据，下次继续恢复。
- 会话消息的文本附件随现有会话详情存储，进入会话详情和历史记录；会话索引只保留现有摘要字段。

## 6. 上下文与模型请求

扩展 `PipelineAttachment.source`，增加 `message-text` 数据源，内容直接为字符串；提供 `fromVirtualTextAttachment()` 转换入口。建议映射为 `type: "document"`、`mimeType: "text/plain"`，展示标题直接使用用户命名。

在 `attachment-resolver.ts` 的最前面识别该来源，直接返回 `rawText` 与格式化文本。转写候选筛选、资产刷新与媒体处理均需识别该来源，确保它始终走纯文本解析。

默认组装顺序：

1. 用户输入正文。
2. 现有真实附件，沿用当前占位和注入规则。
3. 文本附件，按卡片顺序逐份追加到同条用户消息。

正文为空、只有文本附件时同样允许发送。文本附件作为参考材料注入，全文只出现一次，保留模型实际读取内容与用户材料一致。默认无需向正文插入宏占位符。

- 标题作为显示元数据转义后进入已有附件包装格式；全文作为材料处理，附件中的宏语法保留为字面量。
- 不向材料额外赋予系统指令优先级。材料中的指令文本仍属于用户提供内容。
- 输入 Token 预览、消息 Token、上下文分析器、压缩摘要和真实请求均包含文本附件全文；摘要与发送共用材料包装格式。
- 超出模型上下文时，沿用已有提示和上下文管理能力；保留用户原文，明确提示需要缩减或调整上下文。
- 材料编辑成功时使对应摘要和 Token 缓存失效；统计缓存按附件 ID 与内容版本区分，内容版本可由内存 revision 管理。

## 7. 导入导出与兼容

- 会话原生 JSON 导出内嵌 `virtualAttachments` 全文，导入恢复可编辑卡片。
- 旧消息缺少该字段时视为空列表；新字段由消息复制、编辑、同步和导出显式保留。
- Markdown 等面向阅读的导出包含材料标题及完整内容，分隔符根据正文选择或转义，保持代码围栏和换行正确。
- 资产打包仍处理真实附件引用；文本材料跟随消息 JSON 即可。
- 外部格式缺少文本附件结构时，将标题和全文展开为该消息的普通文本，保证材料完整。
- 导入时校验字段类型、数量与内容大小；预览以文本或现有受控 Markdown 渲染，标题按文本展示。

## 9. 建议实施顺序

1. 补齐类型、消息持久化和管道文本解析，支持手动创建、编辑、发送文本附件。
2. 补齐草稿持久化与迁移、窗口同步、提交快照和失败恢复。
3. 接入两个输入编辑器的自动粘贴转换、普通文本恢复与撤销。
4. 接通历史消息编辑、分支复制、统计、上下文分析和导入导出，并同步附件系统架构文档。

四步共同构成首个完整版本。验证聚焦材料完整性、操作可恢复性和请求一致性：

- 阈值边界、选区保留、正文恢复以及一次撤销能还原整次粘贴。
- 仅有文本附件也能发送；真实附件混用时，请求材料各出现一次。
- 编辑取消保持原消息；修改消息和保存分支分别遵循各自所有权。
- 切换会话、重启恢复、发送失败和跨窗口编辑均保留全文，提交后继续输入的草稿独立存在。
- JSON 导出导入后全文与结构一致；Token 预览和上下文分析覆盖相同文本。

新增自动化测试围绕上述公开行为选择必要用例，复用已有覆盖。前端实施完成后按项目规范运行类型检查和 Vite 构建，在真实 Tauri 窗口走查粘贴、编辑与窄窗口体验。
