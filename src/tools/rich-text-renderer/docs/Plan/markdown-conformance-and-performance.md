## 已确认的产品约定（2026-10-25）

- **段落内单次回车产生可见换行**。主人明确偏好输入时的换行在显示时保留，后续兼容性修补应保护这一行为。空白行继续表达段落分隔。
- 同输入库对照使用相同换行策略，例如 `markdown-it` 的 `breaks: true`。官方默认输出差异与项目行为契约分别统计；修复优先级按内容正确性和实际影响安排。
- **文本末尾回车是否显示尾部空白行**仍待单独确认，当前行为保留；段内可见换行与末尾空白行分开讨论。
- 首轮 20/652 是严格静态 AST 比较的历史结果，包含预期的产品行为差异。后续报告需要显示产品配置与差异分类；该历史比例用于定位，质量评估结合具体问题。

## 第一项实施记录

### 运行入口

在仓库根目录运行：

```powershell
bun run rich-text:commonmark
bun run rich-text:check
bun run test:run -- scripts/rich-text/commonmark.test.ts
```

报告默认写入 `.tmp/rich-text-commonmark/report.md` 与 `.tmp/rich-text-commonmark/report.json`。可通过 `--out-dir <路径>`、`--timeout-ms <毫秒>` 调整输出目录与单例超时，默认 2000 ms。日常运行使用已入库的用例，离线可重复执行。

实现位于 `scripts/rich-text/`，复用现有 jsdom 依赖。官方 HTML 使用惰性 DOM 片段转换为语义树；实际 AST 直接映射，避免浏览器自动修复实际树而掩盖嵌套差异。解析在独立 Worker 中串行执行，每条输入有超时保护，超时后重建 Worker 并继续。启动失败或比较器内部异常使命令失败；规范差异、解析异常与超时计入报告。

脚本使用独立 TypeScript 配置，根 `tsconfig.node.json` 排除该目录，由 `rich-text:check` 连同被引用的解析代码进行检查。

## 差异复核：已确认的修复候选（2026-10-25）

本次用最小输入直接调用当前 `CustomParser.parse()`，并以已安装的 `markdown-it("commonmark", { breaks: true })` 对照，排除了单次回车策略造成的主干差异。同时阅读对应解析代码与节点组件确认写入/展示链路。复现脚本位于忽略目录 `.tmp/rich-text-commonmark/triage.ts`、`triage-extra.ts`，下方记录可独立复现的输入与结果。下列已完成项于本轮实施；其余项保留后续计划。

### 优先修：代码内容与围栏边界

- [x] **围栏长度错误导致后文错归属**。输入如下，预期是一个包含内部三个反引号的 `md` 代码块，随后为正文 `after`：

`````text
````md
```
inside
```
````
after
`````

实际产生多个错误分块：首个代码块内容为 `` `md ``，`inside` 成为正文，最后的代码块包含四个反引号和 `after` 且被标记为未闭合。起止围栏需记录字符种类与长度，结束围栏应匹配对应规则。定位：`parser/Tokenizer.ts` 的 `RE_CODE_FENCE_OPEN` 及结束围栏扫描。

- [x] **语言标记混入代码正文**。输入：

````text
```c++
int n = 1;
```
````

实际语言为 `c`，代码正文前多出一行 `++`。这会改变用户查看、复制的代码内容。语言/信息字符串应与正文分离。当前开头正则仅接受 `\w*`。

- [x] **波浪线围栏缺少支持**。`~~~js` 包裹的代码当前成为普通段落。与长度规则一起补齐，避免代码进入普通 Markdown/公式解析。

### 优先修：列表结构与编号

- [x] **列表项内的续段脱离列表**。输入：

```markdown
- first

  continuation

- second
```

预期 `continuation` 属于第一个列表项；实际成为根级段落，并将后续列表拆成另一个根节点。`parser/block/parseList.ts` 遇双换行直接结束当前项，尚未结合后续缩进判断列表项续段。该问题影响列表归属，与紧凑列表的段落间距策略分开处理。

- [x] **有序列表起始数字丢失**。`3. third` 换行接 `4. fourth`，实际 AST 只有 `ordered: true`，缺少起始数字。另一个独立缺口是 `components/nodes/ListNode.vue` 虽声明 `start`，模板尚未绑定 `<ol start>`。修复需同时贯通 token → AST → 实际列表元素。

### 随后补齐：链接与字符内容

- [x] **引用式链接缺少解析**。输入 `[foo]: /url "title"`，空行后 `[foo]`，实际将定义与引用都显示为普通文本；预期定义被消费，引用产生链接。定位：块级定义收集与内联引用解析目前缺少对应路径；后续还需处理前向引用和流式定义补全。
- [x] **正文字符实体原样显示**。输入 `&amp; &#35; &#x4e2d;`，实际文本内容仍为这三个编码串，预期可见内容为 `& # 中`。`TextNode.vue` 输出 Vue 文本节点，后续渲染也会保留这些编码。补齐普通 Markdown 文本的命名/数字实体解码，代码内容继续按字面值保留；解码结果仍通过文本节点输出，防止 `<` 等字符被重新解释为 HTML。现有 `decodeHtmlEntities` 主要用于 HTML 内容且只覆盖少数命名实体，需先确认复用边界。

### 暂缓或继续核实

- 四空格缩进代码当前成为普通段落，属于后续兼容性补齐项，优先级排在围栏截断、内容污染与列表归属之后。
- 紧凑列表的 `<p>` 包装、代码块末尾 LF、无标题链接的 `title: ""` 与属性省略，先结合组件展示与 AST/导出契约区分显示策略、比较器噪声和实际缺陷。
- 普通反斜杠转义、`***both***`、含反引号的双反引号行内代码、带标题链接、URL 中平衡括号与基本嵌套列表，在本次最小复现中主干语义正常；其余规范用例仍逐例判断。

固定语料、配置、运行时与机器信息。先预热，再交错执行版本与实现，采用可复现顺序，降低始终先跑某一版造成的偏差。文件读取、动态导入、实例构造、结果归一化和报告写入放在计时区外；冷启动另测。

### 流式与 Worker

分成连续处理与定时回放两种模式：

1. **连续处理**：固定 16、64、256 个 UTF-16 代码单元分块，逐次等待计算完成，用于衡量处理量和长输入增长趋势。采用保留代理对的确定性切分，记录实际 chunk 数；自身版本运行相同切分结果。
2. **定时回放**：先从 64 个代码单元 / 50 ms 的可复现节奏开始，按原定时刻投递输入，记录实际投递偏差、积压与合并，覆盖生产调度行为。网络等待与累计处理时间分别展示。

当前 Worker 只承担分词，AST 构造与后续处理留在主线程。计算对照可使用同一进程内的分词适配器隔离传输成本；真实 Worker 路径在 WebView 单独采样首次启动、热态往返与序列化成本。报告显式标注执行路径，之前替换 Worker 的正确性测试耗时仅作排查参考。

按需采集边界扫描、stable/pending parse、diff、patch apply 与队列 flush 的阶段数据，以及累计实际重解析字符数；计时开销另行检查。性能统计之外校验完成态与完整解析的语义，护栏触发或解析失败单列，保留错误上下文。

引用密集流的优化前采样显示，索引构建自耗时约占整体采样 29%，查找后续空白行的正则约占 8.2%，AST diff 也占有明显比例。多代码块流中，`isInsideCodeBlock` 与围栏开头检测占据显著时间，完整 buffer 的重复边界判断值得继续处理。实体密集静态输入则出现 `decodeMarkdownEntities` / `unescapeAll` 的解码热点。

### 已实施的两个优化

1. **按补丁范围维护 AST 索引。** `replace-node` 只清理旧子树并登记新子树；`text-append` / `set-prop` 更新目标和祖先的索引引用。插入、删除、范围替换与根替换继续完整重建，及时刷新发生偏移的路径。省去批末重复重建。
2. **引用定义的单行标题快路径。** 原实现对每条定义先向后搜索全文中的下一处空白行，连续定义区容易产生平方级扫描。现在优先在标题起始行调用标题解析器，需要跨行续写时才进入原有空白行限制路径。

批内索引需要逐步可用：后续 patch 可以引用刚插入或替换得到的 ID。旧调查中的“统一延迟到批末重建”建议已同步修正。

## 第二轮研究：稳定前缀与围栏边界（2026-10-25）

### 前缀复用的反例

对预设、规模化语料与 CommonMark 语料做了分块原型实验。直接把“旧稳定区 AST + 新增文本 AST”拼接，会改变原有输出。旧稳定区经常以单个 LF 结束；后续文本到达后，该 LF 可能成为双换行分段的一部分，或仍属于同一段落。

例如旧前缀 `first\n` 的 AST 含尾部 `hard_break`，扩展为 `first\n\nsecond\n` 后，完整解析的第一段只有文本。直接保留旧节点会残留该换行。即使检查新增片段前有空白分隔，也需要回看旧尾块。含空格的空白行还会影响当前 token 的合并方式。

该原型保留在 `.tmp/rich-text-bench/probe-stable.ts`，反例明细在 `stable-probe.json`。下一步的块级增量解析需要记录准确的源码范围、保留尾块回看，并处理内容编辑、回退与全局引用依赖；当前节点 `meta.range` 大多为占位范围，需要先补齐可用于失效判断的锚点。

## 内存补测（2026-10-25）

### 测量范围与口径

- 每个版本、输入和轮次使用独立子进程，避免进程峰值和前一版本对象相互干扰。父进程生成固定语料，子进程加载模块与输入，完成固定小样本预热并 GC 两次后记录起点。
- 每块处理和实际补丁应用后采样 RSS、heapUsed、heapTotal、external，记录采样峰值；RSS 与 commit 的进程高水位另读取 `bun:jsc.memoryUsage()`，包含加载、预热、多个处理周期与检查点，截止于末轮语义校验之前。
- 每个进程处理、完成、销毁同一输入三次。完成后先保留自然状态读数，再 GC 两次记录仍持有渲染状态的堆；销毁处理器和 AST 状态且函数返回后，再 GC 两次记录释放点。
- GC 后使用 `heapStats().heapSize`；`extraMemorySize` 是其中的子项，报告单列供分析。本机临时 20 MiB ArrayBuffer 探针确认，额外内存增长同时进入 heapSize，读数按包含关系解释。
- Worker 模式 RSS 覆盖整个 Bun 进程及分词线程，堆检查点仅覆盖主线程 isolate。分词 Worker 在各处理周期保留，任务结束后终止，贴合现有共享服务的生命周期。
- 末轮峰值和持有量先取样，再验证产物；末轮释放点包含语义校验后的运行时成本。细小末态增量还包含 JIT、模块缓存和采样记录，单凭三次释放点无法判定长期泄漏。
- 这些结果描述 Bun 计算管线；Tauri WebView 的 Worker、Vue/DOM、重型节点与整个桌面应用的占用仍需真实运行态测量。

新增入口 `bun run rich-text:memory:tauri`，默认要求静态前端实例。脚手架读取该实例已发布的构建快照，定位实际的 `RichTextRenderer-*.js` 导出，复用生成语料与完整解析语义比较。生产解析器、分词 Worker 和节点组件均沿用实际实现。`--allow-hmr` 留作脚手架排查入口，正式结果使用静态构建。

- 四类约 100 KiB 输入，每类连续挂载、完成、卸载三次；固定顺序为普通混排、代码围栏、引用密集、跨空行列表，共 12 个周期。各类开始前用至多 1,024 字符预热，四类共享同一主窗口和分词 Worker。
- 以 256 UTF-16 单元切块，通过真实 `StreamSource` 推入，每次等待 Vue 更新及一帧；关闭流式平滑和进入动画，保留默认 AST 节流与安全护栏。代码块设为展开，视口停留顶部，CodeMirror 继续按现有 IntersectionObserver 策略延迟初始化。
- 完成后等待 AST 与全量解析的归一化结果一致，再等待 1 秒，记录自然状态及 GC 后持有量。卸载后等待 1 秒，记录自然状态，再对主线程执行两次 GC、分词 Worker 执行一次 GC，记录释放点。
- 主线程与分词 Worker 分别通过 CDP `Runtime.getHeapUsage` 采样。`backingStorageSize`、`embedderHeapUsedSize` 等原始字段单独保存；下表仅列主线程 JS `usedSize`。
- 原生采样只跟踪身份核验后的应用 PID 及其后代，覆盖当前实例的 WebView2 浏览器、渲染、GPU、utility 和辅助进程。Private Bytes 汇总表达进程组私有内存；Working Set 汇总包含共享页重复计数。Vite、测试运行器和其他应用实例均在此进程树之外。
- PowerShell 每轮采样后休眠 250 ms，实际间隔还包含进程查询开销。本次保存 342 个样本，间隔中位数 700 ms、P95 1,157 ms、最大 1,468 ms。表中的原生峰值为采样峰值，短于采样间隔的尖峰仍可能遗漏。检查点引用最近的已完成原生样本，原始时间戳一并保留。

### 100 KiB 实测结果

主线程持有堆取三个周期的中位数；原生 Private Bytes 峰值取各周期采样峰值的中位数。单位均为 MiB：

| 输入       | 完成并 GC 后主线程堆 | 第 1 / 2 / 3 次卸载并 GC 后主线程堆 | 进程组 Private Bytes 峰值 | 进程组 Working Set 峰值 |
| ---------- | -------------------: | ----------------------------------- | ------------------------: | ----------------------: |
| 普通混排   |               110.60 | 78.07 / 78.19 / 78.20               |                  1,076.39 |                1,245.59 |
| 代码围栏   |               144.70 | 79.72 / 79.79 / 79.86               |                  1,018.29 |                1,151.71 |
| 引用密集   |               106.25 | 80.03 / 80.04 / 80.04               |                  1,214.49 |                1,383.37 |
| 跨空行列表 |               135.53 | 80.23 / 80.24 / 80.22               |                  1,259.11 |                1,445.23 |

分词 Worker 始终保持为同一个 target，各类 GC 后约 0.60 / 0.49 / 0.54 / 0.58 MiB，持有与释放检查点接近。每次卸载后，探针的组件代理和根元素弱引用均已回收，两个流订阅均已解除。DOM 节点数回到各类起点：普通混排为 8,588，后续类为 8,590；事件监听数均回到 3,578。

代码样本含 1,248 个短围栏。完成态整个页面共有 101,125 个 DOM 节点、14,990 个监听器，探针内有 63,754 个元素；卸载后回到 8,590 / 3,578。这使代码块头部、编辑器外围结构与长文档挂载策略成为后续值得单独评估的方向。跨空行列表的完成态主线程堆也较高；进程组原生峰值则以列表和引用样本更高，后续需同时关注分配速率与原生回收节奏。

### 回收观察与适用边界

- 首个普通混排大样本前的 GC 主线程堆约 45.21 MiB，第一次卸载后为 78.07 MiB，增加约 32.86 MiB；后两次为 78.19 / 78.20 MiB。这个首次大输入增量保留为待定位项，具体保留链需要堆快照。当前证据覆盖组件、DOM、订阅的回收及短周期重复行为，长期趋势仍需更长会话观察。
- 三次卸载点显示的进程组 Private Bytes 约为 543.50–789.55 MiB，Working Set 约为 742.59–944.50 MiB。主线程 JS 堆、Worker 堆、浏览器原生内存与进程组工作集分别解释。
- 排查阶段曾在 HMR 环境观察到卸载对象持续存活；同一类 10 KiB 混排输入关闭 Vue DevTools 事件采集后，连续三次组件与元素弱引用均可回收，DOM 计数保持稳定。正式静态构建没有安装该 DevTools hook，相关 HMR 读数单独留在排查报告中。
- 本轮覆盖当前版本的一组固定顺序窗口周期，保留顶部视口与节点懒挂载；全篇滚动、Mermaid/HTML 沙箱以及首屏/长任务耗时继续按独立场景推进。前端使用生产构建，后端为 debug，应用资源由 loopback HTTP 提供；完整发布包仍有后端构建与资源协议的环境差异。
- Bun 与 V8 的堆定义、模块加载和 UI 工作量各有口径。历史版本收益继续参考已有 Bun 对照；本轮 Tauri 数据描述当前版本真实 UI 的占用和回收行为。
